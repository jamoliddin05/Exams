GPIO and Interrupts: One Pin, Two Ways to Listen

"The first peripheral, one register at a time, all the way to an interrupt." GPIO fills in the empty slots of lesson 00's peripheral model, and every pin turns out to be a bit position you can calculate. Two buttons then show the two ways to listen: button A is polled once per millisecond, and button B interrupts through EXTI, the NVIC and the vector table of lesson 04.

1. The pins, the model, and what a register is (pin maps, slides 1–2)

Inside the chip the header positions disappear. Every pin is one bit position in its port's registers: pin n of GPIOA is bit n of IDR and bits 2n+1 : 2n of MODER.

3. MODER: what is this pin? (slides 5–6)

Offset 0x00, two bits per pin at bits 2n+1 : 2n.

ValueModeThe pin is…
00Inputread by IDR; nothing drives it
01Outputdriven by ODR
10Alternate functionhanded to a peripheral (UART, timer, SPI…) chosen by AFR
11Analogdisconnected from the digital logic, for the ADC or to save power
  • PA5 (LD4) as an output: pin 5 → bits 11:10 → write 01 there and leave the other 30 bits alone. In C that is GPIOA->MODER = (GPIOA->MODER & ~(3u << 10)) | (1u << 10);, taken apart in section 8.
  • The reset value is 0xEBFFFFFF. "Every pin is 11, analog, except PA13 and PA14, which are 10", alternate function. They are the SWD debug lines, and the debugger must reach the chip before any of your code has run.
  • Analog is the safe default. Nothing is driven, and a floating input draws no current.
  • But "an analog pin reads 0 in IDR, whatever voltage is on it". A button that reads 0 when pressed then reads pressed, forever.
  • "So input mode is written, never assumed." gpio_init() writes 00 explicitly.

4. OTYPER, OSPEEDR and PUPDR: drive, edge speed, pull (slides 7–9)

RegisterBits per pinCodesGPIOA resetThis lesson
OTYPER (0x04)10 push-pull, 1 open-drain0x00000000, all push-pullleft at reset
OSPEEDR (0x08)200 very low, 01 low, 10 high, 11 very high0x0C000000: PA13 = 11left at reset, very low
PUPDR (0x0C)200 none, 01 pull-up, 10 pull-down, 11 reserved0x24000000: PA14 = 10, PA13 = 01PA0, PA1 pull-up → 0x24000005
  • Push-pull drives "high and low, the normal choice". Every output pin has a P-MOS from the pin to 3.3 V and an N-MOS from the pin to ground. Their gates are driven together by the inverse of the ODR bit, so exactly one is on. A P-MOS conducts when its gate is low, an N-MOS when its gate is high.
  • Open-drain switches the P-MOS off for good. Only the N-MOS is left, with its drain on the pin. It can pull the pin low or let go, and high has to come from a resistor.
  • "Two open-drain outputs can share one wire safely." The worst they can do is both pull low. The wire is 1 only if every chip lets go, a wired-AND. This is how I²C puts many chips on two wires (lesson 09 sets OTYPER).
  • Two push-pull outputs on one wire, one driving high and the other low, connect 3.3 V to ground through two transistors. That is a short.
  • OSPEEDR "speed" is "how sharply the output switches", the slope of each edge. It does not set how often software can toggle the pin. Sharp edges are needed for SPI at tens of MHz, and they radiate more noise and cost more current. "Choose the slowest speed that works: it is the quietest."
  • PUPDR: "A pin connected to nothing is not 0 and not 1; it drifts, and reads randomly." A pull resistor gives it a default. A button wired to GND needs a pull-up: released, the pin reads 1; pressed, the button overpowers the resistor and the pin reads 0.
  • The reset value leaves the two debug lines pulled and every other pin floating:
PUPDR reset 0x24000000 = 00 10 01 00 00 00 ... 00
pin                       15 14 13 12 11 10 ...  0
PA14 = 10 pull-down, PA13 = 01 pull-up, the rest 00 none

OSPEEDR reset 0x0C000000: bits 27:26 = 11, PA13 very high, the rest very low

5. IDR and ODR: reading a pin, and writing it the obvious way (slides 10–11)

  • IDR: offset 0x10, one bit per pin, read only (writing it does nothing). It is "a live photograph of all 16 pins at the moment you read it".
  • To look at one pin, "shift it down to bit 0 and mask everything else away": (GPIOA->IDR >> 1) & 1u for PA1, or test GPIOA->IDR & (1u << 1).
IDR = 0x0000A001 = ... 1010 0000 0000 0001
                       15   12    8    4  0
PA15 = 1, PA13 = 1, PA0 = 1, every other pin = 0
(0x0000A001 >> 1) & 1 = 0      so PA1 is LOW
  • Two warnings. A pin in analog mode always reads 0 in IDR. A pin in output mode reads what it is actually doing, which is usually, but not always, what ODR asked for.
  • ODR: offset 0x14, one bit per pin, what each output should be. ODR |= (1u << 5) sets PA5 high, ODR &= ~(1u << 5) sets it low, ODR ^= (1u << 5) toggles it.
  • "These look like one step. They are three." This core is load/store (lesson 01), so it cannot change a bit in a peripheral register directly. GPIOA->ODR |= 1u << 5 compiles to:
movs r2, #160
movs r3, #32               r3 = 1 << 5
lsls r2, r2, #23           r2 = 160 << 23 = 0x50000000 (GPIOA)
ldr  r1, [r2, #20]    1.   READ   ODR   (offset 20 = 0x14)
orrs r3, r1           2.   MODIFY OR in bit 5
str  r3, [r2, #20]    3.   WRITE  ODR back

"Read, modify, write." Most of the time that is fine. Section 6 shows when it is not.

6. BSRR and BRR, and why BSRR is the safe one (slides 12–13)

  • BSRR: offset 0x18, write only, two halves. Bits 31:16 reset pins 15–0, bits 15:0 set pins 15–0.
  • A 1 at bit n → pin n goes high. A 1 at bit n + 16 → pin n goes low. A 0 anywhere → nothing changes for that pin.
  • "Because zeros mean leave alone, one write can set some pins, clear others and ignore the rest." The LED bar writes eight pins at once: GPIOB->BSRR = ((uint32_t)(uint8_t)~leds << 16) | leds;
  • BRR (offset 0x28) is the reset half on its own. GPIOA->BRR = 1u << 5 also sets PA5 low.
  • Suppose main() turns PA5 on with ODR |= 1 << 5, and an interrupt handler turns PA6 on with ODR |= 1 << 6. The interrupt arrives between main's load and its store.
  • main() writes back a copy of ODR it read before the handler changed it. "The handler's work is silently undone." This is lesson 03's lost update.
  • With BSRR there is nothing to read, so there is nothing stale to write back. GPIOA->BSRR = 1u << 5 compiles to a single str r2, [r3, #24] (offset 24 = 0x18).
  • "One store. An interrupt can land before it or after it, never inside it." That property is called atomic, and it is why BSRR exists.

7. AFR: which peripheral gets the pin? (slide 14)

  • When MODER says 10, alternate function, "AFR says which one". Four bits per pin, so it takes two registers: AFR[0] for pins 0–7 and AFR[1] for pins 8–15. Pin n sits in AFR[n / 8] at bits 4(n mod 8)+3 : 4(n mod 8).
  • "The number means nothing by itself." It is looked up in the datasheet's alternate-function table, and it is different for every pin.
  • The serial port is USART2 on PA2 and PA3, both AF1:
AFR[0] after uart2_init() = 0x00001100
  = 0000 0000 0000 0000 0001 0001 0000 0000
pin  7    6    5    4    3    2    1    0
                         AF1  AF1
  • "A wrong AF number gives a pin that looks configured and carries nothing", with no error and no fault. Lesson 06 meets that trap with a timer.
  • The LEDs and the buttons are plain inputs and outputs, so they never touch AFR.

9. Before any of it: the clock gate (slide 18)

  • Every GPIO register is dead until the port's clock is on: RCC->IOPENR |= RCC_IOPENR_GPIOAEN | RCC_IOPENR_GPIOBEN;, "FIRST, always". IOPENR has one bit per port: A bit 0, B bit 1, C bit 2, D bit 3, F bit 5.
  • Without it, "writes to GPIOA vanish and reads return 0", with no error and no fault. Lesson 04's Lab Part 0 showed it: the LED dead, everything else working, and both pieces of code looking correct.
  • So the order in gpio_init() is fixed. Every peripheral in the course starts the same way: "clock, configure, use".
1. clock the ports            RCC->IOPENR
2. set each pin's mode        MODER
3. pulls, types, speeds       PUPDR, OTYPER, OSPEEDR
4. only then use the pins     IDR, ODR, BSRR

10. Buttons: pull-up, active low, and bounce (slides 19–20)

A button is a switch to ground. Pressed, it connects the pin to 0 V. Released, it connects the pin to nothing, which is why the pull-up of section 4 is needed.

ButtonPin levelIDR bitbutton_down() returns
releasedhigh (pull-up wins)1false
pressedlow (switch wins)0true
  • "This is active low: the interesting state reads 0." The code hides it in one place: button_down(pin) returns pin_read(GPIOA, pin) == 0u.
  • "Metal contacts do not close cleanly. They hit, bounce apart, and hit again, for about a millisecond."
  • Wokwi's pushbutton simulates this. By default it makes 10 to 100 transitions over about a millisecond on every press, and the attribute "bounce": "0" turns it off.
  • "A program that treats every falling edge as a press sees many presses from one." Debouncing is part of reading a button.

11. Button A: poll, and believe only what holds (slides 21–22)

The main loop samples button A once per millisecond. A new level is believed only after it has "held unchanged for DEBOUNCE_MS samples in a row" (DEBOUNCE_MS is 20).

typedef struct {
    uint8_t  stable;     /* the level we have ACCEPTED: 1 = pressed */
    uint8_t  raw;        /* the most recent sample, believed or not */
    uint16_t held_ms;    /* samples in a row raw has stayed the same */
    uint32_t changes;    /* times raw has moved, bounce included    */
} debounce_t;

static int debounce_step(debounce_t *d, uint8_t raw)
{
    if (raw != d->raw) {                 /* level moved: restart the count */
        d->raw = raw;  d->held_ms = 0;  d->changes++;
        return 0;
    }
    if (d->held_ms < DEBOUNCE_MS) {
        d->held_ms++;
        if (d->held_ms == DEBOUNCE_MS && raw != d->stable) {
            d->stable = raw;
            return raw ? +1 : -1;        /* +1 press, -1 release */
        }
    }
    return 0;
}
  • main() starts with debounce_t a = { 0 }; (released, nothing seen) and calls debounce_step(&a, button_down(BTN_A_PIN)) every 1 ms. It returns +1 on a press, −1 on a release, and 0 the rest of the time.
  • In words: if the sample differs from the last one, remember it and start counting again. If it is the same, count. When the count reaches DEBOUNCE_MS and the level differs from what was accepted, accept it and report the change.
  • "The press is reported at ms 8, not ms 3", when the contact first touched. The delay is DEBOUNCE_MS after the last bounce, "the price of certainty". At 20 ms it is far below what a person notices.
  • changes went up at ms 3, 4 and 5: three level changes for one press. That is the "level changes seen at 1 kHz" the program prints, and why it is sometimes more than 1.
  • Slide 22, polling "is a filter". Bounce transitions are microseconds apart and samples a millisecond apart, so most bounces fall between two samples and are never seen (Figure 7). Button A reports one or two level changes per press because the sampling is too slow to see the mess. The button itself bounces just as much as B.
  • Polling "depends on the loop coming back". A printf at 115200 baud costs about 87 µs per character (10 bits / 115200 = 86.8 µs) and delays the next sample. For a button that is harmless. "For a pulse shorter than the loop, it is invisible."
  • "Polling is simple, cheap and predictable", often right for a human-speed button. It is wrong "when you must not miss an event, or when the CPU has better things to do than ask".

12. Button B: three hops from pin to function (slide 23)

  • "GPIO does not interrupt." A separate block, EXTI (extended interrupt and event controller), watches pins and raises interrupts.
  • The path is PA1 → EXTICR (which port?) → EXTI line 1 (edge, pending, mask) → NVIC IRQ 5 → vector 21 → handler. "Every arrow has its own switch, and every switch defaults to OFF."
  • NVIC_EnableIRQ() and NVIC_SetPriority() write the NVIC for you. Every EXTI register is written by hand.
  • One more switch sits in neither block. PRIMASK, a core register, turns off every interrupt at once. It is "the one switch that starts on" (0 = interrupts enabled).

Every register of the two blocks: EXTI (EXTI_TypeDef, base 0x40021800) and the NVIC (NVIC_Type in core_cm0plus.h, base 0xE000E100).

13. Hop 1: EXTICR picks the port (slide 24)

  • EXTI has 16 lines for GPIO, numbered 0–15. "Line n watches pin n", of the port that EXTICR chooses with a port code: A = 0, B = 1, C = 2, D = 3, F = 5.
  • Each line is a multiplexer: several inputs, one output, and a select number. "Only one input reaches the output at a time", so line 1 can watch PA1 or PB1, never both.
  • Each line gets 8 bits, four lines per register: line n → EXTICR[n / 4], bits 8(n mod 4)+7 : 8(n mod 4). The port code sits in the low bits of that byte.
  • Line 1 for PA1: EXTICR[0] bits 15:8 = 0, so EXTICR[0] = 0x00000000. Line 13 for PC13 (Lab Part 7): EXTICR[3] bits 15:8 = 2, so EXTICR[3] = 0x00000200.
const uint32_t line  = 1;                       /* = pin number */
const uint32_t shift = (line % 4u) * 8u;        /* = 8          */
EXTI->EXTICR[line / 4u] = (EXTI->EXTICR[line / 4u] & ~(0xFFu << shift))
                        | (EXTI_PORT_A << shift);
  • "PA1 and PB1 cannot both interrupt." They share line 1.
  • "Port A's code is 0, the reset value." Forget EXTICR and a port-A button works by accident. Move it to port C and it silently stops.
  • On the STM32C0, EXTICR is in EXTI. On an STM32F4 the same job is SYSCFG->EXTICR[], so code copied from an F4 tutorial will not compile here.

  • How this flag clears: the pending registers are write 1 to clear. Writing 0x2 clears bit 1 and leaves every other line alone, because writing 0 does nothing.
  • So the code assigns with =. A |= would read the other lines' pending bits and write their 1s back, "clearing edges nobody has handled yet".
  • Unmask last, once the edges are set and any stale pending bit is cleared.
  • C0-specific: rising and falling edges latch into separate registers, RPR1 and FPR1. Older STM32 families have a single PR.
  • The NVIC is ARM's, identical on every Cortex-M0+. EXTI lines 0 and 1 arrive together as IRQ 5 (EXTI0_1_IRQn).
  • Enable: NVIC_EnableIRQ(EXTI0_1_IRQn) writes 1 << 5 = 0x00000020 to ISER. Writing 0s to ISER does nothing, "the same zeros mean leave alone idea as BSRR".
  • Priority: this core has 4 levels, 0 (most urgent) to 3, stored in the top two bits of an 8-bit field (__NVIC_PRIO_BITS = 2). IRQ k uses IPR[k / 4], byte k mod 4, value prio << 6.

15. The last hop: the vector table, and the handler (slides 27–28)

When IRQ 5 fires, the CPU looks up the handler's address in the vector table at the start of flash. The first 16 entries belong to the core.

vector number  = 16 + IRQ = 16 + 5 = 21
vector address = 0x08000000 + 21 × 4 = 0x08000000 + 0x54 = 0x08000054
bytes there    = 3d 02 00 08   →  0x0800023D   (little-endian)
nm Main.elf    : 0800023c T EXTI0_1_IRQHandler
  • The word 0x0800023D is the handler's address 0x0800023C plus 1, the Thumb bit (lesson 01).
  • Calling the handler "is nothing magic". The hardware loads a word from a fixed address and jumps there. Your only job is to make sure the right function's address is in that word.
void EXTI0_1_IRQHandler(void)
{
    uint32_t mask = 1u << BTN_B_PIN;
    if ((EXTI->RPR1 | EXTI->FPR1) & mask) {
        EXTI->RPR1 = mask;
        EXTI->FPR1 = mask;
        b_edges++;
    }
}
  • "The handler is an ordinary function." It compiles to fourteen instructions, with "no special prologue, no special return".
  • It uses only r1–r3, which the hardware already saved on entry (lesson 03). It returns with an ordinary bx lr. The hardware loaded lr with a special EXC_RETURN value that tells the core to restore the interrupted program.
  • With the hardware's own saving on the way in and out, the whole visit is on the order of a microsecond at 48 MHz.

16. Clear the pending bit, and spell the name exactly (slides 29–30)

  • "The pending bit is EXTI's memory that an edge happened." The NVIC sees the line as long as the bit is set.
  • Forget to clear it and the handler returns with the line still pending, so the core goes straight back in (tail-chaining). main() never runs again.
  • The symptom is a board that works until the first press and then "freezes completely": the heartbeat stops and the serial port goes quiet. It has not crashed. The handler is running flat out, over and over (Lab Part 3).
  • startup.c fills vector 21 with a weak placeholder that points at Default_Handler, an infinite loop. A function named exactly EXTI0_1_IRQHandler is a strong symbol, and it replaces the placeholder when the program is linked. "The name is the only thing connecting your function to the hardware."
  • Misspell it, EXTI0_1_IRQhandler with one lower-case letter, and the build still reports 0 warnings:

  • "The 36 missing bytes are your handler." Nothing calls a function with the wrong name, so the linker deleted it as dead code. The first press jumps to Default_Handler and the board hangs.
  • Two defences. Look: arm-none-eabi-nm Main.elf | findstr IRQHandler, and every handler you wrote must show T. Check at run time: the banner compares vector 21 with Default_Handler and prints YOUR HANDLER IS NOT INSTALLED if they match.

17. Count in the handler, decide in main() (slides 31–32)

uint32_t edges = b_edges;                 /* one read of the counter      */
if (edges != b_seen) {                    /* new edges: restart the clock */
    b_seen = edges;  b_quiet_ms = 0;  b_armed = 1;
} else if (b_armed && ++b_quiet_ms >= DEBOUNCE_MS) {
    b_armed = 0;                          /* 20 ms of quiet: bounce over  */
    uint8_t down = button_down(BTN_B_PIN);
    ...                                   /* settled pressed, or released? */
}
  • The handler does the least it can: clear, count, return. In main(), "every edge restarts a 20 ms stopwatch; when the stopwatch finishes without another edge, the bouncing is over". Then it looks at the pin once to see where it settled.
  • b_edges is shared between the handler and main() without a lock. It is lesson 03's "one safe case": a single aligned 32-bit word, written by only one side. main() reads the old value or the new one, never half of each.
  • It is volatile, so the compiler reads it from memory every time instead of keeping a stale copy in a register.
  • Why not debounce in the handler? "A handler that waits 20 ms blocks everything of equal or lower priority for 20 ms." "Handlers record; main() decides." That rule survives into the RTOS of lesson 07.

18. Seven ways to get silence (slide 33)

"Every one of these builds with zero warnings and gives a board that does nothing, or nearly nothing." The last column says why that symptom follows.

  • This is "the debugging checklist for every interrupt in the rest of the course": walk the path of Figure 9 hop by hop and read each register back. The banner does exactly that.
  • A quick split: if FPR1 bit 1 never becomes 1, EXTI never saw the edge (clock, MODER, EXTICR, FTSR1). If it becomes 1 and stays 1 with no handler run, the request stops after the latch (IMR1, ISER, or PRIMASK).

  • The first enters the handler with RPR1 bit 1 set and counts one clean edge. The second enters it with nothing pending, so the if is false and nothing is counted. "Never trust the vector, read the pending bit." (Predicted from RM0490, not yet watched.)
  • What carries forward: slide 4's table works for every pin of every port, so bit positions are calculated, never looked up.
  • "Read-modify-write versus a single store" is the most common concurrency bug in embedded code, and you can now see it in a disassembly.
  • Poll or interrupt is a choice made on evidence. Both were measured on the same button.
  • "The interrupt path is the same shape everywhere." A timer, a UART, an ADC each end in a pending bit, an NVIC line and a vector with an exact name (lessons 06, 08, 09).
  • "The polled millisecond is lying a little." tick_wait() polls SysTick's COUNTFLAG, which remembers only one wrap. While a printf blocks for 5 ms, four ticks are lost and ms_now runs slow. Lesson 06 turns SysTick into an interrupt.

General idea vs this chip

Exam focus
  • Pin n: 1-bit registers bit n; MODER, OSPEEDR, PUPDR bits 2n+1 : 2n; AFR[n / 8] bits 4(n mod 8)+3 : 4(n mod 8); BSRR set bit n, reset bit n + 16. Pin 13: MODER 27:26, AFR[1] 23:20, BSRR 13 and 29.
  • Codes: MODER 00 in, 01 out, 10 AF, 11 analog; PUPDR 00 none, 01 up, 10 down. MODER resets to 0xEBFFFFFF: all analog except PA13, PA14 (SWD) at 10.
  • Clear, then set: pin_mode(GPIOA, 4, OUTPUT) on 0xEBFFF7A0 → & ~0x300 = 0xEBFFF4A0 → | 0x100 = 0xEBFFF5A0. A pull-down on PA6 from 0x24000000 → bits 13:12 = 10 → 0x24002000.
  • MODER |= 1u << 10 leaves 11 as 11 (still analog). MODER = 1u << 10 makes the other 15 pins inputs, SWD included.
  • BSRR: PA0 high and PA5 low in one write = (1 << 0) | (1 << 21) = 0x00200001. LED bar with leds = 0x81 → 0x007E0081.
  • ODR |= is ldr, orrs, str: an ISR between the load and the store is overwritten by the stale copy. BSRR is one str, atomic.
  • EXTICR: line n → EXTICR[n / 4], bits 8(n mod 4)+7 : 8(n mod 4), codes A 0, B 1, C 2, D 3, F 5. PB7 → EXTICR[1] = 0x01000000. Port A is code 0, the reset value.
  • IRQs: lines 0–1 → IRQ 5, 2–3 → IRQ 6, 4–15 → IRQ 7. Vector 16 + n at 0x08000000 + 4(16 + n): IRQ 5 → 21 at 0x08000054, IRQ 7 → 23 at 0x0800005C. The word holds the handler address + 1 (Thumb bit).
  • NVIC: ISER bit n enables IRQ n. Priority IRQ k → IPR[k / 4], byte k mod 4, prio << 6, and 0 is the most urgent: IRQ 5 prio 2 → 0x00008000; IRQ 7 prio 1 → 0x40000000.
  • The EXTI flag clears by writing 1 to RPR1 / FPR1 with =, never |=. Forget it and the handler runs forever: a frozen board, not a crash.
  • Slide 33 silences: clock gate, MODER, PUPDR, EXTICR, IMR1, NVIC enable, handler name. FPR1 stuck at 1 means the path stops after the latch.
  • Debounce with DEBOUNCE_MS = 3, samples 0 0 1 0 1 1 1 1: the press is reported at ms 8 and changes = 3. A 1 kHz poll filters bounce; EXTI sees every edge.
  • Handlers record, main() decides. b_edges is one aligned word with one writer: volatile, no lock needed.
