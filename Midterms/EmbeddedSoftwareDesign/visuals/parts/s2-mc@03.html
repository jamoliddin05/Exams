Question 12 · L03, why an ISR is an ordinary C function

On the STM32C031 an interrupt handler is an ordinary function, void TIM3_IRQHandler(void) { ... }, with no special keyword or macro. Why can a plain C function safely interrupt any code?

  1. A The compiler sees the _IRQHandler suffix and adds code that saves all sixteen registers. No. The name matters only to the linker, which puts the address in the vector table. A misspelt name compiles, links and does nothing.
  2. B Handler mode has its own bank of R0–R12, so the interrupted code's registers are never touched. No. The core has one set of R0–R12. Handler mode only forces the stack pointer to MSP.
  3. C On entry the hardware itself stacks R0–R3, R12, LR, PC and xPSR, exactly the registers AAPCS lets a function destroy; the compiler saves any R4–R11 the handler uses, as in every function. Correct. The hardware does the caller's half of AAPCS, and the handler's own prologue does the callee's half.
  4. D The startup code calls every handler through a wrapper function that saves and restores all registers. No. The hardware reads the vector table and jumps straight to the handler's address.

Answer: C. AAPCS splits the registers in two. A called function may destroy the caller-saved R0–R3, R12 and LR, and must give back the callee-saved R4–R11. On interrupt entry the hardware pushes exactly the caller-saved set, plus PC and xPSR: 8 words, 32 bytes.

The callee-saved half is handled by the handler's ordinary prologue, as in every C function. So, seen from the interrupted code, the handler behaves like a function call that happened between two instructions. No keyword and no ISR() macro are needed.

Exam line

An interrupt is a hardware-forced function call. The hardware pushes R0–R3, R12, LR, PC and xPSR (8 words, 32 bytes), exactly the set AAPCS lets a function clobber, so an ISR can be an ordinary C function. Its name puts it in the vector table.

Question 13 · L03, tearing

volatile uint64_t ticks; is incremented by the SysTick handler and read in main() without masking. The read compiles to two 32-bit loads, low word first. ticks is 0x00000000_FFFFFFFF when main() loads the low word, and the SysTick handler runs before main() loads the high word. What value does main() get?

  1. A 0x00000000_FFFFFFFF No. That is the old value. main() gets it only if both loads happen before the handler.
  2. B 0x00000001_FFFFFFFF Correct. Old low word 0xFFFFFFFF, new high word 0x00000001.
  3. C 0x00000001_00000000 No. That is the new value, which main() gets only if both loads happen after the handler.
  4. D 0x00000000_00000000 No. That is the torn value for the other order, high word first: old high 0, new low 0.

Answer: B. The low word is loaded before the increment, so it is the old 0xFFFFFFFF. The increment carries into the high word, which becomes 0x00000001, and main() loads that new high word. Half old and half new gives 0x00000001_FFFFFFFF = 8 589 934 591.

Nobody ever stored that number. It is about twice the real count of 4 294 967 296. This is tearing: one logical value collected in two bus accesses with an interrupt between them. volatile does not prevent it, because both loads really happen. Copy the value inside __disable_irq() / __enable_irq().

Exam line

Tearing: a reader that needs two bus accesses for one logical value is interrupted between them and gets half old, half new, a number never stored by anybody. It hits a uint64_t on a 32-bit machine and a multi-field struct. Fix: a critical section around the copy.

Question 14 · L03, a critical section on this chip

main() and a timer ISR both increment uint32_t counter on the STM32C031, which has one Cortex-M0+ core. Which code in main() makes its increment safe?

  1. A volatile uint32_t counter; and a plain counter++; No. volatile makes the accesses real. The ISR can still land between ldr and str.
  2. B os_mutex_lock(&m); counter++; os_mutex_unlock(&m); No. A mutex asks the scheduler not to switch threads. The hardware starts the ISR without asking the scheduler.
  3. C do { v = __LDREXW(&counter); } while (__STREXW(v + 1, &counter)); No. That is the tool for two cores, and the Cortex-M0+ has neither ldrex nor strex.
  4. D __disable_irq(); counter++; __enable_irq(); Correct. cpsid i sets PRIMASK bit 0, so the ISR cannot start until cpsie i.

Answer: D. Between an ISR and main() on one core, mutual exclusion comes from turning interrupts off: the other context cannot run if it cannot start. __disable_irq() is the single instruction cpsid i, which sets bit 0 of PRIMASK. The ldr, adds, str then run as one indivisible sequence, and __enable_irq() (cpsie i) clears the bit again.

An interrupt that arrives inside the region is held pending and runs right after cpsie i. It is delayed, not lost, and it reads the updated value.

Exam line

This chip's answer is a critical section by masking: __disable_irq(); counter++; __enable_irq();. Each call is one instruction, cpsid i / cpsie i, and changes one bit, PRIMASK bit 0. volatile makes accesses real; a critical section makes a sequence indivisible.
