RTOS: Writing the Thing That Runs Your Tasks

Lesson 06 ended at the superloop's ceiling: every job must be short, or it delays all the others. This lesson lifts that limit with a preemptive kernel of about 300 lines: SysTick decides, PendSV switches, and every task runs on its own stack through a second stack pointer, PSP. The same kernel then shows priority inversion, a stack overflow that does not crash, and a HardFault that names its line.

1. The job that never yields (pin maps, slide 1)

A CPU hog is a job that keeps the CPU and never gives it back, like the prime search for (;;). Put it in lesson 06's superloop and nothing else ever runs again: the LED bar freezes, the buttons die, the report stops.

  • "Cooperative scheduler → one CPU hog can stop the whole system." The superloop is one: each job runs until it chooses to return, so the system works only while every job agrees to be short. The job itself decides when it stops.
  • "Preemptive scheduler → the RTOS can forcibly stop (preempt) the CPU hog." The kernel decides, on a timer interrupt, and later carries the hog on from exactly where it was.
  • On a Cortex-M, preemption takes one interrupt (SysTick), one exception (PendSV) and a second stack pointer (PSP).
  • Pins: PA0 button A (bar speed) and PA1 button B (hog on or off), inputs with pull-ups; PA2 and PA3 USART2 TX and RX (AF1) for the serial monitor; PB0–PB7 the LED bar, one output per LED.

2. A task is a stack and nine numbers (slide 2)

A C function that is running is, at any instant, its stack, its registers (r0–r12, lr, pc, xPSR) and its stack pointer. Save all of that and the function can be put away. Restore it and it continues as if nothing happened.

typedef struct os_task {
    uint32_t   *sp;          /* MUST be first - the assembly reads [tcb + 0] */
    const char *name;
    uint8_t     prio, base_prio, state;
    uint32_t    wake;
    ...
} os_task_t;

The registers live on the task's own stack while it is switched out, so the TCB only has to remember one number: where the stack pointer was.

3. The core's own registers and two stack pointers (slides 3, 3b)

These registers have no address. They live inside the core, and only two instructions reach them: MRS (special register to rN) and MSR (rN to special register). CMSIS wraps each one in an inline function.

  • MSP serves every exception handler, and main() after reset. PSP serves Thread mode when CONTROL.SPSEL = 1: in this kernel, every task, each on its own stack.
  • Handlers always run on MSP, a stack no task owns. So a task's stack only has to hold that task, plus the 8 words the hardware pushes on entry.
  • EXC_RETURN is not a register. It is the number in lr while a handler runs. 0xFFFFFFFD means "return to Thread mode, restore from PSP, keep using PSP", and every switch in this kernel returns with exactly that value.
  • While a task runs, CONTROL = 0x00000002: SPSEL = 1 (PSP), nPRIV = 0 (privileged). The kernel never writes CONTROL; the exception return sets SPSEL.

4. The System Control Block: ICSR and SHPR3 (slide 4)

The SCB (SCB_Type in core_cm0plus.h) is memory-mapped at 0xE000ED00, SCS_BASE 0xE000E000 + 0xD00. Like SysTick it is part of the core, so it is the same on every Cortex-M0+. The kernel writes two of its nine registers.

+0x00 CPUID   +0x04 ICSR (written)   +0x08 VTOR   +0x0C AIRCR   +0x10 SCR
+0x14 CCR     +0x18 reserved         +0x1C SHPR2 (SVCall)          +0x20 SHPR3 (written)
+0x24 SHCSR
  • ICSR is write-1-to-act. Writing PENDSVSET pends PendSV, writing PENDSVCLR cancels a pending one, and zeros do nothing. So the kernel writes the bit alone with =, never |=.
  • SHPR2 and SHPR3 hold one byte per system exception. This chip implements only the top two bits of each byte (__NVIC_PRIO_BITS = 2), so there are four levels, 0–3, and a priority p is written as p << 6.
  • NVIC_SetPriority(PendSV_IRQn, 3) writes the SCB, not the NVIC. CMSIS picks the word and the byte from the exception number.
  • SysTick (0xE000E010) is the kernel's third core block, used as in lesson 06. SysTick_Config(48000000 / 1000) loads 47999 for a 1 ms tick and also leaves SysTick at priority 3.
pend PendSV    ICSR = 1 << 28                    = 0x10000000
cancel it      ICSR = 1 << 27                    = 0x08000000
priority 3     byte = 3 << (8 − 2)               = 0xC0
SHPR3          SysTick in byte 3 (bits 31:24), PendSV in byte 2 (bits 23:16)
               0xC0 << 24 | 0xC0 << 16          = 0xC0C00000

5. PendSV: deciding vs switching (slide 4b)

A switch must never happen inside another interrupt handler. That handler's frame is on MSP, half-finished, and swapping the task beneath it would return it into the wrong world. So switches happen in one place only, PendSV, a system exception with two properties.

  • It is triggered by software. SCB->ICSR = SCB_ICSR_PENDSVSET_Msk sets its pending bit. Nothing else ever raises it.
  • This kernel gives it the lowest priority, 3. So it runs only when no other handler is active, after every other interrupt has finished, on the way back to a task (tail-chained).
static void schedule(void) {        /* called with interrupts masked */
    os_task_t *n = pick();  os_next = n;
    SCB->ICSR = (n != os_current) ? SCB_ICSR_PENDSVSET_Msk : SCB_ICSR_PENDSVCLR_Msk;
}

Why PENDSVCLR: if the current task should keep running after all, the cancel stops a switch requested earlier, which was chosen from information that is now stale.

6. One switch, step by step (slides 4c, 5, 6)

  • Deciding and switching are different steps. Steps 3 to 5 can happen anywhere; steps 7 and 8 happen only in PendSV. Steps 2 to 9 run in Handler mode on MSP.
  • SysTick is only one way in. os_delay(), a mutex unlock and a queue put also call schedule() and join at step 4, so a task that sleeps does not wait for the tick to be switched out.
  • The hardware does half the work. Every exception entry stacks the same 8 words (r0–r3, r12, lr, pc, xPSR). PendSV's own code saves the other 8, r4–r11.
  • A switched-out task is "sixteen words and one pointer". tcb->sp points at its r4, and its hardware frame starts 32 bytes on, at r0. From tcb->sp: r4–r7 at +0, r8–r11 at +16, r0–r3 at +32, r12, lr, pc, xPSR at +48. The saved pc is at +56, word 6 of the hardware frame.

PendSV_Handler is a naked function (no compiler prologue), at 0x08000700 in Main.elf: 34 instructions, 88 bytes with its literal pool. "That is the whole of multitasking."

    cpsid i
    ldr   r3, =os_current
    ldr   r1, [r3]           @ r1 = the task being left
    cmp   r1, #0
    beq   1f                 @ the very first switch has nothing to save
    mrs   r0, psp            @ 1  r0 -> A's hardware frame
    subs  r0, #32            @ 2  reserve 8 words ...
    str   r0, [r1]           @    ... tcb->sp = psp - 32
    stmia r0!, {r4-r7}       @ 3  r4-r7 at +0, r0 -> +16
    mov   r4, r8             @ 4  (and r5,r9 / r6,r10 / r7,r11: 4 movs)
    stmia r0!, {r4-r7}       @    r8-r11 at +16: A fully saved
1:  ldr   r2, =os_next
    ldr   r1, [r2]
    str   r1, [r3]           @    os_current = os_next
    ldr   r2, =os_switch_count  @ ldr / adds #1 / str: count++
    ldr   r0, [r1]           @ 5  r0 = B's saved sp, at B's r4
    adds  r0, #16            @ 6  skip to B's r8-r11 ...
    ldmia r0!, {r4-r7}       @    ... load them, r0 -> +32
    mov   r8, r4             @    (and r9,r5 / r10,r6 / r11,r7)
    msr   psp, r0            @ 7  PSP -> B's hardware frame
    subs  r0, #32            @ 8  back to B's r4 ...
    ldmia r0!, {r4-r7}       @    ... r4-r7 restored last
    cpsie i
    ldr   r0, =0xFFFFFFFD    @ 9  EXC_RETURN: Thread mode, PSP
    bx    r0                 @    hardware pops B's 8 words, B's pc included
  • sp must be the TCB's first field, because ldr r0, [r1] reads [tcb + 0]. os_current and os_next are not static, because the assembly reads them by name.
  • Why mrs r0, psp and stmia, not push: PendSV runs in Handler mode, where push would use MSP. stmia only counts upward, so the code steps down 32 bytes first.

A desktop OS switch has the same shape: decide in one place, switch later in a deferred low-priority step, save half the registers on entry and the other half in the switch. Much more state moves.

"What makes the RTOS switch cheap is what it leaves out": no address space, no FPU state, no privilege change to undo. That is also why one bad pointer in any task can overwrite every other task.

7. Why r8–r11 go the long way round (slide 7)

  • stmia r0!, {r4-r11} would do it in one instruction on a Cortex-M3. On this core it does not exist. The M0+ runs Thumb-1 plus six (lesson 01), and its stm and ldm have an 8-bit register list that reaches only r0–r7. push and str are limited to the low registers too.
  • So r8–r11 are copied into r4–r7, which are already saved and free, and stored from there. Restoring runs the trick backwards: r8–r11 first, r4–r7 last, so the copy is not overwritten.
  • mov r4, r8 is legal: mov between low and high registers is one of the few Thumb-1 instructions that reach r8–r12. In the disassembly, sl and fp are r10 and r11, their old APCS names.
  • The first draft did not assemble: GCC's default inline-assembly syntax rejects subs r0, #32 on this core. One line, .syntax unified, fixed it.

8. The first switch: forging a frame (slide 8)

A new task has never run, so it has never been preempted, so there is no saved context to restore. os_task_create() builds one: the stack the task would have if it had just been interrupted at its first instruction.

*--sp = 0x01000000u;                   /* xPSR: only the Thumb bit         */
*--sp = (uint32_t)fn & ~1u;            /* pc:   the function's start       */
*--sp = (uint32_t)task_exit;           /* lr:   where it goes if it returns */
*--sp = 0u; *--sp = 0u; *--sp = 0u; *--sp = 0u;   /* r12, r3, r2, r1      */
*--sp = (uint32_t)arg;                 /* r0:   its argument (AAPCS)       */
for (int i = 0; i < 8; i++) *--sp = 0u;           /* r11..r4              */
  • xPSR's T bit (24) must be 1. Returning with it clear asks for ARM state, which the M0+ does not have: a HardFault at the task's first instruction, on the first switch into it. The flags N, Z, C, V can be anything. The stack is chosen by EXC_RETURN, not by xPSR.
  • arg goes in the r0 slot, because AAPCS passes a function's first argument in r0. The task receives it as a normal parameter.
  • lr is task_exit, so a task function that returns is parked for good instead of wandering off into memory.
  • os_start() pends the very first switch from main(), which runs on MSP. PendSV returns with 0xFFFFFFFD, so execution never comes back to main().

9. Who runs next: pick() (slide 9)

static os_task_t *pick(void)
{
    uint32_t cur = os_current ? (uint32_t)(os_current - tasks) : 0u;
    os_task_t *best = 0;
    for (uint32_t i = 1; i <= n_tasks; i++) {
        os_task_t *t = &tasks[(cur + i) % n_tasks];
        if (t->state == OS_READY && (best == 0 || t->prio > best->prio)) best = t;
    }
    return best;
}
  • Fixed-priority preemptive: the highest-priority READY task runs, always.
  • Round-robin among equals: the search starts after the current task, and only a strictly higher priority replaces a find, so tasks of equal priority take turns, one tick each.
  • Idle, priority 0, is always ready, so there is always an answer.

10. Which priority numbering? Kernel vs NVIC (slide 9)

"Priority numbers here run the other way from the NVIC." In this kernel, as in FreeRTOS, a higher number is more urgent. In the NVIC, 0 is most urgent. Two numbering schemes on one chip: always say which one you mean.

  • The kernel's numbers are just a uint8_t compared by pick(). __NVIC_PRIO_BITS = 2 limits interrupt priorities, not task priorities: a task at 4 is legal, and it outranks every other task.
  • Thinking "low number = urgent" for a task backfires. Created at 4 to make it the least urgent, the hog becomes the most urgent task and, always READY, starves everything (Figure 1, last case).

11. The tick, sleeping, and a hog that does not hurt (slides 10–11)

ticks++;
if (os_current) os_current->ticks++;           /* who was running: CPU use */
for each task: if SLEEPING and (int32_t)(ticks - wake) >= 0 -> READY;
schedule();                                     /* pend PendSV if needed    */
  • os_delay(ms) marks the task SLEEPING, asks for a switch, and the task is gone until the tick wakes it. The CPU is not waiting for it: someone else runs.
  • os_delay_until(&last, period) is lesson 06's at += period as a call. The task wakes on a fixed grid however long its own work took, so the bar's frames stay 60 ms apart while the hog runs flat out.
  • Busy-waiting (lesson 05) spins at 100% CPU, and nobody else runs meanwhile. Sleeping costs no CPU, and every other READY task runs.
  • The per-task ticks counter is statistical profiling: each tick charges one millisecond to whoever was running. Over a second, that is each task's CPU share.

Measured, scenario 1 (Figure 1, middle case): with the hog on, it takes every spare cycle (100%), yet bar and button, at higher priority, are serviced on time. Each wakes, preempts the hog within a tick, works a few microseconds and sleeps again, so they show 0% and still work. Press B and the hog's share passes, whole, to idle. About 420 switches a second: the button wakes 200 times a second and the bar about 17, and each visit is two switches, in and out.

12. Sharing: the mutex (slide 12)

Two tasks that touch the same thing need mutual exclusion, as in lesson 03. Masking interrupts works, but for a long critical section it freezes the whole system. A mutex blocks only the tasks that want this resource.

void os_mutex_lock(os_mutex_t *m)
{
    uint32_t pm = enter();                       /* PRIMASK, as always   */
    while (m->owner != 0) {
        os_current->state      = OS_BLOCKED;     /* wait - off the CPU   */
        os_current->waiting_on = m;
        schedule(); leave(pm);  pm = enter();    /* switched out here    */
    }
    m->owner = os_current;
    leave(pm);
}
  • The kernel's own bookkeeping is protected by masking interrupts for a few instructions, lesson 03's tool unchanged. enter() saves PRIMASK and masks; leave(pm) restores the saved value, so critical sections nest and stay correct inside a handler.
  • The switch happens at leave(pm): PendSV is pending and waits only for the mask to lift.
  • A busy flag instead (while (busy) { }) spins on the CPU. If the waiter has the higher priority, the holder never runs again to clear the flag.
  • "The mutex is a way to make a long critical section cheap for everyone who does not need it."

13. Priority inversion and priority inheritance (slides 13–14)

Three tasks. High needs the mutex briefly every 100 ms. Low holds it for 30 ms at a time. Mid never touches it, but computes for 120 ms. High blocked by low is legitimate: low holds what high needs. Then mid preempts low, low cannot finish and release the mutex, and high is now waiting for mid, a task it outranks that shares nothing with it.

  • Mars Pathfinder, 1997: the lander kept resetting because a high-priority bus task was starved through exactly this pattern. Engineers reproduced it on the ground and fixed it by turning on one flag, remotely.
  • The fix, priority inheritance: while low holds a mutex that high is waiting for, low borrows high's priority. Mid can no longer preempt it. Low finishes, unlocks, drops back to base_prio, and high goes. The kernel raises the holder; it never lowers a third task.
#if OS_PRIORITY_INHERIT
    if (m->owner->prio < os_current->prio) m->owner->prio = os_current->prio;
#endif
/* os_mutex_unlock() restores base_prio */

Measured, scenario 2, five seconds each: with OS_PRIORITY_INHERIT 1, high's worst wait is 10 ms and no wait is over 40 ms; with 0, the worst wait is 110 ms and 6 of 49 waits are over 40 ms. Same tasks, same code, one #define. Low's critical section is 30 ms, so any wait over 40 ms is time high spent waiting for mid.

Limitation, stated plainly on the slide: this inheritance is right for one mutex at a time. A task holding two, with different waiters, needs a real implementation; FreeRTOS's is several hundred lines.

14. Queues: data between tasks, and from interrupts (slide 15)

A mutex protects shared data. Often the better design is not to share it: give it to someone. A queue copies items in and out, and blocks a reader while it is empty and a writer while it is full.

os_queue_put(&q, &item);            /* task: blocks if full   */
os_queue_get(&q, &item);            /* task: blocks if empty  */
os_queue_put_from_isr(&q, &item);   /* ISR: never blocks - returns 0 if full */
  • An interrupt handler must never block: there is no task to put to sleep, only a handler on MSP. So the ISR version reports "full" and lets the handler decide. Neither os_queue_put() nor os_mutex_lock() belongs in a handler.
  • It calls schedule(), so a task waiting on the queue can be made ready inside the interrupt. The switch to it happens the moment the last handler returns.
  • This is lesson 08's design: the UART receive interrupt puts bytes in a queue, and a protocol task blocks on it, using no CPU until a byte arrives.

15. Sizing a stack, and an overflow that does not crash (slides 16–17)

  • os_task_create() fills each stack with 0xDEADBEEF. The stack grows down, so the words at the bottom that still say 0xDEADBEEF were never reached. Counting them gives the high-water mark, the deepest the stack has ever been.
  • Measured, used / size in words: bar 24 / 128, button 30 / 128, hog 20 / 128, idle 16 / 64, report 115 / 512. printf is the expensive one: 115 words, 460 bytes.
  • "The method matters more than the numbers": run the program, exercise every path, read the high-water mark, add a margin. "A stack sized by guessing is wrong in one of two directions, and only one of them is visible."
  • Too small, measured: the report task gets 96 words and needs 115. Nothing crashed. It wrote 115 − 96 = 19 words below its stack, where the linker had put primes, the hog's counter. The counter then read 536 871 010 = 0x20000062, a stack address.
  • What people expect is a crash at the guilty task. What it usually is on an MCU is another task's data quietly wrong, so the bug looks like it is in the victim (the hog). The high-water mark catches it; bigger cores use an MPU guard region, and FreeRTOS can check on every switch. Nothing on this core checks the stack pointer, and the linker cannot know how deep a stack will go at run time.

16. A HardFault that says where (slide 18)

  • On a fault the hardware stacks the usual eight words and enters HardFault_Handler, on PSP's stack if a task was running. Bit 2 of lr (EXC_RETURN) says which stack: 1 = PSP (0xFFFFFFFD, a task faulted), 0 = MSP (0xFFFFFFF1, a handler faulted). See Figure 2.
  • Word 6 of the frame is the pc that faulted, word 5 is lr, word 7 is xPSR. arm-none-eabi-addr2line -e Main.elf 0x08000422 answers with the exact line of Main.c. The instruction there is udf #255, undefined on purpose (__builtin_trap() in the hog).
  • The M0+ has one fault handler and no fault-status registers, so you learn where and not why. On the Cortex-M4 in lesson 11, CFSR says why as well.

    mov  r1, lr

    mrs  r0, psp              @ a task faulted
    b    2f
1:  mrs  r0, msp              @ a handler faulted
2:  ldr  r1, =fault_report    @ r0 = the frame = first argument

17. What you built, what a real RTOS adds, and how it was measured (slides 19–20)

  • "The core is the same, instruction for instruction." xTaskCreate, vTaskDelayUntil and xQueueSendFromISR are this kernel's os_task_create, os_delay_until and os_queue_put_from_isr. From here on, lessons are written as tasks.
  • The measurements ran in Renode 1.17.0 on its STM32F072 platform, a Cortex-M0 with the same ARMv6-M architecture, with os.c and Main.c unchanged. A test-only startup.c skipped the C0's clock waits, and the C0's GPIO was mapped as plain memory for button presses.
  • Renode does not fault on an unaligned word access; ARMv6-M silicon does. So the lab faults with __builtin_trap(), which faults everywhere.

General idea vs this chip

Exam focus
  • Cooperative: a job stops only when it returns, so one CPU hog freezes everything. Preemptive: the kernel's tick takes the CPU away. A hog at the highest priority still starves everyone, because the highest-priority READY task always runs.
  • Priority numbering: kernel and FreeRTOS, higher number = more urgent (idle 0, button 3). NVIC, 0 = most urgent; PendSV and SysTick sit at 3, the least urgent. Any interrupt preempts any task.
  • Switched-out stack from tcb->sp up: r4–r7 (+0), r8–r11 (+16), r0–r3 (+32), r12, lr, pc, xPSR (+48), 64 bytes. pc at +56: tcb->sp = 0x20000440 puts it at 0x20000478. PendSV saves r4–r11; the hardware saves the rest. After the return, PSP = tcb->sp + 64.
  • Pend PendSV: SCB->ICSR = 0x10000000 with =, never |=; cancel with 0x08000000. Priority 3 = byte 0xC0, so SHPR3 = 0xC0C00000.
  • Switch in PendSV, not in SysTick_Handler: at priority 3 it runs only when no handler is active. Deciding happens anywhere, even in an ISR; switching only in PendSV.
  • EXC_RETURN 0xFFFFFFFD = Thread mode, PSP (every switch). Bit 2 = 1 means PSP, so a HardFault with lr = 0xFFFFFFFD came from a task, and 0xFFFFFFF1 from a handler; frame word 6 is the faulting pc.
  • Forged frame: xPSR 0x01000000 (T bit), pc = fn & ~1, lr = task_exit, r0 = arg, zeros elsewhere. xPSR = 0 HardFaults at the task's first instruction.
  • r8–r11 go through r4–r7 because Thumb-1 stm/ldm list only r0–r7; on restore r8–r11 come first.
  • pick(): with hog (p1) current and report (p1) ready, report runs next (round-robin); if bar (p2) wakes, bar preempts.
  • An ISR cannot lock a mutex or call os_queue_put(): both may block. It uses os_queue_put_from_isr(), which returns 0 when full, and the handler drops and counts the item.
  • Priority inversion: high waits for mid through low's mutex. Inheritance lends high's priority to low until it unlocks. A stack overflow usually corrupts another task's data instead of crashing; the 0xDEADBEEF high-water mark catches it.
