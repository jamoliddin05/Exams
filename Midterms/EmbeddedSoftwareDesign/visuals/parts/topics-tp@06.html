Time and Timers: Letting the Hardware Keep Time

Lesson 05 kept time by polling SysTick, and every printf quietly stole milliseconds. This lesson hands time to the hardware. SysTick becomes a 1 ms interrupt, TIM3 draws a servo pulse with no CPU at all, and TIM14 writes down when an echo edge happened, to the microsecond. The project is a parking sensor: an HC-SR04 ranger, a servo gauge and an 8-LED bar, run from a loop that never waits.

0. This lesson's pins (the two pin-map pages)

The board page shows each wire at its header position on the Nucleo-C031C6. The chip page shows the same pins as bit positions in their port's registers: pin n of GPIOA is bit n of IDR, bits 2n+1:2n of MODER, and so on (lesson 05, slide 4).

  • The two outer double rows are ST's morpho headers, which reach every pin. The inner single rows are the Arduino headers; PA5 is also D13.
  • Two timer pins, two AF numbers: PA6 = AF1 (TIM3_CH1) and PA7 = AF4 (TIM14_CH1). Slide 10 explains why the number depends on the pin.

1. The millisecond that lied (slide 1)

Lesson 05's clock was a loop asking SysTick whether it had wrapped:

while (!(SysTick->CTRL & SysTick_CTRL_COUNTFLAG_Msk)) { }
ms_now++;
  • COUNTFLAG remembers one wrap. A printf of 90 characters at 115200 baud holds the loop for about 8 ms (90 × 10 bits × 8.68 µs = 7.8 ms).
  • Seven wraps happen while nobody is asking, and seven milliseconds vanish. "Time that depends on the loop coming back is only as good as the loop."
  • The fix is lesson 03's second rendezvous, an interrupt instead of a poll. Each wrap forces a one-line function to run, whatever main() is doing.
static volatile uint32_t ms_ticks;

void SysTick_Handler(void) { ms_ticks++; }

SysTick_Config(SystemCoreClock / 1000u);      /* in main(), once */

2. SysTick and SysTick_Config() (slides 1–2)

SysTick is part of the ARM core: four registers at 0xE000E010, the same four on every Cortex-M (SysTick_Type in core_cm0plus.h). It is a 24-bit counter that counts down, so the longest period is 2²⁴ clocks, 350 ms at 48 MHz.

SysTick_Config() is CMSIS and hides nothing. These are its five lines:

if ((ticks - 1UL) > SysTick_LOAD_RELOAD_Msk) return 1;           /* 24 bits only */
SysTick->LOAD  = ticks - 1UL;                                     /* 47999        */
NVIC_SetPriority(SysTick_IRQn, (1UL << __NVIC_PRIO_BITS) - 1UL);  /* 3            */
SysTick->VAL   = 0UL;
SysTick->CTRL  = CLKSOURCE | TICKINT | ENABLE;                    /* 0x00000007   */
  • For 1 ms at 48 MHz, ticks = 48 000 000 / 1000 = 48 000, so LOAD = 47 999 = 0xBB7F. VAL counts 47 999 down to 0, which is 48 000 clocks.
  • CTRL = 0x7: bit 2 CLKSOURCE (core clock), bit 1 TICKINT (interrupt on each wrap), bit 0 ENABLE.
  • Priority (1 << 2) − 1 = 3, the lowest. "A late tick is caught up, a missed capture is gone" (slide 15).
  • SysTick is part of the core, not ST's silicon. Every Cortex-M has it at the same address with the same registers, which is why every RTOS uses it as its heartbeat. Lesson 07 does.
  • SysTick_Handler has no flag to clear, unlike every other handler in the course. Its request is the wrap itself, and taking the exception acknowledges it.

3. millis() and the wrap that does not matter (slide 3)

ms_ticks is a uint32_t. It wraps after 2³² ms, 49.7 days, and code that compares absolute times breaks on day 50.

if (millis() >= deadline) ...          /* WRONG at the wrap */
if (millis() - start >= period) ...    /* right, always     */
  • Unsigned subtraction is modulo 2³², so now - start is the true elapsed time even when now has wrapped past zero and start has not. Every timeout in this lesson is written that way.
  • Reading ms_ticks needs no lock: one aligned word, one writer (lesson 03, slide 7). volatile is what forces each millis() to actually load it.

4. Doing several things at once without waiting (slide 4)

With a real clock the loop never blocks. Each job checks whether its time has come, and if not, gets out of the way:

for (;;) {
    uint32_t now = millis();
    if (now - ping_at   >= 100)  { ping_at   += 100;  ranger_ping(); }
    if (now - report_at >= 1000) { report_at += 1000; printf(...);   }
    if (now - beat_at   >= 500)  { beat_at   += 500;  toggle LD4;    }
}
  • Three jobs at three rates, none aware of the others. This is cooperative scheduling in its smallest form, and "most small products ship exactly this". A job gives up the CPU only by returning.
  • Advance the schedule with ping_at += 100. With ping_at = now, a pass that runs 3 ms late shifts every later ping by 3 ms, and the error accumulates. += keeps the schedule on a 100 ms grid and absorbs the lateness.
  • Every job must be quick. One job that takes 50 ms delays all the others by 50 ms. Lesson 07 removes that limit with a preemptive kernel.

5. The timer: every register on one page (slide 5)

TIM3 at 0x40000400 and TIM14 at 0x40002000 are built from the same register set, TIM_TypeDef. The offsets are the same for every timer on the chip, and a simple timer like TIM14 just leaves most of them unimplemented. An address is base + offset: TIM3->CCR1 is 0x40000400 + 0x34 = 0x40000434.

  • Nine registers out of twenty-five do all of this lesson's work. They fall into four groups, the same four in every timer.
  • Time base (PSC, ARR, CNT): how fast it counts and how far. Events (EGR, DIER, SR): what happens when it gets there, and who is told. Channel (CCMR1, CCER, CCR1): compare to make a waveform, or capture to take a timestamp. Control (CR1): preload on, then run.
  • CCMR1 is one register with two layouts. Bits 1:0, CC1S, decide which one the rest of it means: 00 = output compare (TIM3), 01 = input capture from TI1 (TIM14).
  • TIM3 and TIM14 are 16-bit timers: ARR, CCR1 and the count in CNT use bits 15:0. The header's masks are 32 bits wide because they also serve the 32-bit TIM2 of other STM32s. CNT bit 31, UIFCPY, is a copy of UIF, readable in the same load as the count when UIFREMAP is set.

6. A timer is a counter with three registers (slide 5b)

Every STM32 timer, from the 16-bit TIM14 to the advanced TIM1, is built on the same core. The timer clock passes through the prescaler into CNT. When CNT reaches ARR, an update event sets CNT back to 0 and raises UIF.

count rate = f_clk / (PSC + 1)     update rate = f_clk / ((PSC + 1) × (ARR + 1))

TIM3, 1 µs per count and a 20 ms frame, at 48 MHz
PSC + 1 = 48 MHz / 1 MHz  = 48       → PSC = 47      (0x002F)
ARR + 1 = 20 ms / 1 µs    = 20 000   → ARR = 19999   (0x4E1F)
update  = 48 000 000 / (48 × 20 000) = 50 Hz

Both registers hold N − 1: a count of N steps runs from 0 to N − 1.
PSC = 2 → CNT steps once every 3 clocks
ARR = 3 → CNT runs 0 1 2 3 0 1 …, 4 counts per update
  • The −1 is the classic off-by-one. PSC = 48 divides by 49 and gives 48.98 Hz, and nothing complains. Only the report line's count of TIM3 updates against SysTick notices (slide 16, Lab Part 2).
  • More to work by hand: PSC 47 with ARR 999 updates every 1 ms (1 kHz). PSC 23 counts at 2 MHz. TIM14 runs PSC 47 with ARR 0xFFFF and wraps every 65.536 ms.

7. Shadow registers, and why UG comes first (slide 6)

PSC, ARR and CCR1 are double-buffered. What you write lands in a preload register. The counter keeps using the shadow copy until the next update event, when the preload is copied across.

TIM3->PSC  = 47;              /* sits in preload...                          */
TIM3->ARR  = 19999;
TIM3->EGR  = TIM_EGR_UG;      /* ...until this forces an update right now    */
TIM3->SR   = ~TIM_SR_UIF;     /* UG also raised UIF - clear it, or the first */
TIM3->DIER |= TIM_DIER_UIE;   /* interrupt is a phantom                      */
  • Buffering is what lets you change a PWM duty cycle mid-flight without ever producing a malformed pulse. It is also why a freshly configured timer can ignore you.
  • Skip UG and the prescaler is still 0 for the first period: 20 000 counts at 48 MHz, about 0.4 ms instead of 20 ms (20 000 / 48 MHz = 0.42 ms). ARR took effect at once only because it was written before ARPE switched its preload on.
  • On a timer that runs once, that is a bug you will see. On one that runs forever, it is a glitch you probably will not.

8. TIM3_IRQHandler and the opposite convention (slide 7)

void TIM3_IRQHandler(void)
{
    if (TIM3->SR & TIM_SR_UIF) {
        TIM3->SR = ~TIM_SR_UIF;       /* write 0 to clear */
        ...
  • The name works because it replaces the weak alias in the vector table (lesson 04). TIM3 is IRQ 16, vector 16 + 16 = 32, at 0x08000000 + 32 × 4 = 0x08000080.
  • Timer flags clear by writing 0. EXTI flags clear by writing 1. Same chip, same vendor, opposite conventions. ST's own LL driver shows both: WRITE_REG(TIMx->SR, ~(TIM_SR_UIF)) and WRITE_REG(EXTI->FPR1, ExtiLine).
  • The compiler builds ~TIM_SR_UIF as movs r2, #2 ; negs r2, r2, which is 0xFFFFFFFE, and one str. Writing 1s to every other flag leaves them alone, so the clear touches only UIF and needs no read.
  • Written the EXTI way, TIM3->SR = TIM_SR_UIF clears every other flag and leaves UIF set. The handler re-enters forever, and it builds with zero warnings. In Lab Part 1 the banner stops part-way, SysTick (priority 3) starves so time stops, and the servo holds its position, because the PWM is hardware.

9. Output compare: the timer draws a waveform (slides 8–9)

Add a fourth register, CCR1, and the counter drives a pin by itself. In PWM mode 1 (OC1M = 110) the pin is high while CNT < CCR1 and low after, until the counter reaches ARR and the next frame starts.

  • With the counter ticking once per microsecond, CCR1 is the pulse width in microseconds. CCR1 = 1500 means exactly 1.5 ms.
  • No CPU is involved in a single edge. The ISR is only there to change CCR1, and OC1PE (preload) makes every change wait for the next frame boundary, so a pulse is never cut in half.
  • Four writes turn the channel on: CCMR1 (mode and preload), CCER.CC1E (connect to the pin), CR1.ARPE, and the pin's alternate function.
  • A hobby servo reads the width of a pulse, repeated every 20 ms: nominally 1.0 ms at one end, 1.5 ms at the centre and 2.0 ms at the other end.
  • "Nominal" is doing real work there. Real servos differ, Arduino's Servo library uses 544–2400 µs for its 0–180°, and Wokwi documents no range at all, so Lab Part 4 measures it.
  • The frame rate is not critical; servos accept a wide range around 50 Hz. The pulse width is the whole message, which is why this lesson counts in microseconds.

10. Getting the signal out: the AF table (slide 10)

The timer channel is inside the chip. pin_af() connects it to a pin, and the number it needs comes from a table in the datasheet. The reference manual does not list it.

  • The same signal has different AF numbers on different pins. This lesson's second timer shows it too: TIM14_CH1 is AF4 on PA7 and AF0 on PB1.
  • PA6's number lives in GPIOA->AFR[0], bits 27:24 (pin n below 8: bits 4n+3:4n), and its MODER field must be 10.
  • A wrong AF number gives a pin that is electrically fine, driven by some other peripheral or by nothing. The timer still counts, the interrupt still fires, the report still says 50 updates a second, and the servo does not move. Lab Part 5: "the timer works, the pin doesn't."

11. The smallest control loop (slide 11)

uint32_t now  = TIM3->CCR1;
uint32_t want = servo_target_us;
if      (want > now + SLEW) now += SLEW;
else if (want + SLEW < now) now -= SLEW;
else                        now  = want;
TIM3->CCR1 = now;                 /* preloaded: takes effect next frame */
  • The update interrupt runs once per frame and moves the pulse towards the target, never more than SLEW = 20 µs a frame. 20 µs × 50 frames a second = 1000 µs per second of travel, so the servo glides instead of snapping.
  • That is a rate limiter, the smallest possible piece of control code: measure, compare, correct, once per period. It runs in the right place, an interrupt tied to the exact rate at which the output is consumed.
  • Every controller in Part 3 of the course, from the line follower to the drone's attitude loop, has this shape with better arithmetic inside.

12. Input capture: the hardware takes the timestamp (slide 12)

Output compare makes an edge at a chosen time. Input capture answers the reverse question: what time was this edge?

  • At the edge on PA7 the hardware copies CCR1 ← CNT, then raises CC1IF, and only then does the ISR run and read CCR1.
  • "The timestamp is taken before the interrupt is even requested." ISR latency, 1 µs or 100 µs, "changes when you READ it, not what it SAYS."
  • Measuring a pulse with an EXTI interrupt and millis() would include the interrupt's latency, and the latency varies with whatever else is running. Input capture removes the CPU from the measurement entirely. The ISR is a courier, not a stopwatch.

13. Measuring the echo, and what Wokwi showed (slides 13, 13b)

The HC-SR04 answers a 10 µs trigger on PA8 with a high pulse whose width is the round-trip time of the sound, 58 µs per centimetre. TIM14 free-runs at 1 MHz (PSC 47, ARR 0xFFFF) and captures both edges, CC1P = CC1NP = 1.

uint16_t t = (uint16_t)TIM14->CCR1;          /* reading CCR1 clears CC1IF */
if (pin_read(GPIOA, ECHO_PIN)) echo_rise = t;           /* rising  */
else { echo_us = (uint16_t)(t - echo_rise); ... }       /* falling */
  • The 16-bit subtraction is correct across a wrap. TIM14 wraps every 65.5 ms and the longest echo, 400 cm, is 23.2 ms. Rise 60000, fall 17664: (uint16_t)(17664 − 60000) = 23 200 µs = 400 cm. Figure 3's last step draws it.
  • Reading CCR1 clears CC1IF, a third clearing convention and the only one that needs no write at all.
  • The trigger pulse uses TIM14 too. CNT is already counting microseconds, so it is the stopwatch for the 10 µs.
  • Wokwi does not implement timer input capture; its STM32 timers do PWM output only. Every report line of the first run read echo 0 us = 0 cm, because CC1IF never set.
  • So the firmware also listens on PA7 through EXTI line 7 on both edges (lesson 05), and that handler reads TIM14->CNT itself, already late. Capture is used whenever it has produced a pulse, EXTI otherwise, and every report line names its source.
t=  9000 ms  TIM3 50/s  echo  5882 us = 101 cm (EXTI)  servo 1495 us  edges cap 0 exti 161

cap 0, exti +20 a second    2 edges per ping × 10 pings a second
5882 us, slider 100 cm      58.8 us per cm, sound at 340 m/s;  5882 / 58 = 101 cm
servo 1495 us               2000 − 101 × 1000 / 200 = 2000 − 505
3 LEDs                      (200 − 101) × 8 / 200 = 3.96 → 3 (integer division)

The EXTI timestamp is late by the interrupt latency, and both edges are late by about the same amount, so the width is still right to within a microsecond or two. That only holds while nothing else delays one of the two interrupts. On silicon, slide 12's argument for capture still stands.

14. Two variables from one interrupt: tearing (slide 14)

The capture ISR writes two things together, the width and a count. main() wants a consistent pair, so it reads both with interrupts off:

__disable_irq();
uint32_t n  = echo_count;
uint32_t us = echo_us;
__enable_irq();

Without the critical section, a capture can land between the two loads:

main()                          capture ISR
n  = echo_count;    → 41
                                echo_us = 5882;      the width of capture 42
                                echo_count++;        → 42
us = echo_us;       → 5882
n = 41 sits with the width of capture 42: a torn pair
  • This is lesson 03, slide 7's tearing, now in real code. The slide words it as a new count with an old width; in this code order the halves come out the other way round, and the bug is the same.
  • With the critical section, the window is two load instructions long, a fraction of a microsecond with interrupts off. The capture itself is not delayed at all, because the hardware already took the timestamp (slide 12). The interrupt is merely held pending until __enable_irq().
  • One variable alone, like ms_ticks, needs no lock (slide 3). A single aligned word with one writer cannot tear.

15. Three interrupts, three priorities (slide 15)

  • On a Cortex-M0+ a higher-priority interrupt preempts a running lower-priority handler. Equal priorities never preempt each other; they queue, and the NVIC takes the higher priority first, then the lower IRQ number.
  • NVIC numbering: 0 is the most urgent. This chip keeps 2 priority bits, the top two of each priority byte, so priority p is stored as p << 6.
  • The table is not based on importance to the user. The servo matters more than the clock to someone watching, but it has 20 ms of slack. Priority follows deadline. That rule has a name, deadline-monotonic, or rate-monotonic when each deadline is the job's own period, and lesson 07 builds a scheduler on it.

16. Two clocks checking each other (slide 16)

t=  5000 ms  TIM3 50/s  echo  5800 us = 100 cm  servo 1500 us  (last line took 8 ms)

SysTick path   48 MHz / 48 000         = 1000 ticks a second
TIM3 path      48 MHz / 48 / 20 000    = 50 updates a second
self-test      TIM3 updates per 1000 SysTick ticks = 50, every second
PSC = 48       48 MHz / 49 / 20 000    = 48.98 a second → reads 48 or 49
took           88 chars × 86.8 µs      = 7.6 ms, and t= still advances by 1000
  • Both counts come from the same 48 MHz through completely different dividers. If PSC and ARR are right, the answer is exactly 50 every second. It is a self-test: arithmetic in two independent places that must agree.
  • The took figure is the other half of the story. The clock kept counting through 7 or 8 ms of printf; lesson 05 would have lost seven of those milliseconds.
  • TIM3 50/s was measured in Renode, whose platform file clocks its timers at 10 MHz. The first run read TIM3 10/s (10 MHz / 48 / 20 000 = 10.4). The self-test caught the simulator.

18. What carries forward (slide 18)

  • Time is now an interrupt, and now - then is the only comparison you write.
  • Timers are one model, many instances. TIM3 made a waveform and TIM14 measured one. TIM1, TIM16 and TIM17 are the same registers with more features, and need no new lesson.
  • The superloop has a ceiling. Every job in slide 4's loop must finish quickly, or it delays all the others. Lesson 07 lifts the ceiling: SysTick becomes the heartbeat of a scheduler that can interrupt a job and run another, and delay_ms() comes back without stopping anything else.

General idea vs this chip

Exam focus
  • PSC and ARR at 48 MHz: 1 µs counts and a 20 ms frame give PSC 47, ARR 19999, 50 Hz. A 1 ms update: PSC 47, ARR 999. A 2 MHz count: PSC 23.
  • Forgot the −1: PSC 48 gives 48.98 Hz and a 1500-count pulse of 1531 µs. Only the TIM3-against-SysTick count notices.
  • SysTick at 1 ms: LOAD 47999 (0xBB7F), CTRL 0x7, priority 3, no flag to clear. Longest period 2²⁴ clocks ≈ 350 ms; asking for 1 s makes SysTick_Config return 1.
  • millis() wraps after 49.7 days. start 0xFFFFFF00, now 0x00000100: now − start = 0x200 = 512 ms. millis() >= start + 500 fires 484 ms early there.
  • Flags: TIM SR write 0 (SR = ~TIM_SR_UIF = 0xFFFFFFFE), EXTI write 1, CC1IF by reading CCR1, SysTick nothing. SR = TIM_SR_UIF: the handler re-enters forever, SysTick starves, the PWM keeps running.
  • No EGR = UG: the first period runs at prescaler 0, 0.42 ms. UG without clearing UIF: a phantom first interrupt.
  • PWM mode 1: high while CNT < CCR1, so at 1 µs a count CCR1 is the width in µs. Servo: 20 ms frame, 1.0 / 1.5 / 2.0 ms. TIM3 CCMR1 0x68, CR1 0x81, CCER 0x1.
  • Wrong AF or no CC1E: the timer runs, the report says 50/s, the pin is dead. PA6 AF1, PA7 AF4, GPIOA AFR[0] = 0x41001100.
  • Capture: CCR1 ← CNT at the edge, so latency does not change the value. Both edges: TIM14 CCER 0xB. Rising only (0x1): no widths, ever. (uint16_t)(17664 − 60000) = 23 200 µs = 400 cm.
  • Priorities follow deadlines: TIM14 1, TIM3 2, SysTick 3. IPR4 = 0x40000080, SHPR3 = 0xC0000000. Equal priorities queue, lower IRQ number first.
  • Superloop: ping_at += 100 holds the grid, = now drifts. Cooperative: one 50 ms job delays every other job by 50 ms.
