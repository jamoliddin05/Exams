Question 27 · L07, Two priority numberings

In this course's kernel, the button task has priority 3 and the hog task has priority 1. On the same chip, an EXTI interrupt has NVIC priority 1 and SysTick has NVIC priority 3. Which statement is correct?

  1. A The button task outranks the hog, and the EXTI interrupt outranks SysTick Correct. Kernel: bigger is more urgent, 3 beats 1. NVIC: 0 is most urgent, 1 beats 3.
  2. B The hog outranks the button task, and the EXTI interrupt outranks SysTick No. This applies the NVIC rule, smaller is more urgent, to the tasks.
  3. C The button task outranks the hog, and SysTick outranks the EXTI interrupt No. This applies the kernel rule, bigger is more urgent, to the interrupts.
  4. D The hog outranks the button task, and SysTick outranks the EXTI interrupt No. Both orders are reversed.

Answer: A. The chip has two numberings. In the kernel, as in FreeRTOS, a higher number is more urgent, so the button task (3) outranks the hog (1).

In the NVIC, 0 is most urgent, so the EXTI interrupt (1) outranks SysTick (3). Slide 9: "Two numbering schemes on one chip: always say which one you mean."

Exam line

Kernel (and FreeRTOS): the highest number is most urgent, 0 is idle. NVIC: 0 is most urgent, 3 is least (2 priority bits). Always say which numbering you mean.

Question 28 · L07, Saved context on the task stack

Task B was switched out by this kernel's PendSV_Handler, and B's TCB now holds sp = 0x20000400. At which address is B's saved pc, the instruction B will resume at?

  1. A 0x20000418 No. That is tcb->sp + 24: it leaves out the 8 words PendSV saved and lands on r10.
  2. B 0x2000043C No. +60 is the last word, xPSR.
  3. C 0x200003C8 No. This counts downward. The saved words sit at higher addresses than tcb->sp.
  4. D 0x20000438 Correct. 0x20000400 + 32 (r4–r11) + 24 (pc is frame word 6) = 0x20000438.

Answer: D. tcb->sp points at r4. PendSV saved r4–r11 there, 8 words or 32 bytes, so the hardware frame r0, r1, r2, r3, r12, lr, pc, xPSR starts 32 bytes on, at 0x20000420.

The pc is word 6 of that frame, 24 bytes further: 0x400 + 32 + 24 = 0x400 + 0x38, so 0x20000438.

tcb->sp                  = 0x20000400   → r4
+ 8 words (r4–r11) × 4   = + 32 = 0x20  → 0x20000420, r0: the hardware frame starts
+ 6 words (r0 … lr) × 4  = + 24 = 0x18  → 0x20000438, pc
total offset 32 + 24     = 56   = 0x38
Exam line

From tcb->sp upward: r4–r7 (+0), r8–r11 (+16), r0–r3 (+32), r12, lr, pc, xPSR (+48). The hardware frame starts 32 bytes above tcb->sp, and pc is its word 6: tcb->sp + 56.

Question 29 · L07, Stack overflow and the high-water mark

The report task calls printf and needs 115 words of stack at its deepest. A student shrinks its stack from 512 to 96 words. The linker happens to place the hog task's counter primes in the word just below the report task's stack. What does the board most likely do?

  1. A It HardFaults at the first printf, and the fault report names the report task No. Nothing on this core checks the stack pointer, so writing below the array does not fault.
  2. B Nothing crashes; the report keeps printing, but the hog's primes count suddenly shows a huge, wrong value Correct. The 19 extra words land below the array, on primes.
  3. C The kernel detects the overflow at the next context switch and stops the report task No. That is FreeRTOS's check on every switch. This kernel only shows the high-water mark in its report.
  4. D The build fails, because the linker sees that 115 words do not fit in a 96-word array No. Stack depth is a run-time fact. The linker only places a 96-word array.

Answer: B. The stack grows down, so the report task's 115 − 96 = 19 extra words land below its array, on primes and whatever lies under it. Nothing on this core checks the stack pointer, so nothing faults.

Another task's data goes quietly wrong, and the bug looks like it is in the hog. Slide 17: "not a crash, but somebody else's data quietly wrong, far from the cause." An MPU guard region, which would catch it, is for bigger cores.

Exam line

A stack overflow on an MCU usually does not crash: it quietly corrupts another task's data, far from the cause. Fill each stack with 0xDEADBEEF, exercise every path, read the high-water mark, add a margin.

Question 30 · L07, Why an ISR must not block

A UART receive interrupt handler must pass each received byte b to a protocol task that waits in os_queue_get(&q, ...). Which line belongs in the handler?

  1. A os_queue_put(&q, &b); No. The task API blocks while the queue is full, and a handler cannot block.
  2. B os_mutex_lock(&m); rx[n++] = b; os_mutex_unlock(&m); No. A mutex is never used from an ISR: locking can block.
  3. C while (!os_queue_put_from_isr(&q, &b)) { } No. On a full queue the handler spins forever. The task that would empty it cannot run until the handler returns.
  4. D if (!os_queue_put_from_isr(&q, &b)) { dropped++; } Correct. Never blocks: it returns 0 when full and the handler decides.

Answer: D. An interrupt handler must never block: there is no task to put to sleep, only a handler on MSP. os_queue_put_from_isr() never blocks. It returns 0 when the queue is full and lets the handler decide, here by counting the lost byte.

A and B call task APIs that can block, on a full queue or a held mutex. C never sleeps, but on a full queue it spins forever.

Exam line

An ISR must never block: there is no task to put to sleep. Use os_queue_put_from_isr(), which returns 0 when full; the task it wakes runs when the last handler returns.
