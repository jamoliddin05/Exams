Question 27 · L07, PendSV and SysTick priority value

os_start() must make PendSV and SysTick the least urgent exceptions on the chip. In SHPR3, SysTick's priority is bits 31:30 and PendSV's is bits 23:22; these are the only implemented bits (__NVIC_PRIO_BITS = 2). Which 32-bit value written to SHPR3 does it?

  1. A 0x00000000 No. Both fields 00 is priority 0, the most urgent NVIC level.
  2. B 0x03030000 No. The 3s land in bits 25:24 and 17:16, which do not exist, so both stay at 0.
  3. C 0xC0C00000 Correct. 3 << 6 = 0xC0 in SysTick's byte and in PendSV's byte.
  4. D 0x80800000 No. Only bits 31 and 23 are set: each field reads 10, priority 2.

Answer: C. In the NVIC numbering 0 is most urgent, so the least urgent level is 3, binary 11. Each priority byte keeps only its top two bits, so 3 becomes 3 << 6 = 0xC0.

SysTick's byte is bits 31:24 and PendSV's is bits 23:16, so SHPR3 = 0xC0C00000, the value slide 4b shows after os_start. Option A is the kernel's numbering, where 0 is idle, applied to the NVIC.

least urgent NVIC level   = 3 = 11₂

SysTick, byte 31:24       = 0xC0 << 24 = 0xC0000000
PendSV,  byte 23:16       = 0xC0 << 16 = 0x00C00000
SHPR3                     = 0xC0C00000

Question 28 · L07, Forging the first frame

A student edits os_task_create() so that every new task's forged frame holds xPSR = 0x00000000 instead of 0x01000000. Everything else is unchanged. What happens after os_start()?

  1. A The tasks run normally: the flags N, Z, C and V simply start at 0 No. The flags are harmless; bit 24, T, is the one that matters.
  2. B The first switch into a task HardFaults at that task's first instruction, because T = 0 asks for ARM state, which the M0+ does not have Correct. The forged xPSR is popped on the first switch, with T = 0.
  3. C The tasks run on MSP instead of PSP, because the forged xPSR no longer selects the process stack No. EXC_RETURN bit 2 picks the stack; 0xFFFFFFFD still says PSP.
  4. D The kernel runs until the first SysTick, which faults because the frame the hardware pushes now has T = 0 No. The hardware stacks the live xPSR, whose T is 1. Only the forged word is wrong.

Answer: B. The hardware pops the forged xPSR on the first switch into each task, when PendSV returns with 0xFFFFFFFD. Bit 24, T, must be 1: the M0+ runs only Thumb code, so T = 0 asks for ARM state and the core HardFaults at the task's first instruction.

The first task to be switched to is the most urgent READY one, so that is the task the fault report names.

Question 29 · L07, Priority inversion and inheritance

Three tasks run on this kernel: high (priority 3), mid (2) and low (1). Low locks a mutex. While low holds it, high asks for the same mutex and blocks. Then mid, which never uses the mutex, becomes READY and computes for 120 ms. With OS_PRIORITY_INHERIT set to 1, what does the kernel do?

  1. A Low inherits mid's priority, 2, so low and mid take turns, one tick each No. The holder borrows the waiter's priority, high's 3. At 2, high would still wait through mid's turns.
  2. B Nothing: high waiting for low is ordinary blocking, so mid runs its 120 ms first No. That is the unbounded priority inversion the flag exists to stop.
  3. C Low runs at high's priority, 3, until it unlocks, so mid cannot preempt it and high waits only for low's critical section Correct. Priority inheritance, slide 14.
  4. D Mid's priority is lowered to 0 while high waits, so low can finish first No. The kernel raises the holder; it never lowers a third task.

Answer: C. Without a fix this is priority inversion: mid preempts low, low cannot unlock, and high ends up waiting for mid, a task it outranks, for as long as mid runs.

Priority inheritance lends the holder the waiter's priority. Low runs at 3 until it unlocks, drops back to its base_prio 1, and high goes. Mid still gets its 120 ms, only later.

Exam line

Priority inversion: high waits, in effect, for mid, a task it outranks. Priority inheritance: while low holds a mutex high wants, low runs at high's priority, so mid cannot preempt it; on unlock low returns to base_prio.

Question 30 · L07, Why r8–r11 go the long way round

In PendSV_Handler on the Cortex-M0+, the old task's r4–r7 are already stored and r0 points at the next free word of its stack. Which sequence stores r8–r11 next?

  1. A stmia r0!, {r8-r11} No. The Thumb-1 register list has bits for r0–r7 only; this form exists on the Cortex-M3.
  2. B push {r8-r11} No. push lists only r0–r7 and lr, and in PendSV it would use MSP, not the task's stack.
  3. C str r8, [r0, #0] … str r11, [r0, #12] No. Thumb-1 str also names only r0–r7.
  4. D mov r4, r8 / mov r5, r9 / mov r6, r10 / mov r7, r11, then stmia r0!, {r4-r7} Correct. Copy into the already-saved r4–r7, then store those.

Answer: D. The M0+ runs Thumb-1, where stm and ldm have an 8-bit register list, one bit for each of r0–r7, so they cannot name r8–r11.

The kernel copies r8–r11 into r4–r7, which are already saved and free, with mov, one of the few Thumb-1 instructions that reach r8–r12, and stores those. The restore runs backwards: r8–r11 first, r4–r7 last.
