Question 15 · L04, Stack top

A student edits the MEMORY block of link.ld to RAM (rw) : ORIGIN = 0x20000000, LENGTH = 6K and rebuilds. The line _estack = ORIGIN(RAM) + LENGTH(RAM); is unchanged. Which value does the core load into SP at reset?

  1. A 0x20001800 Correct. 6K = 6 × 1024 = 6144 = 0x1800, and 0x20000000 + 0x1800 = 0x20001800.
  2. B 0x20003000 No. That is the 12 KB top. _estack is computed from LENGTH, so it moves.
  3. C 0x20000000 No. That is the bottom of RAM. The stack grows down from the top.
  4. D 0x20001770 No. 0x1770 is 6000. In link.ld, K means 1024 bytes.

Answer: A. 6K is 6 × 1024 = 6144 bytes, which is 0x1800 (6 × 0x400). The linker computes _estack = 0x20000000 + 0x1800 = 0x20001800.

No C code is involved in getting that value into SP. vectors[0] holds &_estack, the table sits at 0x08000000, the hex file now starts 00 18 00 20, and the hardware loads word 0 into SP before the first instruction. _estack is computed, not typed, so it is the one value that follows the new LENGTH.

Exam line

_estack = ORIGIN(RAM) + LENGTH(RAM) is computed, so changing LENGTH moves the stack top. 6K = 6 × 1024 = 0x1800, so SP starts at 0x20001800.

Question 16 · L04, Vector placement

In link.ld a student moves the .isr_vector output section so that it comes after .text in FLASH, and changes nothing else. What happens?

  1. A The linker stops with an error, because .isr_vector must be the first section in FLASH No. The linker only checks that everything fits. Zero errors, zero warnings, identical sizes.
  2. B It builds with no error and no warning and gives a valid hex file, but a real chip cannot start, because the first two words of FLASH are now instruction bytes Correct. The core takes SP and PC from those two words.
  3. C It builds and runs normally, because the core finds the section named .isr_vector at reset No. Section names do not exist on the chip. The core reads fixed addresses.
  4. D It builds and runs normally until the first interrupt, which hangs the board No. Words 0 and 1 of the table are the stack pointer and the reset vector, so it fails at reset.

Answer: B. At reset the core reads the first two words of FLASH itself: word 0 into SP and word 1 into PC. It does not know where the linker put the table. After the move, .text starts at 0x08000000, so those two words are machine code, and SP and PC get meaningless values. A real chip cannot start.

Nothing on the way complains. The compiler checks the language, the linker checks the arithmetic, and objcopy writes a hex file with correct checksums. Slide 20 calls this the failure mode the course cares about more than any other.

Exam line

Moving .isr_vector after .text builds with no error and no warning and produces a valid hex file. A real chip can't start, because the first two words of FLASH are now instruction bytes.

Question 17 · L04, CMSIS

GPIOA->ODR ^= (1u << 5); toggles LD4 on PA5. The names GPIOA and ODR come from CMSIS, here ST's device header stm32c031xx.h. What does CMSIS do to make this line reach the pin?

  1. A It links ST's HAL library, and GPIOA->ODR calls a library function that writes the register No. CMSIS is not ST's HAL. Nothing is linked and no function is called.
  2. B It supplies a special I/O instruction for the GPIO port, because GPIO sits outside the peripheral region at 0x50000000 No. There is no I/O instruction and no I/O address space. 0x50000000 is an ordinary address.
  3. C startup.c fills a table of register addresses in RAM at reset, and -> looks the address up at run time No. The address is a constant, known at compile time. Nothing is looked up.
  4. D Nothing is linked or called: GPIOA is a pointer to a struct at a fixed address, so GPIOA->ODR is base + offset, 0x50000000 + 0x14 = 0x50000014, worked out at compile time Correct. CMSIS is headers, not a library.

Answer: D. CMSIS, the Common Microcontroller Software Interface Standard, is headers, not a library. It is #defines and struct declarations that put names on the addresses ST published in the reference manual. GPIOA is a pointer to a GPIO_TypeDef at 0x50000000, and ODR is the struct member at offset 0x14.

The compiler turns GPIOA->ODR into an ordinary load and store at 0x50000014. Peripherals are reached by ordinary loads and stores, even GPIO, which on the STM32C0 sits at 0x50000000, outside the 0x40000000 peripheral region.

Exam line

CMSIS is headers, not a library. GPIOA->ODR is base + offset, 0x50000000 + 0x14, computed at compile time and reached by an ordinary load and store.
