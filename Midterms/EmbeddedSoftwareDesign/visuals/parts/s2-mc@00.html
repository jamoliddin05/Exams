Question 1 · L00, Alignment and byte order

A packet arrives in uint8_t buf[8] at address 0x20000100. It holds the bytes 11 22 33 44 55 66 77 88, buf[0] first. One field is the little-endian uint32_t stored at buf + 1. Which line puts that field into uint32_t v on the Cortex-M0+?

  1. A v = *(uint32_t *)(buf + 1); No. It loads a word from 0x20000101, which is not a multiple of 4. The M0+ HardFaults.
  2. B v = (uint32_t)buf[1] << 24 | buf[2] << 16 | buf[3] << 8 | buf[4]; No. It puts buf[1] in the top byte. That is big-endian and gives 0x22334455.
  3. C v = *(uint32_t *)buf >> 8; No. The aligned word is 0x44332211, and shifting it gives 0x00443322. The 0x55 is never loaded.
  4. D v = buf[1] | buf[2] << 8 | buf[3] << 16 | (uint32_t)buf[4] << 24; Correct. Four aligned byte loads put buf[1] in the low byte and give 0x55443322.

Answer: D. The field is the bytes 22 33 44 55 at 0x20000101 to 0x20000104. Little-endian puts the byte at the lowest address in the low end, so the field's value is 0x55443322. D builds exactly that from four byte loads, and a byte load is aligned at any address.

A casts the buffer to uint32_t * and loads a word from 0x20000101. That address is not a multiple of 4, so the Cortex-M0+ HardFaults. A Cortex-M3 or M4 would return 0x55443322, more slowly. B assembles the bytes big-endian, and C loads the wrong word and loses 0x55.

Exam line

An n-byte access wants an address divisible by n. The Cortex-M0+ HardFaults on an unaligned word access; an M3 or M4 performs it, more slowly. Casting a uint8_t * buffer to uint32_t * is the classic trap, so assemble a packet field from bytes, lowest address in the low byte.

Question 2 · L00, Harvard vs von Neumann

On an AVR, a lookup table was declared PROGMEM and read with pgm_read_byte(). Ported to the STM32C031, it becomes the code below, and the table is placed in flash. What does the second line do?

const uint8_t gamma[256] = { 0, 0, 1, 1, 2, 2, 3, 4, /* ... */ };
uint8_t y = gamma[i];
  1. A It reads SRAM at the table's address, because an ordinary load reaches only the data space No. That is Harvard thinking. Here one address names one place, and the table's address is in flash.
  2. B It raises a HardFault, because an ordinary load may not read the flash region No. Flash sits in the same map as everything else, and ordinary loads read it.
  3. C It reads the byte from flash with an ordinary load, because code and data share one address space Correct. One address space, so the same ldrb that reads a variable reads flash.
  4. D It reads a copy of the table that the startup code placed in SRAM, so the load never touches flash No. Startup copies only .data. A const table stays in flash.

Answer: C. The STM32C031 has one unified (von Neumann) address space. The table's address is a flash address, and the same ldrb that reads a variable reads it. PROGMEM "has no equivalent here and needs none", so pgm_read_byte() becomes a plain array read.

A is Harvard thinking. On the AVR, program memory and data memory each start at 0, so one number names two places, and an ordinary load picks the data one. That is why LPM existed. Nothing faults here (B), and a const table is never copied to SRAM (D).

Exam line

Harvard: separate code and data spaces, so the AVR needed LPM and PROGMEM. This chip has one unified address space. A const array in flash is read by the same ldr as anything else, and PROGMEM has no equivalent here.

Question 3 · L00, Vectored vs non-vectored dispatch

A small 8-bit controller sends every interrupt to one fixed address. The code there reads status registers one by one to find which source fired, then calls the right routine. What is this scheme called, and what does the STM32C031 do instead?

  1. A Vectored dispatch. The STM32C031 instead polls each peripheral's status register from main() No. One shared entry that asks who called is non-vectored, and this chip dispatches in hardware.
  2. B Non-vectored dispatch. The STM32C031 is vectored: the source's number indexes a table of handler addresses Correct. The number picks the slot, and the hardware jumps to the address in it.
  3. C Non-vectored dispatch. The STM32C031 is vectored, and like the AVR its table entries are jump instructions No. The AVR's slots hold jump instructions. This chip's slots hold plain addresses.
  4. D Vectored dispatch. The STM32C031 uses the same scheme, with the NVIC as the status register that software reads No. Wrong name, and the NVIC indexes the table itself. No software searches.

Answer: B. One fixed entry point whose code must "interrogate the hardware to discover who called" is non-vectored dispatch. It is cheap in silicon and slower in software, because every interrupt pays for the status reads.

The STM32C031 is vectored. The source has a number, the number indexes a table, and the hardware goes straight to the handler. Vectored machines differ in what a slot holds. It is a jump instruction on the AVR, a descriptor on x86 and a plain address here, so C is wrong, and A and D give the scheme in the question the wrong name.

Exam line

Non-vectored: every interrupt enters at one fixed address, and software interrogates the hardware to find who called. Vectored: the source's number indexes a table. The AVR's slots hold jump instructions, x86's hold descriptors, and this chip's hold plain addresses.

Question 4 · L00, Control, status, data

You meet a peripheral the course never covers, ST's I2C1. Its chapter lists CR1 (peripheral enable, interrupt enables), ISR (flags such as TXIS, RXNE, BUSY), TXDR and RXDR. Using the programmer's model, which reading is right?

  1. A Control: CR1. Status: ISR. Data: TXDR, RXDR. Look it up in ST's reference manual Correct. CR1 configures, ISR reports, TXDR and RXDR carry the bytes, and I2C1 is ST's block.
  2. B Control: CR1. Status: ISR. Data: TXDR, RXDR. Look it up in ARM's Cortex-M Generic User Guide No. The roles are right. ARM's guide covers only NVIC, SysTick, SCB and MPU.
  3. C Control: ISR. Status: CR1. Data: TXDR, RXDR. Look it up in ST's reference manual No. The hardware writes ISR to report what happened. You write CR1.
  4. D Control: TXDR. Status: RXDR. Data: CR1, ISR. Look it up in ARM's Cortex-M Generic User Guide No. TXDR and RXDR carry the payload, and ARM's guide does not describe I2C1.

Answer: A. "Configure with CONTROL. Watch with STATUS. Move bytes through DATA." You write the settings in CR1, the hardware reports what happened in ISR, and TXDR and RXDR carry the payload out and in. These are the same roles as USART's CR1, ISR, TDR and RDR.

I2C is ST's peripheral, so ST's reference manual describes it. ARM's Cortex-M Generic User Guide covers only ARM's own blocks, the NVIC, SysTick, SCB and MPU. B has the right roles and the wrong manual, and C and D get the roles wrong.

Exam line

Every peripheral has the same three roles: control (you write the settings), status (the hardware reports what happened) and data (the payload, both ways). The names move between chips; the roles never do. ARM's blocks are in ARM's Generic User Guide, and ST's blocks are in ST's reference manual.
