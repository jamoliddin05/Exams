UART and a Python Host: Talking to the Board, Properly

The serial port that printf has used since lesson 04 now works in both directions, driven by interrupts, and a program on the PC talks to it. USART2 is the peripheral model's fourth instance. Receive reuses lesson 07's kernel queue, transmit uses a lock-free ring built on lesson 03's one-writer rule, and every line meant for a program carries an NMEA XOR checksum that host.py, the course's first Python, checks.

1. USART2 in the peripheral model (pin maps, slide 1)

"Every row is a slot you already know. That is the whole point of Part 0's model: the fourth peripheral is not a fourth new thing."

  • Pins this lesson wires: PA2 = USART2 TX and PA3 = USART2 RX, both alternate function 1 (MODER 10, AFR 1). PA0 and PA1 are buttons A and B, inputs with pull-ups. PB0–PB7 drive the LED bar, one output bit per LED.
  • USART1 and USART2 share one register set (USART_TypeDef). USART2 sits at 0x40004400.
  • Defaults left alone: 8 data bits, no parity, 1 stop bit (8N1), no flow control, no prescaler. CR2, CR3 and PRESC keep their reset values.

2. Six registers out of twelve (slide 1)

  • Set up once: BRR and CR1 say how fast, which directions and which interrupts.
  • Status: ISR says what happened. ICR is where you write 1 to clear a flag of ISR.
  • Data: RDR and TDR, one byte each way. They are 9 bits wide for 9-bit frames. This lesson uses 8.

3. Clock gate, pins and baud rate (slide 1b)

RCC->APBENR1 |= 1u << 17;             USART2EN              = 0x00020000
GPIOA->AFR[0]: PA2 → bits 11:8, PA3 → bits 15:12, AF1 = 0001 in each
               0x00000100 | 0x00001000                = 0x00001100

BRR = f_clk / baud = 48 000 000 / 115 200 = 416.67 → 417 = 0x1A1
uart.c rounds:  (48 000 000 + 57 600) / 115 200 = 417   (integer division)
actual rate:    48 000 000 / 417 = 115 108 baud, 0.08% slow
  • BRR is "clocks per bit", so the same baud rate needs a different BRR on a different clock. At the 12 MHz reset clock, 115 200 baud needs 12 000 000 / 115 200 = 104.17 → 104.
  • Other rates at 48 MHz: 9600 → 5000, 19 200 → 2500, 57 600 → 833.33 → 833.
  • 0.08% is "far inside the few percent a UART tolerates, because the receiver resynchronises on every start bit" (Figure 3).
  • The banner prints BRR = 417, read back from the register.

4. One byte on the wire (slide 2)

  • The line idles high. A start bit (low) opens the frame, 8 data bits follow least significant bit first, and a stop bit (high) closes it: "10 bit-times per byte".
  • Sending: a 90-character line takes about 8 ms, and a polled printf holds the CPU for all of it.
  • Receiving: the UART holds one received byte. The next one is complete 86.8 µs later. If software has not read RDR by then, a byte is lost and ORE (overrun) is set.
115 200 bits/s ÷ 10 bits per byte = 11 520 bytes/s
1 / 11 520 = 86.8 µs per byte              (one bit = 8.68 µs)
90-character line: 90 × 86.8 µs = 7.8 ms ≈ 8 ms
at 9600 baud: 10 / 9600 = 1.04 ms per byte

5. Why receive must be an interrupt (slide 3)

  • "Polling would work only if every path through the program came back to the UART within 86.8 µs." One printf holds a task for 8 ms, and lesson 07's hog never comes back at all.
  • So receive becomes a producer and a consumer. The ISR reads RDR and calls os_queue_put_from_isr(). task_proto calls uart_getc(), which blocks in os_queue_get().
  • "The ISR meets the hard 86.8 µs deadline with a few dozen instructions. The queue turns it into a soft one": the task only has to catch up before 64 bytes pile up, 64 × 86.8 µs = 5.56 ms.
  • While nothing arrives, the protocol task is blocked and costs nothing (lesson 07, slide 15).
  • USART2_IRQn = 28 has NVIC priority 1, above the kernel's SysTick and PendSV at 3. In the NVIC, 0 is the most urgent.

6. One interrupt, three jobs, five ways to clear a flag (slide 4)

void USART2_IRQHandler(void)
{
    uint32_t isr = USART2->ISR;
    if (isr & USART_ISR_ORE) {                /* overrun             */
        USART2->ICR = USART_ICR_ORECF;        /* clear: write 1, ICR */
        stats.rx_overruns++;
    }
    if (isr & USART_ISR_RXNE_RXFNE) {         /* a byte arrived      */
        uint8_t c = (uint8_t)USART2->RDR;     /* reading clears RXNE */
        if (!os_queue_put_from_isr(&rx_queue, &c)) stats.rx_dropped++;
    }
    if ((USART2->CR1 & TXEIE) && (isr & USART_ISR_TXE_TXFNF)) { ... }
}
  • One vector for everything: the handler reads ISR once and checks all three flags on every entry.
  • The TXE branch also tests TXEIE, because TXE is set whenever the transmitter is idle, even when this handler ran for a received byte.
  • The ISR version of put never blocks. A full queue drops the byte and counts it.

Five conventions on one chip. The slide's habit: "for every flag, look up how it clears." The penalty for guessing is an interrupt that never stops.

7. Transmit: a lock-free ring (slide 5)

Sending goes the other way: tasks produce, the interrupt consumes.

static uint8_t           tx_ring[256];
static volatile uint16_t tx_head;   /* written ONLY by tasks (producer) */
static volatile uint16_t tx_tail;   /* written ONLY by the ISR (consumer) */

static void tx_put(uint8_t c)
{
    uint16_t next = (tx_head + 1) % 256;
    while (next == tx_tail) { os_delay(1); }    /* full: let the ISR drain */
    tx_ring[tx_head] = c;                        /* 1. the data            */
    tx_head = next;                              /* 2. THEN publish it     */
}
  • "No mutex, no masked interrupts, because each index has exactly one writer." Tasks read tail and write head. The ISR reads head and writes tail. This is lesson 03 slide 7's safe case (a single aligned word written by exactly one context), applied twice.
  • Data before index. If head moved first, the ISR could send a slot that has not been filled yet.
  • One slot always empty. head == tail means empty. If the ring could fill completely, full would look identical. So 256 slots hold at most 255 bytes.
  • Bytes waiting = (head − tail) mod 256. The size is a power of two, so % 256 becomes a mask.
  • The RX side uses a kernel queue with locking inside, the TX side a ring without any, on purpose, so you have seen both.

8. TXEIE: on only while there is work (slide 6)

TXE means "the transmit register is empty". When the UART is idle it is empty all the time, so a permanently enabled TXEIE would interrupt continuously.

/* in the ISR */
if (tx_tail != tx_head) {
    USART2->TDR = tx_ring[tx_tail];           /* send one, clears TXE   */
    tx_tail = (tx_tail + 1) % 256;
} else {
    USART2->CR1 &= ~USART_CR1_TXEIE_TXFNFIE;  /* nothing left: stop     */
}

/* in _write(), after filling the ring: CR1 0x2D → 0xAD */
__disable_irq();
USART2->CR1 |= USART_CR1_TXEIE_TXFNFIE;
__enable_irq();
  • The interrupt request is TXE AND TXEIE. TXE is a level that stays 1 while TDR is empty, so only TXEIE can stop the requests.
  • Measured with the else line removed: "nothing is printed at all, not even the banner." The ISR sent the first character, found the ring empty and was called again and again at priority 1, "above everything that could ever put more data in". Lesson 05's endless interrupt, in a new costume.
  • _write() sets TXEIE with a read-modify-write of CR1, which the ISR also writes. So that one line is a critical section, two instructions long. Two contexts doing read-modify-write on one register is lesson 03's lost-update hazard, so _write() masks interrupts around it.

9. Replacing printf's back end: weak again (slide 7)

/* _lib/retarget.c */
__attribute__((weak)) int _write(int fd, const char *buf, int len) { ...polled... }

/* 08_UART_And_Python_Host/uart.c */
int _write(int fd, const char *buf, int len) { ...ring buffer... }
  • printf has called _write() since lesson 04. retarget.c's version polls, and it is marked weak.
  • "A strong definition beats a weak one at link time." This is the same mechanism as the vector table (lesson 05, slide 30), where a correctly named handler replaces the weak Default_Handler alias.
  • The lesson keeps retarget.c's syscall stubs and replaces exactly one function. printf does not know anything changed. It now returns as soon as the text is in the ring, before the last bit has left the pin.

10. Two tasks, one serial port (slide 8)

static void say(const char *fmt, ...)
{
    va_list ap;  va_start(ap, fmt);
    os_mutex_lock(&print_lock);
    vprintf(fmt, ap);
    os_mutex_unlock(&print_lock);
    va_end(ap);
}
  • The telemetry task and the protocol task both print. Without coordination, two lines can interleave character by character, and a line that is half one frame and half another fails its checksum on the PC.
  • Lesson 07's mutex makes each line atomic. Only tasks print through say(). An ISR could not take the mutex, because locking may block.
  • Second reason: newlib-nano's printf keeps state in one shared structure and is not re-entrant. Two tasks inside it at once can corrupt each other's output even when the timing looks harmless.
  • The lesson makes no measured claim here. In Renode the UART sends instantly, so the window never opened.

11. Lines for people, frames for programs, keys (slides 9, 9b)

The protocol task collects bytes until \r or \n, then looks at the first character:

  • "A person wants words and forgiveness. A program wants a format it can parse and proof the line arrived intact", because a serial line picks up noise, drops bytes when a buffer overflows, and gets cut in half when a cable is pulled.
  • A line longer than 63 characters is thrown away whole instead of being acted on in part.
  • Keys. On a raw terminal each key is sent when you press it. A letter is one byte, an arrow key is three: ESC [ A to ESC [ D, with ESC = 0x1B. keys.c is a state machine with the frame's structure: a start byte, a body, and a final byte 0x40–0x7E that ends it, the part the * plays in a frame.
  • A lone Esc is the same 0x1B that starts every sequence. Only time tells them apart: 50 ms of silence.
  • A $ line is never echoed, or host.py would read it as a frame from the board. Telemetry waits while a line is half typed, or the board would send sta$TEL,..., which host.py skips because the line does not start with $.

12. The frame: NMEA 0183 and its XOR checksum (slide 10)

$LED,170*57
 \_____/ \/
  body   checksum: XOR of every byte of the body, two hex digits

L  E  D  ,  1  7  0
4C 45 44 2C 31 37 30    XOR all seven  ->  0x57
  • "This is NMEA 0183, the sentence format GPS receivers have printed since the 1980s." The body is everything between $ and *. Neither of the two is included.
  • host.py --selftest checks its own arithmetic against a real GPS sentence ($GPGGA,...*47), so this is the NMEA checksum, not one that merely agrees with itself.
  • XOR of bytes is the parity of each bit column: checksum bit k is 1 when an odd number of body bytes have bit k set.
  • Catches any single flipped bit. $LED,171*57 (0 → 1, one bit) is rejected: the checksum comes out 56.
  • Misses two errors in the same bit position of different bytes: they cancel. A CRC catches those. MAVLink, the drone protocol of lessons 13–14, uses one.
  • Replies: $ACK,... when the frame is good, $NAK,CHECKSUM on a mismatch, $NAK,NOSTAR when there is no *. "A frame that fails its checksum is thrown away and counted, never half-used."

15. What carries forward (slide 15)

  • "Every later peripheral that moves a stream of data looks like this": an interrupt that feeds or drains a buffer, and a task that blocks. Lesson 10 replaces the per-byte interrupt with DMA, one interrupt per block.
  • The board now has a partner. Lesson 09 sends real sensor readings in $TEL frames and host.py plots them. Part 3 swaps this protocol for MAVLink, and host.py for mission software that flies a drone.
  • Checked data, not trusted data. A frame that fails its checksum is thrown away and counted. That rule scales from a text line to a flight controller.

General idea vs this chip

Exam focus
  • BRR = f_clk / baud, rounded: 48 000 000 / 115 200 = 416.67 → 417 (0x1A1, 0.08% slow). At 48 MHz, 9600 baud → 5000. At the 12 MHz reset clock, 115 200 baud → 104.
  • Byte time = 10 / baud (start + 8 data + stop): 86.8 µs at 115 200 (11 520 bytes/s), 1.04 ms at 9600. The UART holds one received byte, so the ISR has one byte time to read RDR.
  • Bits: CR1 UE 0, RE 2, TE 3, RXNEIE 5, TXEIE 7 → 0x2D idle, 0xAD sending. ISR ORE 3, RXNE 5, TXE 7. ICR ORECF 3.
  • Clearing: RXNE by reading RDR, TXE by writing TDR, ORE by writing 1 to ORECF in ICR. Compare EXTI (write 1), TIM UIF (write 0), CC1IF (read CCR1).
  • USART2_IRQn = 28: vector 16 + 28 = 44 at 0x08000000 + 44 × 4 = 0x080000B0. One vector for all three jobs, NVIC priority 1 (0 is most urgent), above the kernel's 3.
  • TX ring: head written only by tasks, tail only by the ISR. Store the data, then move head. head == tail means empty, so 256 slots hold 255 bytes.
  • TXEIE left on with an empty ring gives an interrupt storm, because TXE is 1 whenever the transmitter is idle. The CR1 |= TXEIE in _write() is a critical section because the ISR also writes CR1.
  • uart.c's strong _write() beats retarget.c's weak one at link time, like a handler name in the vector table.
  • An ISR never blocks: os_queue_put_from_isr() drops a byte (rx_dropped) when the queue is full. Tasks print through a mutex, or lines interleave and checksums fail.
  • NMEA checksum = XOR of the bytes between $ and *: LED,170 → 57, PING → 10. It catches any single flipped bit (LED,171 → 56) and misses two flips in the same bit position (LED,060 also gives 57).
