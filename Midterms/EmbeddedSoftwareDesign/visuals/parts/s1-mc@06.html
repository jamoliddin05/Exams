Question 23 · L06, PSC and ARR

TIM3 runs from the 48 MHz clock. It must count at 2 MHz and raise an update event every 10 ms. Which register values do that?

  1. A PSC = 24, ARR = 20000 No. Both registers hold N − 1. This divides by 25 and counts 20 001 steps: 10.42 ms, about 4 % slow.
  2. B PSC = 23, ARR = 9999 No. 10 000 counts at 2 MHz is 5 ms, an update rate of 200 Hz.
  3. C PSC = 23, ARR = 19999 Correct. 48 MHz / 24 = 2 MHz, and 20 000 counts of 0.5 µs make 10 ms.
  4. D PSC = 47, ARR = 19999 No. That counts at 1 MHz and updates every 20 ms, the lesson's servo frame.

Answer: C. The counter steps once every PSC + 1 clocks, so 48 MHz / 24 = 2 MHz needs PSC = 23. 10 ms at 2 MHz is 20 000 counts, 0 to 19 999, so ARR = 19999.

Check with the slide-5b formula: 48 000 000 / (24 × 20 000) = 100 Hz, one update every 10 ms. Option A forgets the −1 in both registers, and nothing complains about it.

Exam line

fupdate = fclk / ((PSC + 1)(ARR + 1)). Both registers hold N − 1: a count of N steps runs from 0 to N − 1. Count rate first (PSC), then counts per period (ARR).

Question 24 · L06, clearing UIF

TIM3 raises an update interrupt every 20 ms at NVIC priority 2. SysTick, at priority 3, drives millis(), and TIM3 channel 1 drives the servo on PA6 in PWM mode. The update handler below builds with zero warnings. What does the board do once the timer starts?

void TIM3_IRQHandler(void)
{
    if (TIM3->SR & TIM_SR_UIF) {
        TIM3->SR = TIM_SR_UIF;
        frames++;
    }
}
  1. A It runs normally: writing 1 to a flag clears it, as it does for EXTI No. EXTI flags clear by writing 1; timer flags clear by writing 0.
  2. B Only the first frame is lost: the flag clears itself at the next update event No. Hardware only sets UIF. Software has to clear it.
  3. C The timer stops counting, and the servo pulse on PA6 stops with it No. The CPU is stuck, not the timer. The counter and the PWM channel are hardware.
  4. D The handler re-enters forever, millis() stops advancing, and the servo holds its position Correct. UIF never clears, so TIM3's handler keeps the CPU and starves the less urgent SysTick.

Answer: D. Timer flags clear by writing 0. TIM3->SR = TIM_SR_UIF writes 1 to UIF, which leaves it set, and 0 to every other flag, which clears them.

UIF stays set, so the handler re-enters as soon as it returns. SysTick at the less urgent priority 3 never runs, so millis() stops. The PWM is hardware: PA6 keeps its last pulse and the servo holds still. It builds with zero warnings.

Exam line

Timer flags clear by writing 0: TIM3->SR = ~TIM_SR_UIF;. EXTI flags clear by writing 1. Written the EXTI way, the timer handler re-enters forever, with zero warnings.

Question 25 · L06, millis() wrap

A timeout starts with start = millis();, which returns 0xFFFFFC18, 1000 ms before the 32-bit millisecond counter wraps. Which test becomes true exactly when 1000 ms have passed, here and for any other start value?

  1. A if (millis() >= start + 1000u) No. start + 1000u wraps to 0, so the test is true at once.
  2. B if (millis() - start >= 1000u) Correct. Unsigned subtraction is modulo 2³², so it is the true elapsed time across the wrap.
  3. C if (start - millis() >= 1000u) No. Backwards: 1 ms after the start it gives 0xFFFFFFFF and fires.
  4. D if (millis() > start && millis() - start >= 1000u) No. It never fires: the extra check is false after the wrap, exactly when the difference reaches 1000.

Answer: B. Unsigned subtraction is modulo 2³², so millis() - start is the true elapsed time even when millis() has wrapped past zero and start has not. At millis() = 0x00000000 it gives 2³² − 0xFFFFFC18 = 1000.

The absolute comparison in A breaks at the wrap: here the deadline start + 1000u is itself 0, so the timeout fires immediately. "now - then is the only comparison you write."

Exam line

A uint32_t millisecond counter wraps after 2³² ms, 49.7 days. if (millis() - start >= period) is right, always; if (millis() >= deadline) is wrong at the wrap.

Question 26 · L06, input capture

TIM14 counts at 1 MHz and captures both edges of the HC-SR04 echo on PA7. Its interrupt handler sometimes starts 1 µs after an edge and sometimes 100 µs after, depending on what else is running. Why is the measured echo width still exact to the microsecond?

  1. A At the edge the hardware copies CNT into CCR1 before the interrupt is even requested, so latency changes when the handler reads the time, not what the time says Correct. The handler is a courier, not a stopwatch.
  2. B TIM14 has NVIC priority 1, the most urgent in the program, so its handler starts with no latency No. Priority shortens the wait but cannot remove it, and the question says the latency varies.
  3. C Reading CCR1 clears CC1IF, so no edge is ever missed No. True, but that is how the interrupt is acknowledged. It says nothing about accuracy.
  4. D Both edges are delayed by the same latency, so it cancels in the subtraction No. That is the EXTI fallback's argument (slide 13b). It fails when one edge waits longer than the other.

Answer: A. Input capture takes the timestamp in hardware. The edge copies CNT into CCR1, and only then is CC1IF raised and the interrupt requested.

"ISR latency, 1 µs or 100 µs, changes when you read it, not what it says." Timing the pulse with an EXTI interrupt that reads CNT would include each handler's latency, and the latency varies with whatever else is running.

Exam line

Input capture: on the edge the hardware copies CNT into CCR1, then raises CC1IF. The timestamp is taken before the interrupt is even requested, so latency changes when you read it, not what it says.
