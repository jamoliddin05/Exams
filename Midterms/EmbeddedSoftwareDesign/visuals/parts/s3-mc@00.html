Question 1 · L00, Little-endian load of network bytes

A sensor sends a 32-bit count most significant byte first, in network byte order: 00 01 86 A0, which is 0x000186A0 = 100000. The bytes are stored in arrival order in a 4-byte-aligned buffer buf, and the STM32C031 reads them with uint32_t n = *(uint32_t *)buf;. What is n?

  1. A 0x000186A0 No. That needs a big-endian machine or a byte swap such as ntohl().
  2. B Nothing: the load raises a HardFault No. buf is 4-byte aligned, so the word load is legal on the M0+.
  3. C 0x0A681000 No. That reverses the hex digits. Byte order moves whole bytes.
  4. D 0xA0860100 Correct. buf[0] = 0x00 lands in bits 7:0 and buf[3] = 0xA0 in bits 31:24.

Answer: D. The load is aligned, so it works. Every STM32 is little-endian, so the byte at the lowest address becomes the least significant. buf[0] = 0x00 lands in bits 7:0 and buf[3] = 0xA0 in bits 31:24, which gives 0xA0860100, about 2.69 billion instead of 100000.

A needs a big-endian machine or a byte swap, which is what ntohl() does. C reverses the hex digits instead of the bytes. "The other convention reaches you only when bytes arrive from somewhere else", and a sensor on a wire is exactly that case.

Why the other options are wrong

Option A
The sender's value, not the load's

0x000186A0 is what the sensor meant. Getting it back takes a byte swap, which is what ntohl() is for. A plain load on a little-endian chip does no swap.

A0860100ntohl()000186A0
Option B
Aligned, so no fault

The M0+ faults only when a word load's address is not a multiple of 4. buf is 4-byte aligned, so this load is legal.

buf % 4 = 0→load works
Option C
Digits reversed, not bytes

Reading the hex string backwards splits every byte. The two digits of a byte always travel together.

000186A0reversed0A681000
Exam line

Every STM32 is little-endian, so the byte at the lowest address becomes bits 7:0. Bytes that arrive in network byte order (big-endian) read back reversed, so 00 01 86 A0 loads as 0xA0860100 until a byte swap such as ntohl() fixes it.

Question 2 · L00, Privilege without virtual memory

On a desktop, a store through a corrupted pointer usually ends in a segmentation fault. On the STM32C031, the program drives PB3 as an output that enables a motor driver, and a corrupted pointer p now holds 0x50000414, the address of GPIOB's ODR. The code runs *p = 0x08;. The MPU is not configured. What happens?

  1. A A segmentation fault: the MMU traps the store, because 0x50000414 is outside the program's virtual address space No. This chip has no MMU, so nothing translates the address or traps the store.
  2. B Nothing: peripherals sit in a separate I/O space, so an ordinary store cannot reach them No. That is port-mapped I/O. Here peripherals sit at ordinary addresses.
  3. C A HardFault: the MPU gives each program a private map of memory, and 0x50000414 is not in it No. An MPU only sets permission rules over real addresses, and this one is not configured.
  4. D The store goes through and PB3 goes high: there is no MMU and one real address space, so the pointer reaches a peripheral Correct. The store is an ordinary str to GPIOB's ODR, and 0x08 is bit 3.

Answer: D. The hardware that turns a bad pointer into a segmentation fault is the MMU, which gives each desktop program a private virtual map. This chip has the two privilege levels "and none of the virtual memory". There is one real address space, shared by everything, with peripherals at ordinary addresses.

So the store is an ordinary str to GPIOB's ODR. 0x08 is bit 3, PB3 goes high and the motor turns, with no error. An MPU only sets permission rules over the real addresses, and only once software programs it. It never builds a private map.

Exam line

A desktop stops a bad pointer with the MMU (segmentation fault). This chip has two privilege levels and no virtual memory. It has one real address space and at most an MPU of permission rules, so a stray pointer quietly reaches a peripheral, with no error.

Question 3 · L00, xPSR and the exception number

A breakpoint stops the STM32C031 inside an interrupt handler, and the debugger shows xPSR = 0x01000020. Which IRQ is being serviced, and which vector-table slot holds its handler's address?

  1. A IRQ 4, slot 20 No. That reads 0x20 as decimal 20.
  2. B IRQ 32, slot 48 No. 32 is already the slot. Adding 16 again counts ARM's slots twice.
  3. C IRQ 16, slot 32 Correct. ISR = 0x20 = 32 is the slot, and 32 − 16 = 16 is the IRQ, TIM3.
  4. D IRQ 20, slot 36 No. That reads 0x20 as decimal 20 and treats it as the IRQ.

Answer: C. The bottom of xPSR, the IPSR view in bits 5:0, holds the exception number, which is the slot the hardware took. 0x20 is 32. Bit 24 is the Thumb bit T, always 1, and the flags N Z C V are all 0.

The first 16 slots are ARM's, so the vendor IRQ is 32 − 16 = 16, which is TIM3. Its handler's address sits at 0x08000000 + 4 × 32 = 0x08000080. A and D read 0x20 as decimal 20, and B adds the 16 a second time.

Exam line

xPSR is one word read three ways: flags N Z C V in bits 31:28, the Thumb bit in bit 24, and the IPSR exception number in bits 5:0. Inside a handler that number is the slot. IRQ = slot − 16, and the vector sits at 0x08000000 + 4 × slot.

Question 4 · L00, A register is not a variable

GPIOA's output data register ODR is at 0x50000014, and PA5 is an output. The two lines below must drive PA5 high and then low. Which definition of GPIOA_ODR guarantees that both stores reach the pin?

GPIOA_ODR = 1u << 5;   /* PA5 high */
GPIOA_ODR = 0;         /* PA5 low  */
  1. A #define GPIOA_ODR (*(volatile uint32_t *)0x50000014u) Correct. An object at 0x50000014 that the compiler must access exactly as written.
  2. B #define GPIOA_ODR (*(uint32_t *)0x50000014u) No. Right address, but the first store is dead to the compiler and may be deleted.
  3. C uint32_t GPIOA_ODR = 0x50000014u; No. That is a RAM variable that holds the number 0x50000014. The pin never moves.
  4. D volatile uint32_t GPIOA_ODR = 0x50000014u; No. volatile makes both stores happen, and they still go to RAM.

Answer: A. A register is an address. A turns that address into an object the compiler must access "exactly as written", so both stores go to 0x50000014 in order and PA5 goes high, then low.

B reaches the right address, but without volatile the compiler may cache, reorder or delete accesses. The second store overwrites the first, so the first is dead and may vanish. C and D declare variables in RAM that merely hold the number 0x50000014. Their stores change RAM, and the pin never moves.

Why the other options are wrong

Option B
Right address, no promise

Without volatile the compiler treats ODR like memory. Nothing reads the value 0x20 before it is overwritten, so the first store may be removed.

Option C
A number in a variable

0x50000014 becomes the initial value of a RAM variable. The two lines overwrite that variable and never touch the register.

Option D
volatile on the wrong object

volatile makes every access to the variable happen. The accesses still go to the variable's own RAM address.

Exam line

A register is an address, reached through a volatile pointer such as (*(volatile uint32_t *)0x50000014u). Without volatile the compiler may cache, reorder or delete accesses; for a register, every access must happen exactly as written.
