Question 23 · L06, PWM from PSC, ARR and CCR1

At 48 MHz, TIM3 channel 1 runs in PWM mode 1 on PA6 with PSC = 23, ARR = 39999 and CCR1 = 3000. What signal does PA6 carry?

  1. A A 3.0 ms high pulse every 40 ms No. That reads every count as 1 µs. With PSC = 23 a count is 0.5 µs.
  2. B A 3.0 ms high pulse every 20 ms No. The frame is right, but CCR1 = 3000 is 3000 counts of 0.5 µs, not 3000 µs.
  3. C 18.5 ms high, then 1.5 ms low, every 20 ms No. Mode 1 is high while CNT < CCR1, at the start of each frame.
  4. D A 1.5 ms high pulse every 20 ms, the servo's centre position Correct. 40 000 counts × 0.5 µs = 20 ms, and 3000 counts × 0.5 µs = 1.5 ms.

Answer: D. 48 MHz / (23 + 1) = 2 MHz, so one count is 0.5 µs. The frame is ARR + 1 = 40 000 counts = 20 ms, which is 50 Hz. PWM mode 1 holds the pin high while CNT < CCR1: 3000 counts × 0.5 µs = 1.5 ms, the servo's nominal centre.

"CCR1 is the pulse width in microseconds" holds only at the lesson's 1 µs count, PSC = 47. Here CCR1 holds the width in counts.

Exam line

One count = (PSC + 1) / fclk. Frame = (ARR + 1) counts, pulse = CCR1 counts, high while CNT < CCR1 (PWM mode 1). A servo reads a pulse every 20 ms: 1.0 ms one end, 1.5 ms centre, 2.0 ms the other end.

Question 24 · L06, cooperative scheduling

The superloop below runs three jobs, and now is read once per pass. The report job is changed so that it takes 130 ms. At t = 1000 ms the loop runs the ping, then starts the report. When does the next ping run, and when is the one after it due?

for (;;) {
    uint32_t now = millis();
    if (now - ping_at   >= 100)  { ping_at   += 100;  ranger_ping(); }
    if (now - report_at >= 1000) { report_at += 1000; report();      }
    if (now - beat_at   >= 500)  { beat_at   += 500;  toggle_ld4();  }
}
  1. A At 1100 ms: the SysTick interrupt stops the report and runs the ping on time No. That is preemption. SysTick_Handler only counts milliseconds; the jobs run from the loop.
  2. B The 1100 ms ping is skipped; the next ping runs at 1200 ms No. When the loop comes back, now − ping_at = 130 ≥ 100, so the late ping still runs.
  3. C At about 1130 ms, when the report returns; the one after it is still due at 1200 ms Correct. A job stops only when it returns, and += 100 keeps the 100 ms grid.
  4. D At about 1130 ms, and every later ping is 30 ms late too: 1230, 1330, ... No. That is what ping_at = now would do. The += form absorbs the lateness.

Answer: C. This is cooperative scheduling: a job stops only when it returns. The ping due at 1100 ms waits for the report and runs at about 1130 ms, when the loop comes back.

ping_at += 100 makes ping_at 1100, so the schedule stays on the 100 ms grid and the next ping is due at 1200 ms. Taking the CPU away from a running job is preemption, which lesson 07's kernel adds on top of the same SysTick.

Exam line

Cooperative scheduling (superloop): each job runs until it returns, so one job that takes 130 ms delays all the others by up to 130 ms. Preemptive scheduling (RTOS, lesson 07): the kernel's tick takes the CPU away. Write x_at += period, not x_at = now.

Question 25 · L06, shadow registers and UG

At 48 MHz a fresh TIM3 is set up as below for one update per second, but the EGR = UG line was left out. When do the update interrupts come?

TIM3->PSC   = 999;
TIM3->ARR   = 47999;
TIM3->DIER |= TIM_DIER_UIE;
TIM3->CR1  |= TIM_CR1_CEN;     /* ARPE stays 0 */
  1. A The first after 1 ms, then one every second Correct. The first period still uses the reset prescaler 0: 48 000 counts at 48 MHz.
  2. B Never: PSC stays in its preload register, so the counter never counts No. The counter runs with the old prescaler, and its first update copies the preload across.
  3. C One every second from the start, since both registers take effect when written No. PSC is always double-buffered. Only ARR, with ARPE = 0, takes effect at once.
  4. D One every millisecond, forever No. The first update event copies 999 into the shadow register; after that each period is 1 s.

Answer: A. PSC is double-buffered. The write lands in the preload register, and the counter keeps using the shadow copy, still the reset value 0, until the next update event. The first period is 48 000 counts at 48 MHz, 1 ms. ARR took effect at once only because ARPE is 0.

That first update copies 999 across, and from then on 48 000 000 / (1000 × 48 000) = 1 Hz. EGR = UG forces that copy before the timer starts. On a timer that runs forever this is a glitch you probably will not see.

Exam line

PSC, ARR and CCR1 are double-buffered: a write lands in the preload register and takes effect at the next update event. Write EGR = UG after PSC and ARR, then clear the UIF it raised, or the first period runs at the wrong rate.

Question 26 · L06, capture flag CC1IF

TIM14 counts at 1 MHz and captures both edges of the echo on PA7, with CC1IE set. Which body of TIM14_IRQHandler stores the edge's own timestamp in t and acknowledges the capture interrupt?

  1. A t = (uint16_t)TIM14->CNT; TIM14->SR = TIM_SR_CC1IF; No. CNT is the time now, and writing 1 leaves CC1IF set: the handler re-enters forever.
  2. B t = (uint16_t)TIM14->CNT; TIM14->SR = ~TIM_SR_CC1IF; No. The flag clears, but CNT is late by the interrupt latency.
  3. C t = (uint16_t)TIM14->CNT; No. Reading CNT clears nothing, and it is the wrong time.
  4. D t = (uint16_t)TIM14->CCR1; Correct. CCR1 holds the edge's time, and reading it clears CC1IF.

Answer: D. At the edge the hardware copied CNT into CCR1, so CCR1 holds the edge's time. Reading CCR1 also clears CC1IF, the only clearing convention in the course that needs no write.

CNT is the time now, late by the interrupt latency, so A, B and C store the wrong time. B at least clears the flag, because timer flags clear by writing 0. A writes 1, which leaves CC1IF set, and C clears nothing, so both re-enter forever.

Exam line

Reading CCR1 clears CC1IF: t = (uint16_t)TIM14->CCR1; takes the edge's time and acknowledges the capture in one load. Timer SR flags clear by writing 0, EXTI flags by writing 1.
