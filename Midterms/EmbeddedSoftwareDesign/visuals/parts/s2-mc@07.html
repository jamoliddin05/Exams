Question 27 · L07, Task priority numbering

A student wants the CPU hog to be the least urgent task. Thinking of the NVIC, where 0 is most urgent, they create it with priority 4. The other tasks keep theirs: button 3, bar 2, report 1, idle 0. The hog never sleeps. What does the board do?

  1. A The hog is now the most urgent task and is always READY, so the bar, the buttons and the report never run again Correct. In the kernel, bigger is more urgent, and pick() always takes the most urgent READY task.
  2. B The hog runs only when every other task is asleep, as the student intended No. That would need the smallest number, as the deck's hog has (1).
  3. C os_task_create() rejects priority 4, because __NVIC_PRIO_BITS = 2 allows only 0–3, so the hog never runs No. __NVIC_PRIO_BITS limits interrupt priorities. A task priority is just a number in the TCB.
  4. D Round-robin gives each of the five tasks one tick in turn, so the hog gets a fifth of the CPU No. Round-robin only shares the CPU among tasks of equal priority.

Answer: A. In this kernel a higher number is more urgent, so 4 puts the hog above every other task. pick() always runs the highest-priority READY task, and the hog never leaves READY.

Nothing else is ever picked: the LED bar freezes, the buttons die and the report stops. The other tasks still wake on the tick and wait READY forever.

Exam line

Fixed-priority preemptive: the highest-priority READY task runs, always. In this kernel the highest number is most urgent, so an always-READY task at the top starves everything below it.

Question 28 · L07, PendSV: deciding vs switching

In this kernel, schedule() runs inside SysTick_Handler and inside other handlers, such as a UART receive interrupt. When it finds that another task should run, it only writes SCB->ICSR = SCB_ICSR_PENDSVSET_Msk. Why is the switch itself left to PendSV_Handler?

  1. A Handlers run unprivileged, and only PendSV is allowed to write PSP No. Handler mode is always privileged; any handler could write PSP.
  2. B A switch must never happen inside another handler; PendSV has the lowest priority, so it runs only when no other handler is active, on the way back to a task Correct. Deciding happens anywhere, switching only in PendSV at priority 3.
  3. C PendSV is the most urgent exception, so pending it makes the switch happen before the deciding handler's next instruction No. PendSV is at 3, the least urgent NVIC level. It waits for every other handler.
  4. D Only PendSV's entry makes the hardware stack r4–r11; other exceptions stack only 8 words No. Every exception entry stacks the same 8 words. PendSV's own code saves r4–r11.

Answer: B. Deciding can happen anywhere; switching happens in one place, PendSV, which is pended by software and set to priority 3, the lowest. A handler's own frame is on MSP and half-finished, and swapping the task beneath it would return it into the wrong world.

So PendSV waits until every other handler has finished and tail-chains on the way back to a task. If the decision changes first, schedule() can still cancel it with PENDSVCLR.

Exam line

Deciding (schedule(), anywhere, can cancel with PENDSVCLR) is separate from switching (PendSV_Handler, one place). PendSV is pended by software and has the lowest priority, so the switch happens only when no other handler is active.

Question 29 · L07, EXC_RETURN and the two stacks

Inside HardFault_Handler, the lr register holds 0xFFFFFFF1. The handler tests bit 2 of lr to find which stack holds the faulting frame. Which reading is correct?

  1. A The frame is on PSP; a task was running in Thread mode No. That is 0xFFFFFFFD, low nibble 1101.
  2. B The frame is on MSP; an exception handler was running Correct. Low nibble 0001: bit 2 = 0 (MSP), bit 3 = 0 (Handler mode).
  3. C The frame is on PSP; an exception handler was running No. Bit 2 is 0, so MSP. Handlers always run on MSP.
  4. D The frame is on MSP; main() was running in Thread mode, before the first switch No. That is 0xFFFFFFF9, low nibble 1001: bit 3 = 1.

Answer: B. The low nibble of 0xFFFFFFF1 is 0001. Bit 2 = 0 selects MSP, and bit 3 = 0 means the return goes to Handler mode, so a handler faulted.

A task's fault gives 0xFFFFFFFD (1101: Thread mode, PSP), the value every switch in this kernel returns with. 0xFFFFFFF9 (1001) is Thread mode on MSP, as main() runs before os_start.

Exam line

EXC_RETURN: 0xFFFFFFFD Thread mode, PSP (every switch, a task faulted); 0xFFFFFFF9 Thread mode, MSP; 0xFFFFFFF1 Handler mode, MSP. Bit 2 = 1 means PSP.

Question 30 · L07, Mutex vs masking interrupts

Tasks low (priority 1) and high (priority 2) share a table. Low's update of the table takes about 30 ms; high only reads it, using the same protection as low. The button task (priority 3) never touches the table and must stay on time. Which code should surround low's update?

  1. A __disable_irq(); update_table(); __enable_irq(); No. For 30 ms every interrupt is held off, the tick included, so the button task cannot wake.
  2. B while (busy) { } busy = 1; update_table(); busy = 0; No. High spins on busy above low's priority, so low never runs again to clear it.
  3. C SCB->ICSR = SCB_ICSR_PENDSVCLR_Msk; update_table(); No. It cancels only the switch pending now. The next tick pends PendSV again.
  4. D os_mutex_lock(&m); update_table(); os_mutex_unlock(&m); Correct. Only a task that wants the table waits, BLOCKED off the CPU.

Answer: D. A mutex holds up only the tasks that want this table. High, if it asks during the update, is BLOCKED off the CPU, while the button task and every interrupt carry on.

Masking interrupts is for a few instructions; for a 30 ms critical section it freezes the whole system. Slide 12: "The mutex is a way to make a long critical section cheap for everyone who does not need it."

Exam line

Masking interrupts holds up everything and may last only a few instructions. A mutex holds up only the tasks that want the resource, may last as long as the work takes, and its waiters are BLOCKED off the CPU. An ISR cannot use a mutex.
