Question 9 · L02, Address binding

Your laptop builds hello.c without any linker script from you, and the same binary runs at a different address on every launch. The STM32C031C6 build needs a hand-written link.ld, and SystemCoreClock is at 0x20000000 on every run. Which build stage reads link.ld, and why does only the embedded build need you to write it?

  1. A Compile: the compiler needs the chip's addresses to generate Thumb instructions, and an x86 compiler does not No. The compiler sees one file at a time and leaves a hole and a note wherever it needs an address it does not have.
  2. B Preprocess: link.ld supplies the #defines for the register addresses, which a laptop gets from the OS headers No. Register names come from C headers. link.ld describes memory regions and is read by the linker.
  3. C Link and locate: with no loader and no MMU, every name is bound to its real address at build time, so you must describe the memory map; the laptop binds at run time with an MMU Correct. Locate is the embedded stage, and binding at build time is why its input is written by hand.
  4. D Assemble: Thumb instructions are 16 bits wide, so the assembler needs link.ld to know where each instruction goes No. The assembler turns one file into an .o with no final addresses. Instruction width has nothing to do with where code is placed.

Answer: C. A name can be bound to its address at compile time, load time or run time. A laptop binds at run time: an MMU translates addresses while the program runs, so the same binary works wherever it lands.

This chip has no loader and no MMU, so binding happens at build time and is burned into the image. The locate stage does it, from the memory map you write in link.ld. Preprocess, compile and assemble work on one file at a time and assign no final addresses.

Exam line

Five stages: preprocess, compile, assemble, link, locate. Locate is the embedded one. With no loader and no MMU, binding happens at build time and is burned into the image, so you write the linker script by hand. A laptop binds at run time with an MMU.

Question 10 · L02, Flash and RAM cost

A project builds and runs. You add the three globals below. By how much do FLASH used and RAM used in the build's memory report grow? Ignore alignment.

const uint8_t lut[64] = {1, 2, 3};
uint32_t samples[32];
uint32_t gain = 3;
  1. A FLASH +196 B, RAM +196 B No. 196 = 64 + 128 + 4 charges every variable to both memories.
  2. B FLASH +64 B, RAM +132 B No. It forgets that the initial value of gain must also be stored in flash.
  3. C FLASH +68 B, RAM +132 B Correct. Flash 64 (.rodata) + 4 (.data values) = 68. RAM 128 (.bss) + 4 (.data) = 132.
  4. D FLASH +68 B, RAM +196 B No. A const table never changes, so it stays in flash and takes no RAM.

Answer: C. lut is const, so it goes in .rodata: 64 B of flash and no RAM. samples starts at zero, so it goes in .bss: 128 B of RAM and nothing in flash, because the image records only how many bytes to clear.

gain has a starting value, so it is .data and costs both: 4 B of RAM for the variable and 4 B of flash for its initial value. FLASH 64 + 4 = 68, RAM 128 + 4 = 132.

Exam line

const goes to .rodata (flash only). Zero-initialised globals go to .bss (RAM only, nothing stored in flash). Globals with a starting value go to .data and cost both: the values live in flash, the variables live in RAM.

Question 11 · L02, Missing .bss loop

In a student's Reset_Handler the .data copy is present, but the .bss loop was deleted by mistake. static uint32_t presses; counts button presses. Every test right after plugging the board in passes, but after pressing the reset button the count sometimes starts at a large number. What explains this?

  1. A Without the .bss loop, presses starts as whatever that RAM held, and a reset does not clear SRAM, so after a reset it keeps the previous run's count Correct. The bug depends on what ran before, so it is intermittent.
  2. B The hardware zeroes RAM when power is applied, but the reset button skips that step No. At any reset the hardware only loads SP and PC from two words of flash. It never clears RAM.
  3. C presses is in .data, so its first value is copied from flash, and flash still holds the count from the last run No. A static with no initial value is .bss, and stores go to RAM, never back to flash.
  4. D The RAM LENGTH in link.ld is too large, so the linker placed presses past the end of real RAM No. A wrong LENGTH moves the top of RAM, where the stack is. .bss starts near 0x20000000.

Answer: A. A global or static with no initial value is in .bss, and only the .bss loop in Reset_Handler sets it to zero. Without that loop the variable starts as whatever RAM held.

The slide's wording: the program works perfectly on a cold boot and misbehaves after a reset. A reset does not clear SRAM, so after the reset button presses still holds what the previous run left. The value depends on history, which is why the bug is intermittent.

Exam line

Skip the .bss loop and globals start as whatever was in RAM. The program works on a cold boot and misbehaves after a reset, because a reset does not clear SRAM: an intermittent, history-dependent bug.
