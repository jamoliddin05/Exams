Question 5 · L01, Load–store vs register–memory

On an x86 PC, counter++ on a global int compiles to one instruction, add dword [counter], 1. On the STM32C031 the same line compiles to three: ldr r0, [r1], adds r0, r0, #1, str r0, [r1]. What explains the difference, and what does it cost?

  1. AThe Cortex-M0+ is a register–memory machine, so its ALU must copy the value into a register before it can add to itNo. The models are swapped: the Cortex-M0+ is load–store, the x86 is register–memory.
  2. BThe Cortex-M0+ is a load–store machine, so its three instructions make three bus accesses where the x86 makes oneNo. adds works on r0 only. Both versions read memory once and write it once.
  3. CThe x86 is a load–store machine too, but its decoder hides the load and the store inside one long instructionNo. The x86 is the textbook register–memory machine: its ALU operand may be an address.
  4. DThe Cortex-M0+ is a load–store machine: only ldr and str touch memory, so it needs more instructions, but both versions make the same two bus accessesCorrect. Load–store costs instructions, not memory traffic.

Answer: D. On a load–store machine the ALU sees registers only, and memory is reached only by ldr and str. The x86 is register–memory, so one instruction reads counter, adds 1 and writes it back.

Both versions read memory once and write it once. The slide's summary is "load–store costs instructions, not memory traffic". The three instructions only spell out what the one x86 instruction hides.

Exam line

This chip is load–store: only ldr/str touch memory. counter++ is 3 instructions here and 1 on the register–memory x86, but 2 bus accesses on both.

Question 6 · L01, Signed vs unsigned branches

A calibration offset is declared uint32_t by mistake. This time get_offset() returns −3. The code is built with gcc -Os. What does the board do?

uint32_t delta = get_offset();   /* returns -3 this time */
if (delta < 100) { ok(); } else { alarm(); }
  1. AIt calls ok(), because −3 is less than 100No. That holds for a signed int. delta is unsigned, so −3 became 4 294 967 293.
  2. BIt calls ok(), because cmp leaves N = 1 and the compiler branches on N with bltNo. The compiler uses blt only for signed types. For uint32_t it uses bcc/bcs, which read C.
  3. CNothing runs: the build fails, because −3 cannot be stored in a uint32_tNo. The conversion is legal C. It compiles without an error, which is why the bug is silent.
  4. DIt calls alarm(): delta is unsigned, so the compiler uses an unsigned branch (bcc/bcs), and 0xFFFFFFFD read as unsigned is 4 294 967 293, which is not below 100Correct. Unsigned compare, C = 1, so alarm().

Answer: D. −3 stored in a uint32_t is the bit pattern 0xFFFFFFFD. The compiler picks the branch from the variable's type: an unsigned < becomes cmp plus bcc/bcs, which read the carry flag. 4 294 967 293 ≥ 100, so C = 1 and alarm() runs.

A signed int would use blt/bge, which read N and V, and −3 < 100 would hold. The two readings agree for 0 to 99 and split only for negative values: the slide's "comparison that behaves oddly at the extremes of a range".

Exam line

cmp sets N Z C V and the next branch reads them. blt/bge are signed, bcc/bcs are unsigned, and the compiler picks by the variable's type. A comparison that fails only at the extremes of its range is a signedness bug.

Question 7 · L01, LR and the Thumb bit

In main, the instruction bl clock_init sits at address 0x08000312. You stop the debugger at the first instruction of clock_init. What does LR read, and where does execution continue when clock_init returns with bx lr?

  1. ALR is unchanged, because bl pushed the return address 0x08000316 onto the stackNo. That is a stack-based machine such as the AVR. ARM is a link-register machine: bl writes LR.
  2. BLR = 0x08000316, and execution continues at 0x08000316No. bl sets bit 0, the Thumb bit, so LR is odd.
  3. CLR = 0x08000317, and execution continues at 0x08000316Correct. Next instruction | 1 into LR; bx lr clears bit 0 again.
  4. DLR = 0x08000315, and execution continues at 0x08000314No. That counts bl as 2 bytes. It is one of the six 32-bit instructions, 4 bytes.

Answer: C. bl is a 32-bit instruction, so the next instruction starts at 0x08000312 + 4 = 0x08000316. bl writes that address into LR with bit 0 set, the Thumb bit: 0x08000316 | 1 = 0x08000317.

bx lr reads bit 0 as "Thumb" and branches to LR & ~1 = 0x08000316, the instruction right after the call. Nothing is skipped and nothing is off by one.

Exam line

bl (4 bytes) writes the return address into LR with bit 0 set: LR = next | 1, always odd. bx lr branches to LR & ~1, the instruction after the call.

Question 8 · L01, Literal pool

SystemInit() needs the FLASH base address 0x40022000 in r2. Which instruction or pair does arm-none-eabi-gcc emit for the Cortex-M0+?

  1. Amovs r2, #0x40022000No. The movs immediate is 8 bits, 0 to 255. This cannot be encoded.
  2. Bldr r2, [pc, #44], which loads the word 0x40022000 from a literal pool stored in flash just after the functionCorrect. ARM's answer: a literal pool, loaded PC-relative.
  3. Clui r2, 0x40022 followed by addi r2, r2, 0No. That is RISC-V's answer, two halves. These are not Thumb instructions.
  4. Dmovw r2, #0x2000 followed by movt r2, #0x4002No. That is the Thumb-2 answer on a Cortex-M3 or M4. The M0+ is Thumb-1 plus six and has no movw/movt.

Answer: B. A 16-bit instruction cannot hold a 32-bit constant: after the opcode and the register, movs has 8 bits left, enough for 0 to 255. So the compiler parks 0x40022000 in a literal pool, a list of words just after the function, and loads it relative to the PC.

Every fixed-width machine needs some answer to this. RISC-V builds the constant in two halves with lui and addi, and a Cortex-M4 uses movw and movt. The M0+ has neither.

Exam line

A 16-bit instruction cannot hold a 32-bit constant. ARM's answer is a literal pool next to the code, loaded PC-relative (ldr r2, [pc, #44]). RISC-V uses lui + addi; an M4 uses movw/movt, which the M0+ lacks.
