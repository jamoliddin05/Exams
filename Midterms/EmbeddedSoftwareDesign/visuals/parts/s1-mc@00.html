Question 1 · L00, Little-endian bytes

uint32_t x = 0x1A2B3C4D; is stored at address 0x20000100 on the STM32C031. A debugger's memory view lists the bytes from 0x20000100 to 0x20000103, lowest address first. What does it show?

  1. A 1A 2B 3C 4D No. That is big-endian, network byte order. Every STM32 is little-endian.
  2. B 4D 3C 2B 1A Correct. The least significant byte, 0x4D, goes to the lowest address.
  3. C D4 C3 B2 A1 No. That reverses the hex digits. Byte order moves whole bytes.
  4. D 3C 4D 1A 2B No. That puts the low halfword first but writes each halfword big-endian.

Answer: B. Every STM32 is little-endian, so the least significant byte goes to the lowest address. 0x4D (bits 7:0) sits at 0x20000100, then 0x3C and 0x2B, and 0x1A (bits 31:24) sits at 0x20000103.

A is big-endian, the convention of the 68000, classic SPARC and every internet header. C and D are not byte orders any machine uses for a 32-bit word.

Why the other options are wrong

Option A
Big-endian

Most significant byte first. The 68000, classic SPARC and internet headers use it, which is what htonl() is for.

+01A2B3C4D
Option C
Digits reversed, not bytes

Reading the hex string backwards splits every byte. The two digits of a byte always travel together.

1A2B3C4DreversedD4C3B2A1
Option D
Halfwords swapped

Low halfword 0x3C4D first, high halfword 0x1A2B second, each written big-endian. Little-endian also reverses the bytes inside each halfword.

3C4D1A2Bvs4D 3C2B 1A
Exam line

Little-endian: the least significant byte goes to the lowest address. 0x1A2B3C4D at a is 4D 3C 2B 1A from a to a + 3. Every STM32 is little-endian; network byte order is big-endian.

Question 2 · L00, I/O model and address spaces

An AVR reaches PORTB with the IN and OUT instructions, and reads a constant table in flash with LPM (the PROGMEM keyword). The STM32C031 reaches a GPIO register, a global variable and a const table in flash with the same ldr instruction. Which option names both machines' choices correctly?

  1. A AVR: port-mapped I/O, Harvard. STM32C031: memory-mapped I/O, one von Neumann address space Correct. This is slide 15's AVR vs Cortex-M table.
  2. B AVR: memory-mapped I/O, Harvard. STM32C031: port-mapped I/O, one von Neumann address space No. The I/O models are swapped. Dedicated IN and OUT instructions mean port-mapped.
  3. C AVR: port-mapped I/O, von Neumann. STM32C031: memory-mapped I/O, Harvard No. The address spaces are swapped. LPM exists because the AVR is Harvard.
  4. D AVR: port-mapped I/O, Harvard. STM32C031: memory-mapped I/O, Harvard, since some Cortex-M cores fetch code and data over separate buses No. Separate buses are an implementation choice underneath. The address map stays single.

Answer: A. IN and OUT reach a separate I/O space through dedicated instructions, which is port-mapped I/O. LPM exists because code and data live in separate address spaces, which is Harvard.

The STM32C031 has no port space and one unified address space. One ldr reaches a register, a variable and a flash constant, and only the address tells them apart. D is the trap. Separate buses on some cores do not change the single map.

Exam line

AVR: port-mapped I/O (IN/OUT) and Harvard (LPM, PROGMEM). This chip: memory-mapped I/O with no port space, and one unified address space. Everything the CPU reaches, it reaches by address.

Question 3 · L00, Vectored dispatch

In startup.c, a copy-paste slip puts USART2_IRQHandler in the vector-table entry that belongs to TIM3. The code builds with no warning. What happens when TIM3 raises its interrupt?

  1. A The NVIC notices that the address is not TIM3's handler and raises a HardFault No. Nothing checks who owns an address. A slot is just a number.
  2. B The NVIC looks up TIM3_IRQHandler by name and runs it, so the slip does no harm No. The NVIC does not search. It indexes a table of addresses.
  3. C The CPU runs Default_Handler, because the function in TIM3's entry has the wrong name No. Names are gone at run time. The slot holds USART2_IRQHandler's address.
  4. D The CPU jumps to USART2_IRQHandler and runs it, because nothing checks what an entry holds Correct. "Put the wrong address in a slot and the chip jumps there anyway."

Answer: D. Dispatch on this chip is vectored. TIM3's number indexes a table of plain addresses, and the hardware loads the address in that slot and jumps there. There is no registration call and no check.

The hardware never sees names. A name only decides, at build time, which address goes into the table. Once the wrong address is there, USART2's code runs for every TIM3 interrupt.

Why the other options are wrong

Option A
No check, no fault

A slot holds 32 bits and nothing else. The hardware cannot tell TIM3's code from USART2's code, so it has nothing to fault on.

Option B
No search by name

Function names live in the source and the linker. Flash holds only numbers, and "the NVIC does not search for your handler".

Option C
Default_Handler needs its own address in the slot

A misspelled handler name leaves the weak default's address in the slot (L04 slide 8). Here the slot holds USART2_IRQHandler's address, so that is what runs.

Exam line

Vectored dispatch: the source's number indexes a table, and this chip's table holds plain addresses. There is no registration call. A handler is connected because its address sits in the right slot. Put the wrong address in a slot and the chip jumps there anyway.

Question 4 · L00, Clock gate

Right after reset, the code writes USART2->CR1 = 0x0000000D; and then reads USART2->CR1 back. It reads 0x00000000. The build had no warnings and nothing faulted. What is the first suspect?

  1. A The pin multiplexer: PA2 still belongs to GPIO, so USART2 cannot drive it No. A wrong pin owner leaves the pin silent, but CR1 still reads back what was written.
  2. B The clock gate: USART2's enable bit in RCC is still 0, so the peripheral ignores the write Correct. "A peripheral with no clock reads back as zero and ignores every write."
  3. C The baud divisor: it was computed from the CPU clock instead of USART2's bus clock No. A wrong divisor gives garbage on the wire. CR1 still reads back.
  4. D The register role: CR1 is a status register, so the hardware overwrites what software writes No. CR1 is the control register, the one software writes.

Answer: B. Every peripheral powers up with its clock switched off, to save energy. Until its RCC enable bit is set, "a peripheral with no clock reads back as zero and ignores every write", and nothing reports an error. This is the single most common first-week failure.

The pin multiplexer is the other gate, and it fails just as silently. It cannot make a register read back zero, though. Only the clock gate does that.

Exam line

If a configured peripheral reads back as zero, suspect the clock gate first. Every peripheral powers up unclocked, and writes vanish with no error. A wrong pin owner gives a silent pin; a divisor from the wrong clock gives garbage.
