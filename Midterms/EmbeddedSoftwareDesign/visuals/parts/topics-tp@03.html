Execution and Concurrency: When Two Things Run at Once

The last of four lessons with no code to write. Lessons 00 to 02 gave you the machine, its instructions and the toolchain. This one adds the model "that produces the hardest bugs in this course": what happens when the hardware interrupts your program. Two contexts then share one memory, which brings two hazards with two different fixes. Lessons 05, 06 and 07 apply it to EXTI, timers and the RTOS.

1. Three ways to meet the hardware (slide 1)

"A peripheral finishes when it finishes. Your program has to find out." There are exactly three arrangements, and every embedded design is built from them.

MethodWhat the CPU does while it waitsUse when
Pollingasks "ready yet?" in a loop and does nothing elsethe wait is shorter than the cost of being interrupted
Interruptuseful work until told, then the handler runsevents are rare or must not be missed
DMAuseful work while hardware moves the bytes, "CPU not involved at all"streams of data
  • Left to right, the cost rises in complexity and falls in CPU time.
  • "Polling is not the beginner option." It is the right answer "whenever the wait is shorter than the cost of being interrupted".
  • The course's example is clock setup (L01 slide 13). After writing a new wait state into FLASH->ACR, the code polls until LATENCY reads back the new value. The loop is four instructions (ldr, ands, cmp, bne) and the wait is a few cycles. An interrupt's entry alone, eight registers pushed and a vector read, would cost more.
  • This chip uses all three. Polling depends on the loop coming back and only samples, so it can miss a fast event. An interrupt sees every edge, wanted or not (lesson 05).

2. An interrupt is a hardware-forced function call (slide 2)

"No scheduler, no operating system." The hardware does this between two instructions of whatever was running:

  • Push eight registers onto the stack: R0–R3, R12, LR, PC, xPSR. That is 8 × 4 = 32 bytes, "stacked by the hardware itself".
  • Write the exception number into IPSR, the low bits of xPSR, and load LR with a magic EXC_RETURN value: 0xFFFFFFF9 when main() on MSP was interrupted.
  • Read the vector table. Slot 16 + IRQn holds the handler's address, and the handler runs, always on MSP.
  • Pop and resume. The handler ends with an ordinary bx lr. Branching to EXC_RETURN makes the hardware pop the eight. "Your main program never knows it happened. That is the problem."

Why an ISR can be an ordinary C function. The eight pushed registers are "exactly the set AAPCS lets a function clobber". So there is "no special keyword, no ISR() macro. You simply define a function with the right name and the linker puts it in the vector table."

  • AAPCS (L01 slide 18): any function may destroy R0–R3, R12 and LR (caller-saved) and must restore R4–R11 (callee-saved).
  • The hardware saves the caller-saved set, plus PC (where to resume) and xPSR (the interrupted code's flags). The handler's own prologue saves any of R4–R11 it uses, as in every function.
  • The core has one set of R0–R12. Handler mode has no bank of its own.

Three special registers beside R0–R15 decide how interrupts behave. This deck uses the first two. They have no address; only mrs and msr reach them (L00 slide 3b).

3. Two programs sharing one memory (slide 3)

"This is the whole reason concurrency is a topic." Before interrupts, the program had one thread of control. After, it has two, "and they share every global variable".

  • main() "runs when nothing else does". The handler "runs whenever it likes".
  • "Neither one can see what the other is doing."
  • "Two distinct hazards follow, and they need different fixes. Students routinely apply one fix to the other problem and conclude the language is broken."
HazardShared codeWhat goes wrongThe fixThe other fix instead
1. The compiler (slide 4)while (flag == 0) { } waits for the ISRat -Os the loop reads flag once and never exitsvolatile: every access really happensmasking around the loop: the ISR can never run, so it hangs for sure
2. The mid-update interrupt (slide 5)main() and the ISR both do counter++now and then an increment is losta critical section: ldr, adds, str become indivisiblevolatile: every access already happened, and updates are still lost

4. Hazard one: the compiler does not believe you (slide 4)

while (flag == 0) { }        /* wait for the ISR to set it */
  • The compiler reasons, "correctly by the rules of C": this loop does not modify flag, so flag cannot change, so it reads it once and loops on a register. The result is an infinite loop "that no amount of staring at the source will explain".
  • The as-if rule. "A C compiler is not required to do what you wrote; it is required to produce a program that behaves as if it had, judged only by the observable behaviour the language defines." How many times memory is read, in what order, and whether a variable exists at all, it may change freely. The same rule governs the compiler on your laptop.
  • Why hardware breaks it. "The hardware is an observer the language does not know about." A pin that changes, a status bit that clears when read, another context writing a variable: none of these is observable in C's account. Optimising them away is not misbehaviour.
  • Fix: volatile uint8_t flag; It extends what counts as observable: "every access written must actually happen, all of them, in the order written."
  • "volatile is about the compiler. It is not a lock, it does not make anything atomic, and it does not help with the next slide."
  • CMSIS already declares every peripheral register __IO, which is volatile. Your own shared globals are your job. The classic symptom is "works at -O0, hangs at -Os" (L01 slide 21).

5. Hazard two: the interrupt lands mid-update (slide 5)

"Recall from lesson 01 that touching memory is always three instructions." On a load–store machine counter++ in main() is ldr, adds, str, and an interrupt can land between any two of them.

  • "Two increments happened. The counter went from 5 to 6. One update vanished."
  • volatile does not help: "every access did happen, in order, exactly as written. The problem is that the sequence was not indivisible."
  • The handler did not corrupt main()'s r0. The hardware stacked it on entry and restored it on return (section 2). main() carried on with a value that was already stale.

Four standard words. "These are the standard names, and they are not embedded-specific."

TermDefinition
race conditionthe result depends on the relative timing of two contexts
critical sectionthe region of code that must not be interleaved
mutual exclusionthe guarantee you need over it: at most one context inside at a time
atomica sequence that cannot be observed half-done

"Every concurrent system in computing is built from those four words, whether the two contexts are an ISR and main(), two threads on a laptop, or two processes writing one file."

6. How mutual exclusion is obtained, and this chip's answer (slide 5)

"What changes between systems is only how mutual exclusion is obtained."

ContextsHow you get mutual exclusion
ISR vs main(), one coreturn interrupts off: "the other context cannot run if it cannot start"
two threads, one OSa mutex, "which asks the scheduler not to switch"
two cores"neither of the above works": an atomic read-modify-write instruction is required, ldrex/strex on larger ARM cores, lock cmpxchg on x86
  • "Masking interrupts stops the other context on this core; it does nothing to a second core, which is still running."
  • "A Cortex-M0+ is single-core and has neither, which is exactly why interrupt masking is the right tool here and would be the wrong tool on a phone."
  • A mutex is no help against an ISR. It asks the scheduler not to switch, and the hardware starts an ISR without asking the scheduler.

This chip's answer: a critical section by masking. "Stop interrupts for the three instructions":

__disable_irq();     /* cpsid i : PRIMASK.PM = 1 */
counter++;           /* ldr, adds, str: now indivisible */
__enable_irq();      /* cpsie i : PRIMASK.PM = 0 */
  • Each call is one instruction, and "all either one changes is a single bit, bit 0 of the core register PRIMASK". While PM = 1 no configurable interrupt is taken, whatever its priority. A request that arrives is held pending and taken right after cpsie i.
  • "Keep it short. Every cycle spent with interrupts off is a cycle in which the chip cannot respond to anything."
  • __enable_irq() re-enables unconditionally. Code that may already run masked saves __get_PRIMASK() first and restores it with __set_PRIMASK() (notes, textbook context).

volatile makes accesses real · a critical section makes a sequence indivisible

"The two fixes are not interchangeable. Most concurrency bugs in this course come from using the first where the second was needed."

7. A bug that only appears sometimes (slide 6)

The lost update needs the interrupt to land in a two-instruction window. "On a 48 MHz chip that window is about 40 nanoseconds wide."

one cycle at 48 MHz = 1 / 48 000 000 s = 20.8 ns
window = 2 cycles × 20.8 ns = 41.7 ns, about 40 ns

1 000 interrupts/s  → roughly once every 7 hours:     1 000 × 3 600 × 7 = 25.2 million interrupts
10 000 interrupts/s → roughly once every 40 minutes: 10 000 × 60 × 40 = 24 million interrupts
ten times the rate, ten times as often:               7 h / 10 = 42 min
  • Each interrupt is one more draw on where main() happens to be. Only a draw inside the window loses an update, about one in 25 million here, so the failure rate is in step with the interrupt rate.
  • "They survive your testing, they survive the demo, and they appear in the field. You cannot find them by running the program more." More running only resamples the timing. "You find them by reasoning about which variables are shared, and protecting those."
  • "A useful discipline: for every global, write down which contexts touch it. If the answer is more than one, it needs volatile, and probably a critical section too."

8. Not everything needs protecting; tearing (slide 7)

"Turning interrupts off has a cost, so be precise about when it is needed."

SituationSafe?Why
ISR writes a uint8_t, main only reads itYessingle aligned access, one writer
ISR sets a flag, main reads and clears itUsuallybut the clear is read-modify-write
main does counter++, ISR also incrementsNothe lost update of section 5
main reads a uint64_t the ISR writesNomore than one bus access; you can read half
Either side touches a multi-field structNothe reader can see it half-updated
  • "The pattern: a single aligned word written by exactly one context is safe. Everything else needs thought." Such a word still needs volatile, so that main() really reads it each time (guide P12).
  • Tearing is the failure in rows four and five. "A reader that needs two bus accesses to collect one logical value can be interrupted between them and walk away with half of the old value and half of the new: a number that was never stored by anybody."
  • The same hazard makes a 64-bit counter unsafe on a 32-bit machine "in any language, on any operating system", and makes a shared struct need protecting even when each field is small.
  • Even volatile uint64_t compiles to two separate ldrs. The fix is to copy the value inside a critical section.
uint64_t ticks goes 0x00000000_FFFFFFFF → 0x00000001_00000000 in the ISR
low word first:  low = 0xFFFFFFFF (old), ISR runs, high = 0x00000001 (new)
                 → 0x00000001_FFFFFFFF = 8 589 934 591, about double the real count
high word first: high = 0x00000000 (old), ISR runs, low = 0x00000000 (new)
                 → 0x00000000_00000000, the counter seems to jump back to 0
masked copy:     0x00000000_FFFFFFFF or 0x00000001_00000000, both real values

9. Priority: which interrupt wins (slide 8)

"Several peripherals can want attention at once. The NVIC decides, by priority, and it can also let a more urgent interrupt preempt a handler already running."

  • Each interrupt's priority is one byte in the NVIC's IPR registers, four to a word. "This chip implements only the top two bits of each byte, so there are just four levels (0 is the most urgent)."
  • IRQ n lives in IPR[n / 4], byte n mod 4, bits 8(n mod 4)+7 : 8(n mod 4)+6. The byte is the level shifted left by 6: 0x00, 0x40, 0x80, 0xC0.
  • Equal priorities do not preempt each other. A second request at the same level waits until the running handler returns (lesson 06).
  • Handlers must be short. "Anything slow in a handler delays every interrupt of equal or lower priority." The usual shape is to set a flag or push to a buffer, return, and let main() do the work.
  • Preemption multiplies the sharing problem. "It is not only main-versus-ISR any more; it is ISR-versus-ISR."

"The vocabulary here is shared with operating-system scheduling, because it is the same problem."

TermMeaning
preemptionone runnable context displacing another mid-execution

priority inversiona high-priority task waits on something a low-priority one holds; Mars Pathfinder kept resetting on the surface in 1997 for this reason (lesson 07)

What you should be able to say (slide 10)

  • 1. The three ways to meet hardware, and a case for polling. Polling, interrupt, DMA. Polling is right whenever the wait is shorter than the cost of being interrupted, for example the few cycles until FLASH->ACR reads back a new wait state.
  • 2. Why an ISR here is an ordinary C function. On entry the hardware itself stacks R0–R3, R12, LR, PC, xPSR, exactly the registers AAPCS lets a function clobber, and the prologue saves any R4–R11 it uses. The correct name puts the address in the vector table, and bx lr with EXC_RETURN unstacks the frame.
  • 3. What volatile prevents, and one thing it does not do. It stops the compiler caching, merging, deleting or reordering the accesses you wrote: every access happens, in order. It does not make anything atomic and it is not a lock, so it cannot stop a lost update.
  • 4. The sequence that loses an update. main(): ldr reads 5. Interrupt: the handler's ldr reads 5, adds gives 6, str writes 6. Back in main(): adds gives 6, str writes 6. Two increments, and the counter went from 5 to 6.
  • 5. A single aligned uint8_t, written only by the ISR, read by main: critical section? No. It is one indivisible access with one writer, so a read returns the old value or the new one, never a mix. It still needs volatile so that main really reads it.
  • 6. Why handlers must be short. Anything slow in a handler delays every interrupt of equal or lower priority and adds to its latency. Set a flag or push to a buffer, return, and let main() do the work.
  • 7. Works for hours, then misbehaves once. A race condition. The interrupt must hit a window of about 40 ns, so a failure is a rare timing coincidence, and running more only resamples the timing. Find it by listing which contexts touch each global and protecting the shared ones.
  • 8. The as-if rule, and why hardware breaks its assumption. The compiler need only produce a program that behaves as if it did what you wrote, judged by the observable behaviour C defines. Hardware is an observer C does not know about: a changing pin, a status bit that clears when read, an ISR writing a variable.
  • 9. Four definitions without ARM. Race condition: the result depends on the relative timing of two contexts. Critical section: a region of code that must not be interleaved. Mutual exclusion: at most one context inside it at a time. Atomic: cannot be observed half-done.
  • 10. __disable_irq() on a dual-core chip. It masks interrupts on its own core only; the second core keeps running its own ldr, adds, str at the same time. An atomic read-modify-write instruction replaces it: ldrex/strex on larger ARM cores, lock cmpxchg on x86.
  • 11. Tearing, and its two rows. A reader that needs two accesses for one value is interrupted between them and gets half old, half new, a value nobody stored. Rows 4 (main reads a uint64_t the ISR writes) and 5 (a multi-field struct).

General idea vs this chip

Shaded rows are the key contrasts that guide §2 and §7 assign to this lesson. The other rows are the deck's own "general idea / this chip's answer" sections.

Exam focus
  • Polling wins when the wait is shorter than the cost of being interrupted: the four-instruction FLASH->ACR LATENCY wait. A rare or must-not-miss event needs an interrupt; a 2 KB stream needs DMA.
  • Entry stacks 8 registers, R0–R3, R12, LR, PC, xPSR = 32 bytes: the AAPCS caller-saved set plus PC and xPSR. LR = 0xFFFFFFF9; bx lr unstacks. In the TIM3 handler (IRQ 16) IPSR = 32 = 0x20. A misspelt handler name compiles, links and does nothing.
  • A plain uint8_t flag in while (flag == 0) { } works at -O0 and hangs at -Os: read once, by the as-if rule. Fix: volatile, which is not a lock and not atomic.
  • Lost update: counter 5, the ISR increments between main's ldr and str, result 6 (should be 7). From 40 with an ISR doing += 3: 41, not 44. The fix is __disable_irq(); counter++; __enable_irq(); = cpsid i / cpsie i = PRIMASK bit 0.
  • Mutual exclusion by contexts: ISR vs main on one core, mask; two threads, a mutex; two cores, ldrex/strex or lock cmpxchg. The M0+ is single-core and has neither instruction.
  • Window = 2 cycles at 48 MHz = 41.7 ns. 1 000 interrupts/s gives roughly once every 7 h; 10 000/s about every 40 min (ten times the rate, ten times as often). It is a race condition, and more testing will not find it.
  • Safe without a critical section: one aligned word or byte with one writer (still volatile). Tearing: a uint64_t read low then high across an increment from 0x00000000_FFFFFFFF gives 0x00000001_FFFFFFFF; high first gives 0.
  • Priority: 4 levels from the top 2 bits of each IPR byte, 0 most urgent, byte = level << 6. IRQ 1 is in IPR[0] bits 15:14; level 2 is 0x80. PRIMASK holds back every level, 0 included, so the longest critical section sets the worst-case latency.
