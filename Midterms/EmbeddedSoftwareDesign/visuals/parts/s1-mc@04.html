Question 15 · L04, Reset vector

The first eight bytes of a firmware image, from 0x08000000 upward, are 00 30 00 20 1D 02 00 08. At reset the core loads SP and PC from them before any instruction runs. What is the initial SP, and at which address is the first instruction of Reset_Handler?

  1. A SP = 0x20003000, Reset_Handler at 0x0800021C Correct. Each word reads right to left, and bit 0 of 0x0800021D is the Thumb bit.
  2. B SP = 0x20003000, Reset_Handler at 0x0800021D No. Bit 0 is the Thumb bit, not part of the address. Instructions sit at even addresses.
  3. C SP = 0x00300020, Reset_Handler at 0x1D020008 No. That reads the bytes big-endian. ARM is little-endian.
  4. D SP = 0x0800021D, Reset_Handler at 0x20003000 No. That swaps the words. Word 0 is the stack pointer, word 1 the reset vector.

Answer: A. ARM is little-endian, so the byte at the lowest address is the least significant one, and each group of four bytes reads right to left. Word 0 is 0x20003000, the top of the 12 KB RAM, and the core loads it into SP. Word 1 is 0x0800021D, and the core loads it into PC.

Bit 0 of a code address is the Thumb bit. The core reads it as "this target is Thumb code", not as part of the address, so Reset_Handler's first instruction is at 0x0800021C. Because the hardware sets SP itself, that first instruction already has a valid stack, and Reset_Handler can be written in C.

Exam line

At reset the core loads word 0 of FLASH into SP and word 1 into PC before any instruction runs. Each word reads right to left, and bit 0 of a handler address is the Thumb bit, so 0x0800021D means code at 0x0800021C.

Question 16 · L04, Linker symbols

link.ld places .data from 0x20000000 up to 0x20000064, and startup.c declares the two boundary symbols as below. Which line stores the size of .data in bytes, 100, in n?

extern uint32_t _sdata, _edata;   /* defined in link.ld */
  1. A uint32_t n = _edata - _sdata; No. Without & each name reads the four bytes stored at that address. It compiles cleanly and gives garbage.
  2. B uint32_t n = &_edata - &_sdata; No. Subtracting two uint32_t * pointers counts words: 100 / 4 = 25.
  3. C uint32_t n = (uintptr_t)&_edata - (uintptr_t)&_sdata; Correct. Two addresses as integers: 0x20000064 − 0x20000000 = 0x64 = 100.
  4. D uint32_t n = (uintptr_t)_edata - (uintptr_t)_sdata; No. The cast comes after the read, so this is A again: memory contents, not addresses.

Answer: C. The linker creates no storage for _sdata or _edata. It creates a symbol whose value is the address. extern uint32_t _sdata; is "a polite lie told to the compiler" so that &_sdata has a type, and the rule is that a linker symbol is only ever used with &.

C takes both addresses, turns them into integers and subtracts: 0x20000064 − 0x20000000 = 0x64 = 100 bytes. A and D read whatever words happen to live at those addresses. B uses the right addresses, but pointer subtraction divides by sizeof(uint32_t), so it gives 25.

Exam line

A linker symbol is only ever used with &. &_sdata is the address the linker chose; _sdata alone is the four bytes that happen to live there, and it compiles cleanly.

Question 17 · L04, Flash wait states

A student swaps the two halves of SystemInit(), so the clock is raised before the flash wait state is set, as below. It builds with no warnings. What happens on a real chip?

RCC->CR &= ~RCC_CR_HSIDIV;                 /* divide by 1 -> 48 MHz */
while (!(RCC->CR & RCC_CR_HSIRDY)) { }
FLASH->ACR = (FLASH->ACR & ~FLASH_ACR_LATENCY) | FLASH_ACR_LATENCY_0;
while ((FLASH->ACR & FLASH_ACR_LATENCY) != FLASH_ACR_LATENCY_0) { }
SystemCoreClock = 48000000UL;
  1. A Nothing changes, because the compiler moves the FLASH->ACR write back in front of the clock switch No. Register accesses are volatile, and the compiler keeps them in program order.
  2. B For a while the CPU runs at 48 MHz with zero flash wait states, so it can fetch an instruction that is not ready and hang with no error, somewhere unrelated to the bug Correct. Wait states go up before the frequency.
  3. C The chip stays at 12 MHz, because HSIDIV cannot change while LATENCY is 0 No. Nothing in hardware ties the two fields together. The divider changes at once.
  4. D The clock switch raises a HardFault, and the fault handler restores 12 MHz and carries on No. Nothing detects the mistake, and HardFault_Handler is the weak Default_Handler, an infinite loop.

Answer: B. The STM32C0 wakes at 12 MHz, HSI48 ÷ 4. Flash memory cannot be read as fast as the CPU runs at 48 MHz, so it needs one wait state. Slide 16 sets LATENCY first, waits until it reads back, and only then clears HSIDIV.

In the swapped order the clock is already 48 MHz while LATENCY is still 0. The instructions that follow, the HSIRDY loop and the FLASH->ACR write, are themselves fetched from flash in that window. The CPU can fetch an instruction that is not ready yet, and the part hangs with no error, somewhere that has nothing to do with the bug.

Exam line

Wait states go up before the frequency, and come down after it. In the wrong order the part hangs with no error, somewhere that has nothing to do with the bug.
