Question 31 · L08, BRR and byte time

USART2 is clocked at 48 MHz and must run at 38 400 baud, 8N1. Which BRR value is right, and how long does the receive handler have to read RDR after a byte arrives, before the next byte overwrites it?

  1. A BRR = 1250; about 208 µs No. 208 µs is 8 bits. The start and stop bits are on the wire too, so a byte is 10 bits.
  2. B BRR = 313; about 260 µs No. 12 000 000 / 38 400 = 312.5 is the value for the 12 MHz reset clock. At 48 MHz it would send four times too fast.
  3. C BRR = 1250; about 26 µs No. 26 µs is one bit. The next byte needs all 10 of its bits before it lands in RDR.
  4. D BRR = 1250; about 260 µs Correct. 48 000 000 / 38 400 = 1250 clocks per bit, and 10 bits / 38 400 per second ≈ 260 µs per byte.

Answer: D. BRR counts clocks per bit, so BRR = f / baud = 48 000 000 / 38 400 = 1250, an exact division.

The UART holds one received byte. The next byte needs one whole byte time to arrive, and 8N1 puts 10 bits on the wire per byte (start, 8 data, stop): 10 / 38 400 s ≈ 260 µs. If RDR is still unread when that byte completes, it is lost and ORE is set.

Exam line

BRR = f / baud (clocks per bit), and one 8N1 byte takes 10 / baud. At 48 MHz and 38 400 baud: BRR = 1250, and the handler has about 260 µs to read RDR.

Question 32 · L08, NMEA XOR checksum

host.py --frame "PING" prints the NMEA-style frame for the body PING. In ASCII, P = 0x50, I = 0x49, N = 0x4E, G = 0x47. What does it print?

  1. A $PING*2E No. That adds the bytes: 50 + 49 + 4E + 47 = 12E, low byte 2E. The checksum is an XOR.
  2. B $PING*34 No. That XORs in the $ (0x24) as well. The checksum covers only the bytes between $ and *.
  3. C $PING*10 Correct. 50 ^ 49 = 19, ^ 4E = 57, ^ 47 = 10.
  4. D $PING*16 No. 16 is 0x10 written in decimal. The frame carries two hex digits.

Answer: C. An NMEA 0183 frame is $ body * checksum, and the checksum is the XOR of every byte of the body, written as two hex digits. Neither $ nor * is included.

XOR works bit by bit, so do it in hex or in binary: 50 ^ 49 = 19, 19 ^ 4E = 57, 57 ^ 47 = 10. The frame is $PING*10. Lab Part 1 asks for exactly this sum by hand, checked with --frame.

Why the other options are wrong

Option A
A sum, not an XOR

Adding carries between bits. XOR does not.

50 + 49 + 4E + 47 = 12E → low byte 2E
Option B
The $ was included

The body is the text between $ and *.

24 ^ 10 = 34
Option D
Decimal, not hex

The right value printed in base 10. proto_check() would read 16 as 0x16 and reject the frame.

0x10=16but*10
Exam line

Checksum = XOR of every byte between $ and *, as two hex digits: PING gives 50 ^ 49 ^ 4E ^ 47 = 10, so $PING*10.

Question 33 · L08, Clearing ORE

A student's USART2_IRQHandler (below) has no ORE branch, so it never writes ICR. Typing works until, once, interrupts stay masked for longer than one byte time: a byte is overwritten and ORE is set. What happens from then on?

void USART2_IRQHandler(void)
{
    uint32_t isr = USART2->ISR;
    if (isr & USART_ISR_RXNE_RXFNE) {
        uint8_t c = (uint8_t)USART2->RDR;
        os_queue_put_from_isr(&rx_queue, &c);
    }
    /* TX branch as in the lesson */
}
  1. A Nothing visible: reading RDR in the handler clears ORE together with RXNE No. Reading RDR clears RXNE only. ORE has its own clear bit in ICR.
  2. B Reception stops: ORE stays set, and only writing 1 to ORECF in ICR clears it Correct. This is the slide 14 row: forget to clear ORE and reception stops after the first overrun.
  3. C One byte is lost and reception carries on: ORE clears itself when the next byte arrives No. No flag on this chip clears itself. One lost byte is what the lesson's handler gives, because it writes ICR.
  4. D Reception resumes after the board's next reply: writing TDR clears ORE No. Writing TDR clears TXE, the transmit side's flag. It does not touch ORE.

Answer: B. On this chip ORE is cleared by writing 1 to a different register: USART2->ICR = USART_ICR_ORECF;, bit 3 of ICR for bit 3 of ISR. Nothing else clears it. Reading RDR clears RXNE and writing TDR clears TXE.

While ORE is set it blocks further reception, so the board hears nothing after the first overrun. The comment in uart.c adds that, with RXNEIE set, the stuck flag also keeps the interrupt asserted. The lesson's handler writes ICR, counts the overrun and loses one byte.

Exam line

ORE clears only by writing 1 to ORECF in a different register, ICR. Forget it and reception stops after the first overrun. Reading RDR clears RXNE; writing TDR clears TXE.
