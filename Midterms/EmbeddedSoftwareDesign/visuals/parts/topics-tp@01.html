Instruction Set: What the Processor Actually Does

Lesson 00 put a CPU, memory and peripherals on one bus, and made a register an address with a side effect. This lesson reads what the CPU can actually do with an address: the Thumb instructions that arm-none-eabi-gcc -Os emitted for the STM32C031C6. Every listing is real output from the course's spike build, and you only ever have to read it.

1. "You will not write assembly. You will read it." (slide 1)

Four times a term, something goes wrong in a way C cannot explain:

  • the debugger stops somewhere with no source line;
  • a variable changes when nothing wrote to it;
  • a loop that should take 3 µs takes 30;
  • the optimiser deletes code you needed.

Each one is answered in one place, "the instructions the compiler actually emitted". Reading them is a diagnostic skill, like reading a stack trace.

2. Thumb, the only instruction set this chip has (slide 2)

  • ARM designs two instruction sets. A phone's Cortex-A holds both and switches between them as it runs. "A Cortex-M has no ARM state to switch to." Thumb is the only thing its decoder understands.
  • The general idea is code density, how much program you get per byte of memory. Wide fixed-length instructions decode trivially and waste space. Variable-length ones (x86 runs from 1 to 15 bytes) pack tightly, and the decoder must first work out where the next instruction starts.
  • Most RISC families settled on a compressed instruction set, a narrow encoding of the common cases beside the full-width one. Thumb is ARM's, MIPS16 was MIPS's, and RISC-V calls its version the "C" extension. "Memory, not arithmetic, is what a small system runs out of first."
  • The build shows it. Main.map pulls in .../thumb/v6-m/nofp/libgcc.a(_udivsi3.o). thumb is the instruction set, v6-m the architecture, nofp no floating-point unit. GCC ships one copy of its runtime per combination.

4. Load–store vs register–memory (slide 4)

Every instruction set answers one question early and never revisits it. May an arithmetic instruction name a memory address? Both fragments below increment the same counter.

add  dword [counter], 1        ; x86, register–memory: one instruction, memory += 1

ldr   r0, [r1]                 @ Cortex-M, load–store: the same job in three
adds  r0, r0, #1
str   r0, [r1]
Register–memoryLoad–store
Found inx86, 68000, S/360ARM, RISC-V, MIPS, AVR
An ALU operand may bea register or memorya register only
Memory is touched bymost instructionsldr / str, and nothing else
Instruction lengthvariable, x86 is 1 to 15 bytesfixed, Thumb is 2 or 4
counter++ costs1 instruction3 instructions
...and bus accesses22
  • Read the last two rows together. "Load–store costs instructions, not memory traffic." The bus does identical work either way.
  • What the extra instructions buy is a fixed-length encoding, a decoder that never asks how long an instruction is before it finds the next one, and a pipeline whose stages are the same depth for every opcode. A 48 MHz part with no cache is built out of exactly those. This is most of what "RISC" and "CISC" ever meant. (The VAX went further than x86: both operands could be memory.)
  • The AVR was load–store too, with one deliberate crack. sbi PORTB, 0 set a bit in a low I/O register in a single uninterruptible instruction. Cortex-M0+ has no sbi. Every peripheral register is ordinary memory. The convenience comes back as hardware, GPIO's set/reset register BSRR (lesson 05).
  • So setting one bit in a peripheral register is never one instruction here. It is a read, a modify and a write: three instructions, two bus events, and a gap in between that belongs to whatever the processor does next (lesson 03).

Crossing the boundary, on this chip:

InstructionMovesC equivalent
ldr r0, [r1]32 bits, memory → registerx = *p;
str r0, [r1]32 bits, register → memory*p = x;
ldrb / strb8 bitschar, uint8_t

movs is the one that never touches memory. Everything else operates on what ldr brought in. An int16_t loaded with ldrh loses its sign; it needs ldrsh.

These operate on registers only, and almost all of them carry an s.

  • There is no divide instruction on Cortex-M0+. a / b becomes a call to the library routine __aeabi_uidiv, which is why it is dramatically slower than multiply. The spike links 080000b4 <__udivsi3> because one line of C divided, so the .map file shows libgcc.a(_udivsi3.o). Cortex-M3 and above have sdiv and udiv in hardware.
  • Why the s everywhere? On the 16-bit encodings the M0+ uses, most data-processing instructions always update the flags. There is no room in the encoding for a choice, so the compiler writes adds, not add. On M3 and above the 32-bit encodings let you pick.

  • Shifting right is only a division if you pick the shift that matches your signedness. "Getting it wrong turns a small negative number into a very large positive one."

6. Flags and conditional branches (slide 7)

  • The general idea: how does a machine remember the result of a comparison? Condition-code machines keep a few flag bits in a status register. A compare sets them, a later branch reads them, and the two are coupled by invisible state. ARM, x86, AVR and the 68000 work this way.
  • Compare-and-branch machines have no flags register. RISC-V writes blt a0, a1, label, the comparison and the branch in one instruction, and MIPS does the same.
  • Flags buy density: one cmp can feed several branches. They cost a hidden dependency that every instruction in between must preserve, which is awkward for a deeply pipelined or out-of-order machine. That is the main reason newer designs dropped them.
  • This chip is a condition-code machine. "cmp is a subtraction that throws the answer away and keeps the flags. tst is an AND that does the same."
  • The four flags are the top of APSR, the flags view of xPSR from lesson 00: N bit 31 negative, Z bit 30 zero, C bit 29 carry/borrow, V bit 28 signed overflow.

"blt and bcc are not interchangeable." The compiler picks one based on whether your variable is signed. A comparison that behaves oddly only at the extremes of its range is very often a signedness bug, and the disassembly shows it at once.

7. Branches, calls and returns (slide 8)

The general idea: where does a call put the return address? Two answers.

Where the return address goesMachines
Stack-basedcall pushes it to memory; ret pops itx86, 68000, AVR (rcall / ret)
Link registerthe call writes it to a register; return branches to that registerARM, RISC-V (ra), MIPS ($ra), PowerPC
  • A link register makes a leaf call, one that calls nothing else, touch no memory at all: bl in, bx lr out. Leaf functions on this chip often have no prologue.
  • The cost is that LR holds exactly one return address. A function that calls anything must save it before it is overwritten. "That is precisely what push {lr} in every non-leaf prologue is for."
  • pop {r4, pc} pops the saved LR straight into PC, and writing PC is a branch. It replaces pop {r4, lr} followed by bx lr, one instruction saved on every function that touches the stack. The spike's _write has both halves: b5f0 push {r4, r5, r6, r7, lr} ... bdf0 pop {r4, r5, r6, r7, pc}.

8. Addressing modes, and how far an offset reaches (slides 9–10)

ldr and str need an address, and there are only a few ways to build one. Each matches a C construct.

FormExampleIn CEncoding
registerldr r0, [r1]*p16-bit
immediate offsetldr r0, [r4, #28]s->field16-bit, small offsets
register offsetldrb r6, [r1, r3]buf[i]16-bit
SP-relativeldr r0, [sp, #8]a local variable16-bit
PC-relativeldr r2, [pc, #44]a big constant16-bit
scaled registerldr r0, [r1, r2, lsl #2]arr[i] for int32-bit, M3+ only

post-indexedldr r0, [r1], #4*p++32-bit, M3+ only
  • [r4, #28] is base + a fixed offset known at compile time, USART2->ISR. [r1, r3] is base + a variable index computed at run time, buf[i]. [sp, #8] uses the stack pointer as the base, a local.
  • "A peripheral register access is literally a struct field access": base register plus constant offset. That is the whole trick the CMSIS headers use.

A 16-bit instruction has little room left for an offset once it has encoded the opcode and two registers. Five bits for the opcode, three for each register, five for the offset, stored divided by the access size.

InstructionOffset fieldReaches
ldr r0, [r1, #n]5 bits, scaled by 40 to 124 bytes (31 × 4)
ldrh r0, [r1, #n]5 bits, scaled by 20 to 62 bytes (31 × 2)
ldrb r0, [r1, #n]5 bits, unscaled0 to 31 bytes
ldr r0, [sp, #n]8 bits, scaled by 40 to 1020 bytes (255 × 4)
  • Offsets are always positive. There is no [r1, #-4] in 16-bit Thumb. To step backwards the compiler adjusts the base register first.
  • A far field costs an extra instruction. Offset 28 is free (80002d0: ldr r6, [r4, #28]). A field beyond 124 bytes cannot be encoded, so the compiler emits an add to move the base, then loads. That is why a large peripheral struct generates visibly worse code at its far end, and why a driver that keeps a pointer to the register it hammers can be measurably faster.
  • Cortex-M3 and above lift most of this with 32-bit encodings: offsets up to 4095 bytes, negative offsets, scaled register offsets and auto-increment. Same source, denser output.

9. A real function: one C line, read–modify–write (slide 11)

SystemInit() takes the chip from its 12 MHz reset state to 48 MHz. Its first line of C and what the processor got:

FLASH->ACR = (FLASH->ACR & ~FLASH_ACR_LATENCY) | FLASH_ACR_LATENCY_0;

0800022c <SystemInit>:
 800022c:  2007   movs  r0, #7           ; r0 = 0x7, the LATENCY mask
 800022e:  2301   movs  r3, #1           ; r3 = 0x1, the new value
 8000230:  4a0b   ldr   r2, [pc, #44]    ; r2 = 0x40022000, FLASH base
 8000232:  6811   ldr   r1, [r2, #0]     ; LOAD    FLASH->ACR
 8000234:  4381   bics  r1, r0           ; MODIFY  clear the field
 8000236:  430b   orrs  r3, r1           ; MODIFY  set the new value
 8000238:  6013   str   r3, [r2, #0]     ; STORE   back to FLASH->ACR
  • ldr, bics, orrs, str are the load / modify / store of slide 4, from a single line of C. Of those four, only ldr and str touch FLASH->ACR on the bus.
  • "bics is the & ~, orrs is the |. That correspondence is the whole reason to read disassembly."
  • The field being changed is LATENCY, bits 2:0 of FLASH_ACR. r0 = 0x7 is its mask, for bics. r3 = 0x1 is the new value, for orrs.

10. Literal pools and a four-instruction polling loop (slides 12–13)

  • Why does ldr r2, [pc, #44] load from an address computed from the program counter? movs r0, #7 fits: its 8-bit immediate holds 0 to 255. 0x40022000 is 32 bits and cannot possibly fit in a 16-bit instruction.
  • So the compiler parks the constant in a literal pool just past the code and loads it PC-relative. "This is a general consequence of fixed-width encoding, not an ARM quirk."
MachineHow a 32-bit constant reaches a register
x86the instruction simply grows; the constant is embedded, variable length
ARM / Thumba literal pool near the code, loaded PC-relative
RISC-Vbuilt in two halves, lui then addi
AArch64built in halves too, movz then movk

The pool sits at the end of the function, and every peripheral address the function touches is listed in plain sight:

 8000260:  40022000   .word  0x40022000    ; FLASH
 8000264:  40021000   .word  0x40021000    ; RCC
 8000268:  ffffc7ff   .word  0xffffc7ff    ; ~(7 << 11), the HSIDIV mask
 800026c:  20000000   .word  0x20000000    ; &SystemCoreClock, in SRAM
 8000270:  02dc6c00   .word  0x02dc6c00    ; 48000000
  • 0x02dc6c00 is 48,000,000. The clock speed you assigned in C sits in flash as a number, and it is written to 0x20000000, the very bottom of SRAM, where lesson 02's linker puts SystemCoreClock.
  • 0xffffc7ff is all ones except the three HSIDIV bits 13:11 of RCC->CR. An ands with it clears exactly that field.

Lesson 00 described polling as "keep asking". Here it is, waiting for the flash controller to acknowledge the new wait state:

 800023a:  6813   ldr   r3, [r2, #0]    ; read FLASH->ACR
 800023c:  4003   ands  r3, r0          ; isolate the LATENCY field
 800023e:  2b01   cmp   r3, #1          ; is it what we asked for?
 8000240:  d1fb   bne.n 800023a         ; no -> go back and read again
  • The branch target 800023a is the load. That is the loop: read, test, branch back. It costs the CPU every cycle until the hardware agrees.
  • The branch is two bytes. d1fb holds the condition 0001 (NE) and a signed offset in halfwords, 0xFB = −5, counted from PC + 4.
  • No volatile is visible in the machine code. Without it in the C source, the compiler would have read FLASH->ACR once, cached it in r3, and looped forever (block 15).
literal:  address = Align(instruction + 4, 4) + 4 × imm8
          0x8000230: Align(0x8000234, 4) + 4 × 11 = 0x8000260  → 0x40022000
branch:   target  = instruction + 4 + 2 × imm8   (imm8 signed)
          0x8000240: 0x8000244 + 2 × (−5) = 0x800023a

11. A whole C function, line by line (slides 14–15)

_write() makes printf reach the serial port. Eleven lines of C:

static void uart2_putc(char c)
{
    while (!(USART2->ISR & USART_ISR_TXE_TXFNF)) { }
    USART2->TDR = (uint8_t)c;
}

int _write(int fd, const char *buf, int len)
{
    (void)fd;
    for (int i = 0; i < len; i++) {
        if (buf[i] == '\n') { uart2_putc('\r'); }
        uart2_putc(buf[i]);
    }
    return len;
}

And what the processor got. Nothing in it is exotic, and every instruction is one you have now met.

In the codeIs
#10'\n'

#128USART_ISR_TXE, bit 7

(void)fd; became nothing at all. r0 arrived holding fd and is reused at 80002bc for the TXE mask. Every for loop you write looks like this: initialise, compare, conditional branch to the body, increment, unconditional branch back.

  • Hoisting. #128, #13 and the USART2 base are set up once, before the loop, although the C mentions them inside it. Anything that cannot change is lifted out.
  • Inlining, twice. uart2_putc is nowhere in the machine code. Its body appears once for '\r' and again for the character, so _write contains no bl at all.
  • Rotation. The for test sits at the top, the exit is the fall-through, and return len lands in the middle at 0x080002c6. "Address order is not source order", which is why a debugger stepping through optimised code appears to jump around.
  • buf[i] is loaded twice, at 80002ca and 80002d8. A char object is allowed to alias anything, so as far as the standard knows, the store to USART2->TDR might have changed buf[i]. Block 15 is the same rule from the other side.

12. Thumb-1, Thumb-2, and the six 32-bit instructions (slides 16–17)

  • The second column of the disassembly (2007, 4a0b, 6811) is four hex digits, two bytes. Almost every instruction on this chip is 16 bits wide, which is why 32 KB of flash holds a useful program at all.
  • Every 16-bit format spends its top bits on the opcode, three bits on each register it names, and whatever is left on a constant. Three bits per register is why most 16-bit forms reach only R0–R7.
  • Thumb-1 (1994) has 16-bit encodings and nothing else. Thumb-2 (2003, ARMv6T2) keeps every 16-bit encoding and adds 32-bit ones beside them in the same stream. There is no mode switch. The decoder reads a halfword, and if its top five bits are 11101, 11110 or 11111, a second halfword belongs to it.

Every core in that table is Thumb-only. Not one of them can execute an ARM instruction. The only question is which Thumb. The M0+ has six 32-bit instructions, the only ones on this chip:

blcall a function anywhere in the address space
mrs / msrread and write the special registers (PRIMASK, CONTROL, PSP)
dsb / dmb / isbmemory and instruction barriers
  • Everything else an M0+ executes is two bytes. 800028a: f7ff ffcf bl 800022c <SystemInit> in Reset_Handler is four bytes, because a 16-bit branch reaches only about ±2 KB and a call has to reach anywhere. "That is the whole rule for when Thumb widens: not when 32 bits would be convenient, but when 16 bits cannot do the job at all."
  • .n and .w. .n is narrow, 16 bits; .w is wide, 32. On this chip there is nothing to choose, and bne.n is only objdump being explicit. On M3 and above the assembler picks the smallest encoding that reaches, and .w forces the wide one.
  • The s on every adds, the missing divide, the 5-bit positive-only offsets, the eight reachable registers and the literal pools full of addresses are all Thumb-1 limits. The same C on a Cortex-M4 gives add that leaves the flags alone, sdiv instead of a library call, ldr r0, [r1, #2000] in one instruction, and far fewer literal pools, because movw / movt build a 32-bit constant inline.

13. Who owns which register: the calling convention (slide 18)

  • The general idea is an ABI. Sixteen registers, one CPU, and every function wanting all of them. A calling convention, part of the Application Binary Interface, says where arguments go, where the result comes back, and which registers a function may destroy. Every platform has one: SysV AMD64 on Linux, the RISC-V and MIPS conventions, and ARM's AAPCS here.
  • Caller-saved (volatile, scratch) registers may be destroyed by a function, so the caller saves anything it still wants. Callee-saved (non-volatile) registers must be given back untouched, so a function saves them on entry and restores them on exit.
  • It exists because of separate compilation. Your C has to call a library compiled years ago by a different compiler, possibly written in assembly, and neither side can see the other's source.
RegistersAAPCS role
R0 R1 R2 R3arguments in, result out (R0); caller-saved
R4 ... R11callee must preserve
R12 SP LR PCscratch and special

Now _write explains itself. Its arguments arrived in r0, r1, r2 (the file descriptor, the buffer, the length). It returns len by putting it in r0 (movs r0, r2). It pushes r4–r7 "because AAPCS says it must give them back unchanged", since it wanted them for the USART base, the '\r' and the characters. The push stores the lowest register at the lowest address:

14. The Thumb bit: odd addresses that are not bugs (slides 19–20)

The first sixteen bytes of Main.hex, the file that would be flashed:

  • Reset_Handler is at 0x08000274, an even address. The vector says 0x08000275. "The low bit is set on purpose": on this processor it means "the code at this address is Thumb code". Bits 31:1 are the address, bit 0 is T. Every function pointer on the chip is odd.
  • On a Cortex-A the bit answers a real question, which instruction set a branch is landing in. On a Cortex-M the answer is always Thumb, "so the bit is always 1 and the hardware still insists on being told".
  • Clear that bit and the CPU faults immediately on reset. A vector table full of even addresses is a dead chip, and a common hand-written-assembly mistake.

LR is odd too. A real call and the instruction it must come back to:

 800028a:  f7ff ffcf   bl  800022c <SystemInit>
 800028e:  f000 fb31   bl  80008f4

  • bx lr, and pop {r4, r5, r6, r7, pc} which is the same branch in disguise, read bit 0 as the instruction set to resume in, then branch to the address with that bit cleared. "Nothing is skipped and nothing is off by one."
  • One bit does the job of a processor mode flag, so it rides inside the address. That is also why pop {pc} can return at all: the Thumb bit was saved with LR and comes back with it.
  • When it bites. Branch to an address with bit 0 clear and the core faults: it has been told to execute ARM instructions, and it has none. A HardFault whose stacked PC or LR is a sensible-looking even address usually means a function pointer that was computed rather than assigned, or assembly that returned with mov pc, lr instead of bx lr.
  • Inside an exception handler LR is not a return address at all. The core loads a magic EXC_RETURN value there (0xFFFFFFF9, 0xFFFFFFFD), and branching to it unstacks the frame that lesson 03 draws.

15. What the compiler is allowed to do to you (slide 21)

  • The compiler's contract is to preserve the observable behaviour of your program "as defined by the C standard, which has never heard of your peripheral". Three reads you wrote may become one read cached in a register at -Os. It may also hoist, inline and reorder, as block 11 showed.
  • For ordinary variables this is exactly what you want. For a status register it is catastrophic, and it produces the classic symptom: code that works at -O0 and hangs at -Os.
  • The keyword that forbids it is volatile: every access must really happen, in order. CMSIS, the Common Microcontroller Software Interface Standard (ARM's vendor-neutral headers for Cortex-M), has already applied it. Every register in stm32c031xx.h is declared __IO, which is simply volatile. "You inherit the protection; you should still know why it is there."

What you should be able to say (slide 22)

  1. 1How many distinct instructions make up 80% of real firmware? About 13 mnemonics (79.6%), out of 51 distinct ones in the 2100-instruction spike. Move, load/store, compare, add, branch.
  2. 2Why does setting one bit in a peripheral register take at least three instructions? This is a load–store machine, so the ALU never touches memory and the M0+ has no sbi. It takes ldr (read), orrs (modify), str (write): 3 instructions, 2 bus events, with a gap between them.
  3. 3What does bics do, and which C operator produces it? Bit clear, r0 = r0 AND NOT r1. It comes from x &= ~y, the clearing half of clear-then-set.
  4. 4Why is lsls more common than subs? Every peripheral bit field is shift-and-mask, such as 2u << (pin * 2), and each << is an lsls. So lsls (4.0%) beats subs (2.5%).
  5. 5cmp computes a subtraction and discards it. What is the point? The flags. It sets N Z C V in APSR, and the next conditional branch acts on them. One cmp can feed several branches.
  6. 6blt and bcc both mean "less than". The difference? blt is signed (N ≠ V), bcc is unsigned (C = 0). Confusing them breaks comparisons at the extremes of the range: −1 read as unsigned is 4,294,967,295.
  7. 7What does pop {r4, pc} do that pop {r4, lr} does not? It returns. The saved LR goes straight into PC, which is a branch. pop {r4, lr} only restores, and still needs bx lr.
  8. 8Which addressing mode is s->field? Which is buf[i]? s->field is immediate offset, [r4, #28]. buf[i] is register offset, [r1, r3].
  9. 9Why no divide instruction, and how does a .map file show your code divided? ARMv6-M (Thumb-1 plus six) has none, so a / b calls __aeabi_uidiv. The map shows libgcc.a(_udivsi3.o) pulled in (<__udivsi3> at 080000b4 in the spike).
  10. 10ARM designs two instruction sets. The other one, and when does a Cortex-M switch into it? ARM (A32). A Cortex-M never switches: no ARM state exists. A branch with bit 0 clear, which would ask for it, faults.
  11. 11Three things a Cortex-M4 does in one instruction that this M0+ cannot. Divide in hardware (sdiv / udiv). Load with a far or negative offset (ldr r0, [r1, #2000], pre- or post-indexed). Build a 32-bit constant inline (movw / movt). Also add without touching the flags, and IT blocks.
  12. 12The reset vector holds 0x08000275 but the function is at 0x08000274. Why, and what if you "fix" it? Bit 0 is the Thumb bit, "this is Thumb code". An even vector asks for ARM state, and the CPU faults immediately on reset.
  13. 13LR reads 0x0800028f. Which instruction runs on return, and what would an even LR tell you? The one at 0x0800028e (LR & ~1), right after the bl. An even LR is a bad value, from a computed function pointer or mov pc, lr, and returning through it faults.
  14. 14The two instruction-set models. Which is this, which is x86, which was the AVR? Register–memory and load–store. This chip is load–store, x86 is register–memory, and the AVR was load–store (with the sbi crack).
  15. 15RISC-V has no flags register. How does it write if (a < b) goto L, and what does ARM gain with flags? blt a0, a1, L, compare and branch in one instruction. ARM gains density: one cmp feeds several branches.
  16. 16Two ways to remember a return address. Which does this chip use, and what is push {lr} for? Stack-based (x86, AVR) and link register (ARM, RISC-V). This chip uses LR. push {lr} saves the one return address before a nested bl overwrites it.
  17. 17Why can a 16-bit instruction not load 0x40021000? ARM's answer and one other. 32 bits cannot fit in a 16-bit instruction (the movs immediate is 8 bits). ARM uses a literal pool, loaded PC-relative (ldr r2, [pc, #44]). RISC-V builds it with lui + addi; x86 embeds it in a longer instruction.

General idea vs this chip

Shaded rows are the key contrasts that guide §2 assigns to this lesson. The other rows are the deck's own "general idea / this chip's answer" sections.

Exam focus
  • counter++ on memory: ldr, adds, str = 3 instructions and 2 bus accesses (x86: 1 instruction, the same 2). An interrupt between the ldr and the str can lose an update.
  • x &= ~m → bics; x |= b → orrs; x ^= y → eors; << → lsls; if (x & BIT) → tst + beq/bne; a / b → bl __aeabi_uidiv.
  • −8 = 0xFFFFFFF8: asrs #3 → 0xFFFFFFFF = −1; lsrs #3 → 0x1FFFFFFF = 536,870,911. An int16_t needs ldrsh.
  • cmp of 0xFFFFFFFF with 1: blt taken (−1 < 1), bcc not taken (4,294,967,295 ≥ 1).
  • ldr offset = imm5 × 4, at most 124; ldrh 62, ldrb 31, [sp] 1020, never negative. ldr r0, [r1, #128] is not encodable: an extra add moves the base first. ldr r6, [r4, #28] = 0x69E6, imm5 = 7.
  • Literal: Align(A + 4, 4) + 4 × imm8, so ldr r2, [pc, #44] at 0x8000230 reads 0x8000260. Branch: A + 4 + 2 × imm, so d1fb at 0x8000240 goes to 0x800023a.
  • A halfword starting 11101, 11110 or 11111 is the first half of a 32-bit instruction. The M0+ has six: bl, mrs, msr, dsb, dmb, isb.
  • bl at 0x0800028a → LR = 0x0800028f; bx lr → PC = 0x0800028e. Vector 0x08000275 → handler at 0x08000274; an even vector faults on reset.
  • AAPCS: arguments r0–r3, result r0, r4–r11 callee-saved. push {r4–r7, lr} = 5 words, SP − 20.
  • Missing volatile on a status register: works at -O0, hangs at -Os. CMSIS __IO = volatile.
