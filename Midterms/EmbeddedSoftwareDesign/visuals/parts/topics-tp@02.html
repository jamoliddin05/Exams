Development: From Text to a Chip That Runs

The third of four lessons with no code to write. Lessons 00 and 01 gave you a model of the machine and of its instructions. This one is about the other machine, the toolchain: how text becomes bytes at fixed addresses in flash, and what runs between power-on and the first line of main(). Every figure in the deck is real output from the course's build of the STM32C031C6 spike.

1. On a PC, an operating system hides all of this (slide 1)

Run gcc hello.c on a laptop and the OS "decides where your program lives in memory, provides a stack, zeroes your globals, opens stdout, and calls main() for you." There is no operating system here. "Every one of those jobs still has to be done, and if you do not arrange it, nothing does."

The lesson answers one question. "Between power-on and the first line of main(), who does the work, and what happens if nobody does?"

2. Five stages, not one (slide 2)

  • "gcc is not a compiler. It is a driver that runs four or five programs in sequence, and on embedded the last one is the one that bites."
  • The five stages are preprocess, compile, assemble, link and locate. main.c becomes main.o. Then main.o, startup.c and link.ld go into LINK and LOCATE, which "resolve names, then assign real addresses".
  • The first stages are ordinary. Locate is the embedded one. It decides that SystemInit lives at 0x0800022c and SystemCoreClock at 0x20000000.
  • "On a PC the last stage is invisible. Here you write its input by hand." Its input is link.ld, together with startup.c.

3. Address binding: when does a name get its address? (slide 2)

The general idea is address binding. "At what moment does a name in your source acquire a real address?" An operating-systems text gives three possible moments, and every system picks one.

Bound atWhat that meansWhere you meet it
compile timethe address is fixed when the code is built, and cannot movethis chip, and MS-DOS .com files
load timethe loader picks a base when the program startsclassic relocatable executables
run timeaddresses move while the program runs, translated by an MMUevery desktop and phone OS
  • A desktop binds late. That is why the same binary runs at a different address every launch, and why two programs can both believe they own address 0x400000.
  • "Here there is no loader and no MMU, so binding happens at build time and is burned into the image."
  • That single fact is why an embedded build needs a stage a desktop build does not, and why you write its input by hand.
  • So SystemCoreClock is at 0x20000000 on every board and every run until you re-link. Reset_Handler only copies values to the addresses the linker chose, and no MMU translates them.

4. The compiler sees one file at a time (slide 3)

Each .c file is compiled alone, into an .o, "knowing nothing about the others. Where it needs a name it does not have, it leaves a hole and a note."

  • "The linker matches every needs to exactly one defines. None left over, none duplicated, or it refuses." This explains the two errors you will meet most often.
  • undefined reference to X: somebody needs X and nobody defines it. The spike really hit undefined reference to SystemCoreClock. ST's header declares it, and ST's system_stm32c0xx.c defines it, but the course deliberately does not use that file. The course's startup.c defines it instead.
  • multiple definition of X: two files both define it, and the linker will not choose for you. A definition written in a header gives the same error, because it lands in every .c file that includes the header.

5. Your program is sections, not one blob (slide 4)

The general idea: "an object file is sorted by what things need, not by the order you wrote them." Four different sets of requirements give four sections. The names are the same on Linux, on macOS and in any ELF file you ever open. .bss is older still, an assembler directive from the 1950s.

  • SRAM also holds the heap and the stack, which grows down from the top of RAM.
  • Within a region, the next section starts where the one before it ends.

if .data grew to 100 B (0x64), .bss would start at 0x20000064

6. The awkward one: .data, and why .bss is free (slide 5)

  • uint32_t SystemCoreClock = 12000000; must be writable, so it has to live in RAM. Its initial value must survive power-off, so it has to live in flash. "Both are true, so it exists in both places."
  • .bss is the opposite case. A global that starts at zero has no value worth storing, so the image records only how many bytes to clear. 364 bytes of .bss cost nothing in flash, while 96 bytes of .data cost 96.
  • The trade is universal, and your desktop's C runtime does the same. Here you can see the loop that does it.
  • Somebody has to copy 96 bytes from flash to RAM before main() runs. On a PC the loader does it. Here Reset_Handler does, in four lines of the startup file.
src = &_sidata;                                  /* where the values sit in flash */
for (dst = &_sdata; dst < &_edata; ) { *dst++ = *src++; }
for (dst = &_sbss;  dst < &_ebss;  ) { *dst++ = 0; }
  • _sidata, _sdata, _edata, _sbss and _ebss are not variables. The linker invents them, and their values are addresses it chose.
  • "This is the one place where your C code reads decisions the linker made." The code writes &_sdata because it wants the symbol's address. No value is stored there.
SymbolSpike valueMarks
_sidatain flash, after the code and constantsstart of the .data values in flash
_sdata0x20000000start of .data in RAM
_edata0x20000060end of .data: 96 B = 24 words copied
_sbss0x20000060start of .bss
_ebss0x200001CCend of .bss: 364 B = 91 words zeroed
  • "Skip the .bss loop and globals start as whatever was in RAM at power-on. The program works perfectly on a cold boot and misbehaves after a reset."
  • The bug is intermittent because a reset does not clear SRAM. The hardware's only act at reset is loading SP and PC. After the reset button, a global that should start at zero still holds what the previous run left, so the result depends on history.

7. The linker script is the memory map, written down (slide 6)

"The linker knows nothing about your chip." You tell it where flash starts, how big RAM is and which section goes where.

MEMORY

FLASHrx0x0800000032K = 32768 B = 0x80000x08007FFF

  • "Those four numbers come from the datasheet, and they are the difference between firmware that runs and firmware that does not."
  • "Get LENGTH wrong and the build succeeds. The failure arrives later, as a stack that quietly walks off the end of memory." The linker has no way to check the numbers against the chip.
  • The stack starts at the top of RAM, ORIGIN + LENGTH = 0x20000000 + 0x3000 = 0x20003000. With LENGTH = 16K it starts at 0x20004000, 4 KB above the last real byte.
  • The build also reports what it used. "On a 32 KB part that number belongs in every build log. It is the only early warning you get."

9. What runs before main(), and bootstrapping (slide 8)

The complete path from power to your code: power on or reset, then the hardware loads SP and PC from vector[0] and vector[1], then Reset_Handler copies .data, zeroes .bss, calls SystemInit and __libc_init_array, and then calls main().

  • Loading SP and PC is the only step the hardware does for you. "The CPU reads two 32-bit words from address zero of flash, the stack pointer and the reset vector, and starts. That is the entire boot process. Everything else is code you can read."
  • So at reset the hardware does not copy .data, does not clear .bss and does not set up the clock.
  • SystemInit raises the clock from the reset 12 MHz to 48 MHz, and __libc_init_array runs the C library's start-up list. Lesson 04 shows both in detail.

The general idea is bootstrapping, and every computer ever built does the same thing. "On reset the hardware can only do one fixed, dumb act, and that act has to be enough to start software that is progressively less dumb."

PCThis chip
The hardware's fixed actthe CPU begins executing at a fixed address near the top of its address spacethe CPU reads SP and PC from the first two words of flash

  • The real difference is length. Embedded booting is no stranger than a PC's, and it is short enough to read in full.
  • It is also short enough that "if you get one of those two words wrong, nothing else exists to catch it."

What you should be able to say (slide 10)

  • 1. Name the five stages of a build. Which one is the embedded-specific one? Preprocess, compile, assemble, link, locate. Locate is the embedded one: it gives every name its real address from link.ld. On a PC it is invisible; here you write its input.
  • 2. Where does .data live, flash or RAM? Defend your answer. Both. The variables must be writable, so they live in RAM. Their initial values must survive power-off, so a copy lives in flash, and Reset_Handler copies it to RAM before main().
  • 3. What are _sdata and _ebss, and who creates them? Symbols the linker invents. Their values are addresses it chose: _sdata is the start of .data in RAM (0x20000000), _ebss the end of .bss (0x200001CC). They are not variables, so C reads them as &_sdata.
  • 4. What happens if the .bss loop is missing? Why is that bug intermittent? Globals that should start at zero start as whatever RAM held. A reset does not clear SRAM, so after the reset button they keep the previous run's values. The program passes after a cold boot and fails after a reset.
  • 5. Two numbers in the linker script come straight from the datasheet. Which, and what goes wrong if they are too large? The two LENGTHs, FLASH 32K and RAM 12K. Too large and the build still succeeds. With RAM 16K the stack top becomes 0x20004000, above real memory, and the program fails at run time.
  • 6. The hex file begins :02000004 0800. What is that record for, and why did the 8-bit chips never need one? It is an extended linear address record (type 04). It sets the upper 16 bits of every following address to 0x0800, so flash at 0x08000000 is reachable. An 8-bit AVR's whole flash fits in 16 bits of address, so the offset alone was enough.
  • 7. The three moments of address binding. Which does this chip use, which does your laptop use, and what hardware does the laptop need? Compile time, load time and run time. This chip binds at build (compile) time, with no loader and no MMU. The laptop binds at run time, which needs an MMU to translate every address.
  • 8. Why does 364 bytes of .bss cost nothing in flash while 96 bytes of .data costs 96? .bss is all zeros, so the image records only where it is and how many bytes to clear. Every byte of .data has a starting value that must survive power-off, so all 96 bytes are stored in flash.
  • 9. The boot chain of a PC and of this chip. How many handoffs? A PC starts at a fixed address near the top, then runs firmware, a bootloader, a kernel and your program: four handoffs. This chip reads SP and PC from the first two words of flash and runs your code: one link.

Exam focus
  • Hex records: after :020000040800F2 the base is 0x08000000. In :10000000 00300020 75020008 ..., SP = 0x20003000 and the reset vector is 0x08000275, so the handler is at 0x08000274. Offset 0120 lands at 0x08000120.
  • Checksum: :02000004 0801 ?? gives 0x02 + 0x04 + 0x08 + 0x01 = 0x0F, so CC = 0x100 − 0x0F = F1.
  • Flash and RAM cost: const uint8_t lut[64] flash +64, RAM 0. uint32_t samples[32]; flash 0, RAM +128. uint32_t gain = 3; flash +4, RAM +4. Together flash +68, RAM +132.
  • Section addresses: .text at 0x08000000 + 180 = 0x080000B4. If .data grows to 100 B, .bss starts at 0x20000064.
  • Link errors: a definition in two .c files or in a header gives multiple definition. Only an extern gives undefined reference. extern in the header plus one definition links.
  • RAM LENGTH = 16K on this 12 KB part: builds clean, reports 12.21 % instead of 16.28 %, SP = 0x20004000, fails at run time.
  • Missing .bss loop: correct after plugging in, wrong after the reset button, because a reset does not clear SRAM.
  • At reset the hardware does exactly two loads: SP from 0x08000000, PC from 0x08000004. There is no .data copy, no .bss clear and no clock set-up. Boot chains: PC four handoffs, this chip one link.
  • Binding: this chip at build time (no loader, no MMU), so SystemCoreClock is at 0x20000000 on every board and run. A laptop binds at run time with an MMU, so two programs can both use 0x400000.
