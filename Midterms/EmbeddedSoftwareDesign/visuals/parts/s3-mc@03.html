Question 12 · L03, a bug that only appears sometimes

main() and a 1 kHz timer ISR both do count++ on a shared global. Every bench test passes, but in the field the count comes out wrong roughly once every 7 hours. The timer is then changed to 10 kHz. Which statement is right?

  1. A It is a compiler optimisation problem; declaring count as volatile fixes it at any interrupt rate. No. volatile makes accesses real. The ldr, adds, str can still be split by the interrupt.
  2. B It is a stack overflow that builds up with uptime; at 10 kHz it appears about 10 times less often. No. Nothing accumulates; each interrupt is an independent chance to hit the window.
  3. C It is a race condition; at 10 kHz it appears about 10 times as often, roughly every 40 minutes, and running more tests will not find it. Correct. Ten times the interrupts, ten times the hits: 7 h / 10 ≈ 42 min.
  4. D It is tearing of a 32-bit value; at 10 kHz the window closes and the bug disappears. No. An aligned 32-bit word is read in one access, and the window's width does not depend on the rate.

Answer: C. An update is lost only when the interrupt lands in main()'s two-instruction window between ldr and str, about 40 ns at 48 MHz (2 × 20.8 ns = 41.7 ns). Each interrupt has the same small chance of landing there, so ten times as many interrupts give about ten times as many failures: 7 h / 10 ≈ 42 min, the slide's "roughly once every 40 minutes".

The result depends on the relative timing of two contexts, which is the definition of a race condition. Running the program more only resamples the timing. You find it by listing which variables more than one context touches, and protecting those.

Exam line

Works for hours, then fails once: a race condition. The interrupt must land in a two-instruction window, about 40 ns at 48 MHz. You cannot find it by running the program more; you find it by reasoning about which variables are shared, and protecting those.

Question 13 · L03, polling, interrupt or DMA

In which of these situations is polling the right choice?

  1. A Waiting for a user to press a button, which may take minutes, while main() has other work to do. No. A rare, long wait: polling would burn every cycle. Use an interrupt.
  2. B Moving a 2 KB block of received UART data into a buffer while the CPU runs a control loop. No. A stream of data is the job of DMA: the hardware moves the bytes and the CPU is not involved.
  3. C Waiting, after writing a new wait state into FLASH->ACR, until its LATENCY field reads back the new value, a wait of a few cycles. Correct. The wait is shorter than the cost of being interrupted.
  4. D Catching every edge of a signal that can arrive at any moment while main() is busy elsewhere. No. Polling only sees the signal when the loop comes back; an interrupt sees every edge.

Answer: C. Polling is not the beginner option. It is the right answer whenever the wait is shorter than the cost of being interrupted. An interrupt costs an entry (push 8 registers, read the vector table) and an exit (pop 8), and in a few cycles there is no other work to do anyway.

The flash controller acknowledges the new latency within a few cycles, so L01's four-instruction loop (read FLASH->ACR, isolate LATENCY, compare, branch back) is both simpler and faster.

Exam line

Three ways to meet the hardware: polling (CPU does nothing else), interrupt (CPU works until told), DMA (CPU not involved). Polling is the right answer whenever the wait is shorter than the cost of being interrupted, for example the FLASH->ACR latency wait.

Question 14 · L03, keep the critical section short

To protect a shared counter, a student writes this in main(). A UART receive interrupt with NVIC priority 0 is enabled. What does this code do to that interrupt?

__disable_irq();
counter++;
print_count(counter);    /* takes about 5 ms */
__enable_irq();
  1. A A request that arrives inside the region waits until __enable_irq(), up to about 5 ms. The longest critical section sets the worst-case interrupt latency, so only counter++ belongs inside. Correct. PRIMASK holds back every configurable interrupt until cpsie i.
  2. B Nothing: priority 0 is the most urgent level, so the UART interrupt still preempts main() inside the region. No. Priority ranks interrupts against each other. PRIMASK = 1 blocks all configurable interrupts, priority 0 included.
  3. C The request is discarded, so that byte is lost, but the latency of later interrupts is unchanged. No. The NVIC holds the request pending and takes it at cpsie i. What grows is the latency.
  4. D Nothing: __disable_irq() only asks the scheduler not to switch threads, like a mutex. No. That describes a mutex. __disable_irq() is cpsid i, a hardware mask.

Answer: A. __disable_irq() is cpsid i. It sets PRIMASK bit 0, and while that bit is set no configurable interrupt is taken, whatever its priority. The NVIC keeps the UART request pending, and the handler runs right after cpsie i. A request that arrives just after cpsid i waits the whole 5 ms.

Interrupt latency is the gap between the hardware event and the first instruction of the handler, and the longest critical section anywhere in the program sets its worst case. The shared counter needs only its three instructions protected; print_count() can run with interrupts on.

Exam line

Keep critical sections short: every cycle with interrupts off is a cycle in which the chip cannot respond to anything. Interrupt latency is the gap from the hardware event to the handler's first instruction, and the longest critical section anywhere sets its worst case.
