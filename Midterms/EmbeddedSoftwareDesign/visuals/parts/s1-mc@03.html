Question 12 · L03, volatile and the as-if rule

A timer ISR sets a flag and main() waits for it. Built at -O0, the LED turns on. Built at -Os, it never does, although the ISR runs and sets done. What explains this, and what is the fix?

uint8_t done = 0;                         /* global */
void TIM3_IRQHandler(void) { /* ... */ done = 1; }
int main(void) {
    /* ... start the timer ... */
    while (done == 0) { }
    led_on();
}
  1. A The ISR's write lands in the middle of main()'s read-modify-write; wrap the loop in __disable_irq() / __enable_irq(). No. That is the fix for the other hazard, and with interrupts off around the loop the ISR could never run at all.
  2. B A one-byte flag tears when the ISR writes it; declare it uint32_t. No. One byte is one access with one writer. Nothing can tear, and the width does not change the compiler's reasoning.
  3. C At -Os interrupts stay masked while main() sits in an empty loop; call __enable_irq() inside the loop. No. The optimisation level never touches PRIMASK, and the question says the ISR runs.
  4. D By the as-if rule the compiler reads done once and loops on a register copy; declare it volatile uint8_t done. Correct. The ISR is an observer C does not know about. volatile makes every read happen.

Answer: D. The loop body does not modify done, so by the rules of C it cannot change inside the loop. Under the as-if rule the compiler may read it once and loop on a register, because the program it produces behaves the same as far as C can observe.

The ISR's write is a change C does not know about. Declaring volatile uint8_t done extends what counts as observable: every read written in the source must really happen, in order, so the loop sees the 1. At -O0 nothing is cached, which is why the bug only shows up at -Os.

Exam line

As-if rule: the compiler only has to keep the observable behaviour the language defines. Hardware and ISRs are observers C does not know about, so a shared flag needs volatile. volatile makes accesses real; it is not a lock and makes nothing atomic.

Question 13 · L03, the lost update

counter holds 40. main() executes counter++ as ldr r0, [r1] / adds r0, #1 / str r0, [r1]. A timer interrupt is taken right after the ldr, and its handler executes counter += 3 in full before main() resumes. Nothing else touches counter. What does counter hold after main()'s str?

  1. A 41 Correct. main() adds 1 to the 40 it loaded before the interrupt and stores 41 over the handler's 43.
  2. B 43 No. That would need main()'s store to be lost, but main() stores last.
  3. C 44 No. 44 = 40 + 3 + 1 is the right total, which only a critical section around counter++ guarantees.
  4. D 40 No. Every store wrote a new value; the last one wrote 41.

Answer: A. main() loaded 40 into r0 before the interrupt. The handler reads 40 from RAM, adds 3 and stores 43. When main() resumes, its r0 still holds 40 (the hardware stacked and restored it), so it computes 41 and stores 41 over the 43.

Two updates ran and only one survived. This is the lost update of slide 5, with +3 instead of +1.

Exam line

On a load–store machine counter++ is ldr, adds, str. An ISR that updates the same variable between the ldr and the str is overwritten by main()'s stale value. volatile does not help; the sequence must be made indivisible.

Question 14 · L03, mutual exclusion on one core and on two

On the single-core STM32C031, __disable_irq(); counter++; __enable_irq(); makes main()'s increment safe from an ISR. The same code is moved to a dual-core chip, where code on the other core also increments counter. What happens?

  1. A It stays safe: __disable_irq() sets PRIMASK on both cores, so the other core waits too. No. Each core has its own PRIMASK. cpsid i sets only the bit of the core that executes it.
  2. B Updates can still be lost: masking stops only the other context on this core, and the second core keeps running. Two cores need an atomic read-modify-write instruction such as ldrex/strex. Correct. This is the third row of slide 5's table.
  3. C Updates can still be lost, and declaring counter as volatile fixes it. No. volatile makes accesses real, not indivisible.
  4. D It stays safe, because larger ARM cores do counter++ in a single instruction. No. ARM cores are load–store, so a plain counter++ still compiles to a load, an add and a store.

Answer: B. Masking interrupts gives mutual exclusion only against contexts that need this core to run: the other context cannot run if it cannot start. A second core does not need to start anything. It runs its own ldr, adds, str in parallel, and the two sequences can interleave just like main and an ISR.

Between cores you need an atomic read-modify-write instruction: ldrex/strex on larger ARM cores, lock cmpxchg on x86. The Cortex-M0+ is single-core and has neither, which is exactly why masking is the right tool on this chip and would be the wrong tool on a phone.

Exam line

ISR vs main() on one core: turn interrupts off. Two threads under an OS: a mutex. Two cores: an atomic read-modify-write instruction (ldrex/strex, lock cmpxchg). The Cortex-M0+ is single-core and has neither, so masking is its answer.
