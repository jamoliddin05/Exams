Question 31 · L08, Byte time and a polled printf

USART2 is clocked at 48 MHz and BRR reads 5000 (8N1). Lesson 04's polled _write() sends a 48-character line. For about how long does that printf call hold the CPU?

  1. A 4.2 ms No. 4.2 ms is 48 bytes at 115 200 baud, 86.8 µs each. BRR = 5000 at 48 MHz gives 9600 baud.
  2. B 50 ms Correct. 48 000 000 / 5000 = 9600 baud, 960 bytes a second, so 48 bytes take 50 ms.
  3. C 40 ms No. 40 ms counts 8 bits per byte. The start and stop bits are on the wire too, so a byte is 10 bits.
  4. D Almost no time: printf returns as soon as the text is in a buffer No. That is lesson 08's _write(), which fills a ring. Lesson 04's version waits on every byte.

Answer: B. BRR counts clocks per bit, so the line runs at 48 000 000 / 5000 = 9600 baud. 8N1 puts 10 bits on the wire per byte (start, 8 data, stop), so 960 bytes a second and 1.04 ms per byte.

The polled _write() waits for TXE before each byte, so printf returns only when the line has gone out: 48 / 960 s = 50 ms of CPU spent waiting. Lesson 08's _write() copies the line into the ring and returns, and the interrupt sends the bytes.

Exam line

BRR = clock / baud, and an 8N1 byte is 10 bits. 48 000 000 / 5000 = 9600 baud = 960 bytes a second, so a polled printf of 48 characters holds the CPU for 50 ms. Lesson 08's ring _write() returns as soon as the text is in the ring.

Question 32 · L08, host.py: bad and lost frames

host.py --file reads a capture of ten $TEL frames, seq 0 to 9, and nothing else. In transit the seq 4 frame $TEL,5000,4,500,0,0*75 arrived as $TEL,5000,4,600,0,0*75; nothing else was damaged or lost. What does host.py's summary line frames good …, bad …, lost (sequence gaps) … report?

  1. A good 10, bad 0, lost 0 No. 5 → 6 changes one byte, and XOR catches any change inside one byte: the body gives 76.
  2. B good 9, bad 1, lost 0 No. This counts the bad line and forgets that seq 4 never arrives intact, so the good frames jump from 3 to 5.
  3. C good 9, bad 0, lost 1 No. A line that fails its checksum is counted bad. host.py does not drop it silently.
  4. D good 9, bad 1, lost 1 Correct. The damaged line is counted bad, and its seq 4 is missing from the good frames: a gap of one.

Answer: D. The damage is inside one byte: 5 → 6 is 35 ^ 36 = 03, so the XOR of the body becomes 75 ^ 03 = 76. The line still carries 75, so the check fails, and host.py counts the line bad and uses none of it.

Only good frames reach the sequence check. They carry seq 0, 1, 2, 3, 5, 6, 7, 8, 9, and the jump from 3 to 5 adds 5 − 3 − 1 = 1 to lost. Slide 13: a line altered in transit is counted bad, and the sequence number it carried never arrives intact, so it is also a gap.

Exam line

A frame that fails its checksum is thrown away and counted bad, never half-used. Its sequence number never arrives intact, so host.py also counts a gap: good 9, bad 1, lost 1.

Question 33 · L08, Turning TXEIE off

The else branch that turns TXEIE off is deleted from USART2_IRQHandler, leaving the transmit branch below; _write() still turns TXEIE on after filling the ring. What happens after reset?

if ((USART2->CR1 & USART_CR1_TXEIE_TXFNFIE) && (isr & USART_ISR_TXE_TXFNF)) {
    if (tx_tail != tx_head) {
        USART2->TDR = tx_ring[tx_tail];
        tx_tail = (tx_tail + 1) % 256;
    }
}
  1. A Every line prints normally; after each line the handler runs once more, finds the ring empty and returns No. Returning does not clear TXE. With TXEIE still on, the interrupt is pending again the moment the handler returns.
  2. B Nothing is printed, not even the banner Correct. The handler re-enters forever at priority 1, so the code that fills the ring never runs again. Measured: not even the banner.
  3. C Every line prints, a little slower: while the UART is idle, the handler runs once per byte time No. Once per byte time is the rate while bytes are going out. An idle UART keeps TXE at 1, so the handler runs back to back.
  4. D The build warns that TXEIE is turned on but never off, so the fault is caught before it runs No. To the compiler TXEIE is one bit of a register write. The measured build had zero warnings.

Answer: B. TXE means the transmit register is empty. It stays 1 the whole time the UART is idle, and only a write to TDR clears it. With the else gone nothing turns TXEIE off, so once the ring is empty the handler finds nothing to send, returns, and is entered again at once.

The handler runs at priority 1, above SysTick, PendSV and every task, so the code that would put more bytes into the ring never runs again. Slide 6, measured with the else line removed: nothing is printed at all, not even the banner. The deleted line is the fix: USART2->CR1 &= ~USART_CR1_TXEIE_TXFNFIE; when the ring is empty.

Exam line

TXE stays 1 whenever the UART is idle, so TXEIE must be on only while there is work. Forget to turn it off when the ring is empty and the handler runs forever at priority 1: an interrupt storm, and measured, not even the banner.
