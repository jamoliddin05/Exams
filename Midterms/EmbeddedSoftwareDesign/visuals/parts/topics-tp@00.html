The Programmer's Model: What You Can See and Change

The first of four lessons with no code. It gives you a model of what the chip is: the small set of state software can name, in five parts. Every later lesson (GPIO, timers, interrupts, UART, the RTOS) is one of these five parts wearing a different name. Coming from an 8-bit AVR, the big changes are memory-mapped I/O, one address space and a vector table of addresses.

1. A contract over a hidden machine (slides 1–2)

A programmer's model is "a deliberately small, published abstraction", a contract that says "here is the state you may inspect and change, and here is what happens when you do."

  • It includes everything software can name: registers, memory, peripheral registers, modes, exceptions. The contract is "documented, stable, the same on every chip of this family".
  • It leaves out the implementation: pipeline, bus matrix, silicon, "none of it named by your code".
  • The five parts: (1) registers, the working state inside the CPU; (2) memory, one flat address space; (3) peripheral registers, the memory-mapped controls of the hardware; (4) modes and stacks, which of two contexts you run in; (5) exceptions, how the hardware takes control away from you. "Everything in the next thirty lessons is one of those five."
  • The method (slide 2). Meeting a new peripheral, the first question is "which part of the model is this?" Learn one peripheral model and the seventh peripheral, the one not on the syllabus, comes free.
  • Two columns for every mechanism. The general idea is the name in any architecture text, with its known alternatives. This chip's answer is the one picked here, and what it costs. The left column lets you read the datasheet of any processor. The right column is what you need this term.

2. Registers: sixteen, and the special registers beside them (slides 3, 3b)

General idea: a register file. Memory is slow and far away, so every processor keeps a few storage locations inside the CPU, named by a few bits of the instruction instead of by a 32-bit address. How many is one of the oldest design choices:

MachineWorking registers
6502, 8051one accumulator; every result passes through it
JVM, Forthnone; operands sit on a stack
ATmega128 (AVR)32 × 8-bit
Cortex-M (this chip)16 × 32-bit, of which 13 are freely yours
x86-6416 × 64-bit
RISC-V32 × 32-bit, one hardwired to zero
  • Too few and the compiler spills to memory constantly. Too many and every instruction needs more bits to name one, and every interrupt has more state to save.
  • This chip: R0–R15, sixteen 32-bit registers. R0–R12 (13) are freely yours. R13 = SP, R14 = LR and R15 = PC have fixed jobs, and xPSR holds the flags beside them.
  • The CPU cannot compute on memory. It loads into registers, operates there, and stores back.
  • "Write to PC and you have branched. It is an ordinary register."
  • "This is the entire working state of the processor": 16 × 4 bytes = 64 bytes plus xPSR. Everything else your program owns is in memory. That is why an interrupt can save and restore it in a handful of cycles.

  • The special registers (xPSR, PRIMASK, CONTROL) have no number and no address. Only mrs and msr reach them.
  • A Cortex-M3 or M4 adds BASEPRI and FAULTMASK. This core has neither.
  • "Flags at the top of xPSR, the running exception's number at the bottom, and almost nothing in between." T is always 1 here. ISR is 0 in main() and the exception's number inside a handler.
  • You rarely name them in C, but the debugger shows them, and a crash report is mostly their contents.

3. One flat address space: how software reaches a device (slide 4)

General idea one: how does software reach a device? Two answers, both as old as the minicomputer.

Port-mapped I/O (isolated I/O)Memory-mapped I/O
Devices live inan address space of their ownordinary addresses in the ordinary memory map
Reached bydedicated instructions onlyordinary loads and stores; no new instructions
Examplesx86 in / out with a 64 K port space; AVR IN / OUTthis chip, with no port space at all

General idea two: one address space, or two?

Harvardvon Neumann
Code and dataseparate address spaces; 0x100 means two different thingsone address space holds both; a pointer can reach anything
Reading a constant in flashneeds its own instruction: AVR LPM, hence PROGMEMthe same ldr as anything else
MachineAVRthis chip: one unified address space
  • A GPIO register and a global variable are reached by the same ldr. Only the address tells them apart.
  • PROGMEM has no equivalent here and needs none. A const array in flash is read by an ordinary ldr.
  • Some Cortex-M cores fetch code and data over separate buses for speed. That is an implementation choice underneath. The address map stays single and your code cannot tell.
  • "Everything the CPU can reach, it reaches by address. There is no other channel."

5. A register is not a variable (slide 5)

"This is the single idea that separates embedded C from the C you have written before, and almost every beginner bug traces back to getting it wrong." A store to 0x50000014, "just an address", makes a pin go high. "The store instruction has a side effect in the physical world. Nothing in the C language says so."

A variableA register
Lives in RAMIs a piece of hardware
Reading it twice gives the same valueReading it twice can give different values
Writing it changes memoryWriting it makes something happen
Reading is free of consequenceReading can clear a flag or consume a byte
The compiler may cache, reorder or delete accessesEvery access must happen, exactly as written

That last row is why volatile exists. Lesson 03 returns to it.

6. Every peripheral has the same three registers (slide 6)

  • CONTROL: you write it. Settings.
  • STATUS: the hardware writes it and you read it. What happened.
  • DATA: the payload, both ways.
  • The peripheral itself is a state machine between these registers and the pins. "Configure with CONTROL. Watch with STATUS. Move bytes through DATA."
  • "The names move between chips. The three roles never do."

8. Modes and stacks: privilege without virtual memory (slide 8)

General idea: privilege. Nearly every processor since the 1960s runs at two or more levels of trust: a supervisor level that may touch anything, and a lower one that may not. On a desktop these are kernel mode and user mode. The enforcement hardware is normally an MMU, which also hands each program a private, virtual view of memory.

  • This chip has the two levels and none of the virtual memory. There is one real address space and everything shares it.
  • Where a chip fits the optional MPU, the separation is a set of permission rules over real addresses, with no private map.
  • So "a stray pointer here quietly reaches a peripheral instead of earning a segmentation fault".
  • The processor is always in one of two modes, and it switches without being asked.
Thread modeHandler mode
What runsyour main() (later, RTOS tasks)every interrupt and fault handler
StackMSP, or PSP (CONTROL.SPSEL)always MSP
Privilegeprivileged, or not (CONTROL.nPRIV)always privileged
Switchan interrupt takes you to Handler modethe return brings you back
  • CONTROL uses two bits, SPSEL (bit 1) and nPRIV (bit 0). "The other thirty are reserved." Both are 0 at reset: Thread mode on MSP, privileged.
  • Until the RTOS lesson, one stack (MSP) serves everything. It matters later for two reasons. An RTOS gives each task its own stack on PSP. A fault handler runs in Handler mode, which is how it still works when the faulting code has wrecked everything else.
  • Unprivileged Thread mode "is how an RTOS keeps one task from corrupting another".

9. The exception model: a table of addresses (slide 9)

An interrupt is a "hardware-forced function call". How does the hardware find the function?

Non-vectored
One entry point, then ask

Every interrupt enters at one fixed address. That code's first job is to interrogate the hardware to discover who called. Cheap silicon, slower and wordier software.

Vectored, AVR
A table of jump instructions

The source has a number and the number indexes a table. Each AVR slot holds a jump instruction. (x86 slots hold descriptors.)

Vectored, this chip
A table of plain addresses

The NVIC does not search for your handler. It indexes a table of addresses at the start of flash and jumps to the address in the slot.

  • "The first 16 slots are ARM's: reset and faults. Vendor interrupts start at 16." Slot 0 holds the initial stack pointer, slot 1 the address of Reset_Handler.
  • The table is built by your own code. There is no registration call. A handler is connected because its address sits in the right slot.
  • "Put the wrong address in a slot and the chip jumps there anyway."
  • The CPU records which slot it took. While a handler runs, IPSR (the bottom of xPSR) holds the exception number.

exception number = 16 + IRQn    slot address = 0x08000000 + 4 × (16 + IRQn)

10. The data model: width, alignment, byte order (slide 10)

  • Everything is 32 bits wide. The general term is the machine's word size, the width its registers, ALU and bus agree on. Narrower types are emulated on top of it. So a uint8_t is not cheaper than a uint32_t here; it is often more expensive, because the compiler must mask and shift. Do not reach for uint8_t out of AVR habit.
  • Accesses must be aligned. The general rule is natural alignment: an n-byte access wants an address divisible by n. A word wants an address ending in 0, 4, 8 or C; a halfword wants an even address.
  • The bite: casting a uint8_t* buffer to a uint32_t* when parsing packets is "a reliable crash on an M0+".
  • Little-endian. 0x12345678 stored at address 0 puts 0x78 at byte 0, least significant byte first. Big-endian machines do the opposite: the 68000, classic SPARC, and every internet protocol header ("network byte order", htonl()). ARM can be built either way. Every STM32 is little-endian. The other order reaches you only when bytes arrive from somewhere else.

11. Your responsibilities: two gates and the clock (slides 11–12)

"The model says a peripheral has registers. It does not promise they answer." Two gates are shut at power-on, and opening them is your job.

  • The clock gate (RCC). Every peripheral powers up switched off, to save energy. Write to its control register first and the write goes nowhere: no error, and the register reads back zero. "A peripheral with no clock reads back as zero and ignores every write." The single most common first-week failure.
  • The pin multiplexer. There are more peripherals than pins, so each pin is shared and you must say which owner it belongs to. Choose wrong and the pin is electrically healthy and carries no signal.
  • "Both look identical from outside: correct code that does nothing. Neither produces an error message. Suspect them first."
  • The clock is yours too. Every timed thing on the chip derives from one oscillator by division, and each bus has its own prescaler. Nothing picks the divisions for you.
  • A baud rate is a division. The USART does not know what 115200 means. You give it a divisor computed from its own bus clock, and the CPU clock is the wrong one to use. Get it wrong and the output is garbage while the code is perfect.
  • A delay is a count. There is no sleep(). One millisecond means counting a known number of ticks.
divisor = f_bus / baud
48 000 000 / 115 200 = 416.7 → BRR = 417
actual baud = 48 000 000 / 417 = 115 108   (−0.08 %)
same 417 on a 12 MHz bus: 12 000 000 / 417 = 28 777 baud → garbage

ticks = f × t
1 ms at 48 MHz = 48 000 ticks; the same 48 000 ticks at 12 MHz last 4 ms

12. Where the implementation leaks through (slides 13–14)

The model is an abstraction, and abstractions leak. Three places, and "these are the only implementation details this course asks you to care about":

  • Pipeline. General name: pipelining, overlapping the fetch, decode and execute of consecutive instructions. It is why the PC reads ahead of the instruction being executed, and why a taken branch throws away work already started.
  • Two buses. A fast AHB and a slow APB. You cannot name the bus matrix in C, but you must name the register that enables a clock on the right bus: RCC->AHBENR, RCC->APBENR1.
  • Flash is slow. General name: the processor–memory speed gap. The core will run at 48 MHz and the flash will not. Large machines answer with caches. A 32 KB microcontroller cannot spend the transistors, so it uses wait states and a prefetch buffer, and hands you the register: FLASH->ACR.
  • Set the flash wait state before you raise the clock, never after. This is the first of many "ordering requirements the compiler knows nothing about". The code compiles identically either way round; only one order works.
  • Slide 14 shows the implementation once. You will not program any of it directly. "Left of the matrix is ARM's, identical on every Cortex-M. Right of it is ST's."
right:  FLASH->ACR = 1 wait state   then   clock 12 MHz → 48 MHz
wrong:  clock 12 MHz → 48 MHz       then   FLASH->ACR = 1 wait state
        (in between, the core reads flash at 48 MHz with 0 wait states)

What you should be able to say (slide 17)

  • 1. What does a programmer's model include, and what does it leave out? It includes the state software may inspect and change, and what happens when it does: registers, memory, peripheral registers, modes, exceptions. It leaves out the implementation: pipeline, bus matrix, silicon.
  • 2. Name the five parts. Registers, memory (one flat address space), peripheral registers, modes and stacks, exceptions.
  • 3. The one mechanism for reaching anything outside the CPU? An address. Every access is a load or a store to an address, whether it reaches flash, SRAM or a peripheral. There is no other channel.
  • 4. Three ways a register differs from a variable. Reading it twice can give different values. Writing it makes something happen. Reading it can clear a flag or consume a byte. Also, every access must happen exactly as written, hence volatile.
  • 5. The three roles, and who writes each. Control: you write it, to configure. Status: the hardware writes it and you read what happened. Data: the payload, written both ways (you write TDR, the hardware fills RDR).
  • 6. ARM's and ST's peripherals, and the manual. ARM: NVIC, SysTick, SCB, MPU, the same on every Cortex-M, in the Generic User Guide and core_cm0plus.h. ST: GPIO, USART, TIM, ADC, RCC, in ST's reference manual and stm32c031xx.h. Each company documents only its own blocks.
  • 7. A configured peripheral reads back as zero. First suspect? The clock gate. Its enable bit in RCC is still 0, so writes are ignored and reads return 0, with no error.
  • 8. Serial output is garbage but the code is right. Two causes. The baud divisor was computed from the wrong clock, such as the CPU clock instead of the USART's own bus clock. Or the clock tree is not what the code assumes, for example a bus prescaler, or a clock never raised from the reset 12 MHz. Either way the division gives the wrong baud rate.
  • 9. uint8_t* cast to uint32_t*, then a HardFault. Why, and on an M3? The address is not a multiple of 4, and the M0+ faults immediately on an unaligned word access. A Cortex-M3 performs ordinary unaligned loads and stores, only slower, so it would not fault.
  • 10. The three leaks. The pipeline (the PC reads ahead, taken branches cost extra), two buses (enable each clock on the right bus in RCC), slow flash (wait states in FLASH->ACR, set before raising the clock).
  • 11. How does the hardware find the USART2 handler? USART2 is IRQ 28, so exception 16 + 28 = 44. The NVIC reads the word at 0x08000000 + 4 × 44 = 0x080000B0 and jumps to that address. Your code put the address there; there is no registration call.
  • 12. The two ways to reach a device; AVR and this chip. Port-mapped (isolated) I/O and memory-mapped I/O. The AVR used port-mapped I/O with IN / OUT. This chip uses memory-mapped I/O and has no port space.
  • 13. What does Harvard mean, and which AVR keyword existed because of it? Code and data live in separate address spaces, so reading a constant from flash needs its own instruction (LPM). PROGMEM existed only because of that.
  • 14. Segfault hardware, what this chip has, and what a bad pointer does. The MMU. This chip has no MMU: two privilege levels, one real address space and, where fitted, an MPU of permission rules. A bad pointer quietly reads or writes whatever is at that address, possibly a peripheral, with no error.

General idea vs this chip

Shaded rows are the key contrasts that guide §2 assigns to this lesson. The other rows are the deck's own "general idea / this chip's answer" sections.

Exam focus
  • Little-endian: 0x12345678 at address a gives a: 78, a+1: 56, a+2: 34, a+3: 12. The halfword at a+2 is 0x1234. The first byte of 0xAABBCCDD is 0xDD.
  • Vector slot: exception = 16 + IRQn, address = 0x08000000 + 4 × (16 + n). USART2, IRQ 28: 44, 0x080000B0. IRQ 7: 23, 0x0800005C. IRQ 0: 16, 0x08000040. Inside the USART2 handler IPSR = 44 = 0x2C.
  • xPSR 0x0100002C: T = 1, ISR = 44, so the USART2 handler is running. 0x01000000: in main(). Top hex digit 0xA = N and C set.
  • Alignment: a word access needs addr mod 4 = 0. A word read at 0x20000101 HardFaults on the M0+ and works, slower, on an M3/M4.
  • Reads back 0, no error: the clock gate (RCC). Peripheral works but the pin is silent: the pin mux. Garbage at the right baud setting: the divisor came from the wrong clock (417 on a 12 MHz bus gives 28 777 baud).
  • I/O model: AVR port-mapped (IN/OUT), this chip memory-mapped (ldr/str). Address spaces: AVR Harvard (LPM, PROGMEM), this chip von Neumann. Dispatch: vectored, slots hold addresses.
  • No MMU: a stray pointer to 0x5000xxxx writes a GPIO register, no segfault. Handler mode: always MSP, always privileged. CONTROL resets to 0x0; 0x3 = Thread on PSP, unprivileged.
  • Address owner: 0xE000xxxx (NVIC, SysTick) is ARM's, Generic User Guide. 0x4000xxxx and 0x5000xxxx are ST's, reference manual.
  • Special registers have no address, only mrs/msr; the M0+ has no BASEPRI or FAULTMASK. 13 registers (R0–R12) are freely yours. uint8_t is not faster than uint32_t. Flash wait state first, then the clock.
