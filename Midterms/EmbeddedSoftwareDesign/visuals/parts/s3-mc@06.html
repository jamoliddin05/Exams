Question 23 · L06, PSC and ARR for 100 ms

TIM3 is a 16-bit timer clocked at 48 MHz. It must raise an update event every 100 ms. Which register values do that?

  1. A PSC = 4799, ARR = 999 Correct. 48 MHz / 4800 = 10 kHz, one count every 100 µs, and 1000 counts make 100 ms.
  2. B PSC = 47, ARR = 99999 No. 100 000 counts need 17 bits. ARR keeps 0x869F = 34 463, so the period is 34.464 ms.
  3. C PSC = 4800, ARR = 1000 No. Both registers hold N − 1. This is 4801 × 1001 clocks, 100.12 ms, and nothing complains.
  4. D PSC = 479, ARR = 999 No. That counts at 100 kHz, so 1000 counts take 10 ms.

Answer: A. The counter steps once every PSC + 1 clocks: 48 MHz / 4800 = 10 kHz, one count every 100 µs. 1000 counts of 100 µs make 100 ms, so ARR = 999. Check with the slide-5b formula: 48 000 000 / (4800 × 1000) = 10 Hz.

B would be right with the lesson's 1 µs count, but 100 000 counts do not fit a 16-bit ARR (at most 65 535). Only the low 16 bits of 0x1869F stay, 0x869F = 34 463, and the period is 34.464 ms. C forgets the −1 in both registers (100.1 ms), and D counts at 100 kHz and updates every 10 ms.

Exam line

fupdate = fclk / ((PSC + 1)(ARR + 1)). TIM3 and TIM14 are 16-bit timers, so ARR + 1 is at most 65 536 counts: for a long period, slow the count with PSC first, then count with ARR. Both registers hold N − 1.

Question 24 · L06, the pin's AF number

TIM3_CH1 is AF1 on PA6, but the code puts PA6 in alternate-function mode with AF number 2. Everything else is as in the lesson: 1 µs counts, a 20 ms frame, and a report line that counts TIM3 updates per second. What does the board show?

  1. A The report still reads TIM3 50/s and CCR1 still follows the target, but the servo never moves Correct. The AF number only picks who drives the pin. TIM3 inside the chip runs as before.
  2. B TIM3 stops counting, so the report reads TIM3 0/s No. That is the missing clock gate: the registers read 0 and nothing counts.
  3. C The servo moves, but every pulse is about 2 % too long No. That is the missing −1 in PSC: 48.98 Hz, and 1500 counts take 1531 µs.
  4. D The update handler re-enters forever and millis() stops No. That is clearing UIF by writing 1. The AF number does not touch the timer's flags.

Answer: A. The AF number only picks which peripheral drives the pin. With AF2, PA6 is electrically fine but driven by another peripheral or by nothing. TIM3 inside the chip still counts, still interrupts 50 times a second and still updates CCR1: the timer works, the pin doesn't.

PA6's AF field is AFR[0] bits 27:24 (6 / 8 = 0, and 4 × 6 = 24). The number comes from the datasheet's AF table, and the same signal has different numbers on different pins: TIM3_CH1 is AF1 on PA6 but AF12 on PB6.

Exam line

A wrong AF number gives a pin that is electrically fine, driven by some other peripheral or by nothing. The timer still counts, the interrupt still fires, the report still says 50 updates a second, and the servo does not move: the timer works, the pin doesn't.

Question 25 · L06, priority follows deadline

In the lesson the TIM14 echo capture gets NVIC priority 1, the TIM3 update priority 2 and SysTick priority 3 (0 is the most urgent), though a viewer cares more about the servo, driven by TIM3, than about the clock. Which rule picks this order?

  1. A Importance to the user: the job that matters most gets the most urgent priority No. The slide rejects it: the servo matters more to a viewer, and TIM3 still gets only 2.
  2. B Deadline: the job that must be served soonest gets the most urgent priority Correct. Shortest deadline, most urgent priority: deadline-monotonic.
  3. C IRQ number: the lower IRQ number gets the more urgent priority No. TIM3 is IRQ 16 and TIM14 is IRQ 19, yet TIM14 is more urgent. The IRQ number only breaks ties.
  4. D Origin: a core exception such as SysTick always ranks below the vendor's peripheral interrupts No. SysTick's level is a field in SHPR3 like any other, and SysTick_Config chose 3.

Answer: B. Priority follows deadline, not significance (deadline-monotonic). The capture must be read before the next edge overwrites CCR1. The update only has to set CCR1 within the 20 ms frame. A late SysTick tick is still counted.

The IRQ number only breaks ties: equal priorities never preempt each other, they queue, and the NVIC takes the lower IRQ number first. Lesson 07 builds a scheduler on the same rule.

Exam line

Priority follows deadline, not significance (deadline-monotonic): TIM14 capture 1, it must read CCR1 before the next edge; TIM3 update 2, it has the 20 ms frame; SysTick 3, a late tick is still counted. Equal priorities queue, lower IRQ number first.

Question 26 · L06, SysTick's 24-bit reload

At 48 MHz, LD4 must toggle once a second while the superloop also prints report lines that each take several milliseconds. Which code does it?

  1. A SysTick_Config(SystemCoreClock); and toggle LD4 in SysTick_Handler No. ticks − 1 = 47 999 999 is more than 0xFFFFFF, so SysTick_Config returns 1 and configures nothing.
  2. B SysTick_Config(SystemCoreClock / 1000u); and, in the loop, if (now - beat_at >= 1000) { beat_at += 1000; toggle_ld4(); } Correct. A 1 ms tick fits 24 bits, the interrupt counts through every print, and the loop counts 1000 ticks.
  3. C SysTick at 1 ms with no interrupt; the loop waits for COUNTFLAG and toggles LD4 on every 1000th wrap No. COUNTFLAG remembers one wrap, so each print loses all but one of its milliseconds.
  4. D SysTick->LOAD = SystemCoreClock - 1u; SysTick->CTRL = 7u; and toggle LD4 in SysTick_Handler No. LOAD keeps only bits 23:0, 0xDC6BFF, so LD4 toggles about every 0.3 s.

Answer: B. SysTick is a 24-bit down-counter, so its longest period is 2²⁴ clocks, about 350 ms at 48 MHz. One second cannot be one SysTick period. B ticks every 1 ms (LOAD = 47999), and the loop counts 1000 ticks with now - beat_at. The interrupt keeps counting through every print.

A asks for LOAD = 47 999 999, more than 0xFFFFFF = 16 777 215, so SysTick_Config returns 1 and configures nothing: LD4 never toggles. D writes the same value directly; only its low 24 bits stay (0xDC6BFF), and LD4 toggles about every 0.3 s. C polls, and COUNTFLAG remembers only one wrap, so the heartbeat runs slow.

Exam line

SysTick is 24 bits: LOAD = ticks − 1 must fit 0xFFFFFF, so the longest period is 2²⁴ clocks, about 350 ms at 48 MHz, and SysTick_Config returns 1 for anything longer. For a slow beat, tick at 1 ms and count: if (now - beat_at >= 1000).
